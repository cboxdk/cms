# Hooks and addons

An addon extends the kernel through hooks, subscribers, schema contributions and panel contributions, all declared in its manifest and checked by `cms:build`.

## Hooks

Hooks (GUARDRAILS 2.4, PRD 6.2, 6.3, 13.6) implement one of the contracts `Cbox\Cms\Contracts\Hooks\AuthorizeHook` (returns a `HookDecision`: `noObjection()` or `deny($reason)`, never a grant), `TransformHook` (returns `FieldChanges`, each `FieldChange` one top-level field of the revision the plan writes for a `VariantRef`, the owner's or under an extender's namespace) and `ValidateHook` (returns `HookErrors`), the interface of their `#[Hook]`'s phase (`Phase::hookInterface()`); `cms:build` refuses another class with `registry_not_a_hook`. `#[Hook]`, `Phase` and the hook contracts are `#[Experimental]`, as `#[Command]`, `#[Action]` and `#[Query]` are. Each hook gets a `PlanView`, never the plan: the command's name and version, the principal, the call's classification access and the plan's mutations flattened, with every revision's fields filtered to that access by each field's classification in the `TypeCatalog` (a field above it, or undeclared, is absent). `PlanView::releases()` and `release($variant)` give each `ReleasedRevision` of the plan's releases, the `VariantReleased` with the stored revision's fields, which `CommandPipeline` reads once through `RevisionContents` before the hooks (`Domain\Dto\ReleaseRead`, carried in `HookRun::$releases`) and filters the same way; phase 5 validates the release against the same read, and a revision it cannot read is not in the view. That is how a validate hook requires a field at a release that entry.create and entry.revise never require (invariant 36). A hook of an addon gets the lower of that access and its manifest's `AddonCapabilities::$reads`, which `HookEntry::$reads` and `BoundHook::$reads` carry (`BoundHook::access()`), both in the view and in the changes it may make (invariant 21). `Cbox\Cms\Core\Pipeline\Actions\HookRunner` runs them for `CommandPipeline`: the authorize hooks after `plan()` and the kernel's shape check (a denial is `unauthorized`), then the transform hooks, each on the plan as the hooks before left it, then, after the kernel's field validation, the validate hooks (their errors are `validation_hook_failed`, after the kernel's); within a phase by priority with the lowest first, then package, then class (`Domain\Dto\BoundHook::order()`). `Domain\HookPlans` builds the view and applies changes; it refuses a change of a variant the plan writes no or several revisions of, of a field the type does not declare, or of a field above the access the hook gets, as `hook_change_refused`. Each hook is timed with the port `Domain\Stopwatch` (bound to `Adapter\HrtimeStopwatch`, `hrtime(true)`); a hook over its `budgetMs`, or hooks over `Hook::COMMAND_BUDGET_MS` (100 ms) together (`Domain\HookBudget`), reject the command with `hook_budget_exceeded` after the port `Domain\HookOverruns` (bound to `Adapter\LoggedHookOverruns`, a warning in the log) records the `Dto\HookOverrun`. The hooks of a command come from the port `Domain\CommandHooks`, bound to `Adapter\RegistryCommandHooks` (the compiled hooks registry for the command's name and version, built by the container). The tests are `packages/core/tests/Actions/CommandPipelineHooksTest.php` (`vendor/bin/pest --testsuite=Actions --filter=Hooks`) with the test hooks in `packages/core/tests/Pipeline/Probe/Hooks`; `CommandHooksBehaviour`, `StopwatchBehaviour` and `HookOverrunsBehaviour` hold the fakes to the implementations. `docs/addons/hooks.md` documents the extension point.

## The addon manifest

Addons (PRD 13.1 to 13.3, invariant 21) declare a manifest: an addon's service provider implements `Cbox\Cms\Contracts\Build\DeclaresAddon` and returns a `Cbox\Cms\Contracts\Addons\AddonManifest` from `addonManifest()`, with its Composer `package` (its scan roots carry the same name), its `AddonNamespace` (`[a-z][a-z0-9]{0,19}`, never `app` or `ext`, which throw `ReservedAddonNamespace`; anything else wrong throws `InvalidAddonManifest`), the `CoreApiVersion` it needs (read as `^major.minor`; `CoreApiVersion::current()` is 1.0), the absolute `docs` directory, `AddonCapabilities` (`reads`, the highest classification its hooks are handed, public by default), the `AllowedHook`s (command class and phase) and `AllowedSubscription`s (event class and lane) its hooks and subscribers may be, and `SchemaContributions` (field types `<namespace>:<handle>` as `ContributedFieldType` with `fieldTypeContributor`, the class of their `Cbox\Cms\Contracts\FieldTypes\FieldTypeContributor`, which an addon has exactly when it lists a field type, own types `<namespace>:<handle>` and extended types of other owners as `TypeName`, and the absolute schema directory when it owns or extends a type). The Boundary `Registry\Boundary\ProviderAddonManifests` reads the manifests of every registered provider, deferred ones included, into `Registry\Domain\Dto\DeclaredAddons`, turning a manifest that cannot be built, whose docs or schema directory is not a readable directory, or whose field type contributor is not a class that implements `FieldTypeContributor`, into a build problem that names the provider (`registry_reserved_namespace`, `registry_invalid_manifest`); `BuildRegistry::build(ScanRoots, DeclaredAddons)` passes them to `RegistryCompiler`, which refuses two manifests of one package (`registry_invalid_manifest`), two addons with one namespace (`registry_duplicate_namespace`), a core API version the kernel does not satisfy (`registry_incompatible_core_api`), a `#[Hook]` of an addon's package whose command and phase no `AllowedHook` names (`registry_undeclared_hook`) and a `#[Subscription]` of it that receives an event on a lane no `AllowedSubscription` names (`registry_undeclared_subscriber`). A package without a manifest is not an addon, and its hooks and subscribers are not limited. A hook entry of an addon names the addon and what it reads (`HookEntry::$addon`, `$reads`, keys `addon` and `reads` in `hooks.php`), a subscriber entry names the addon (`SubscriberEntry::$addon`, key `addon`), and each manifest's contributions are a `Registry\Domain\Dto\SchemaEntry` in `schema.php` (`extends`, `field_type_contributor`, `field_types`, `namespace`, `package`, `types`, sorted by namespace; `CompiledRegistry::$schema`). An addon's subscribers run as its service actor, never as the system: `cbox-cms.addons.service_actors` maps each addon's namespace to the id of the actor created when its capabilities were approved (`Core\Addons\Boundary\AddonConfig` into `Core\Addons\Domain\Dto\ServiceActors`), and `Core\Addons\Actions\ResolveSubscriberActor::for(SubscriberEntry)` gives that actor, read through the `ActorDirectory`, null for a subscriber of no addon, and throws `SubscriberActorUnavailable` (`addon_service_actor_unavailable`) when none is configured, none has the id, or it is not an active service actor. The tests are in `packages/contracts/tests/Addons`, `packages/core/tests/Actions/BuildRegistryTest.php` (fixture addon `acme/cms-reviews` in `packages/core/tests/Registry/Fixtures/Addon`, manifest from `RegistryFixtures::addonManifest()`), `packages/core/tests/Registry/ProviderAddonManifestsTest.php`, `packages/core/tests/Actions/ResolveSubscriberActorTest.php` and the addon cases of `CommandPipelineHooksTest.php`; `docs/addons/manifest.md` documents the extension point with the running example `examples/Unit/Addons/AddonManifestTest.php`.

## Panel contributions of addons

Addons' panel contributions (PRD 13.4, 13.5, 13.8) are the `panel` member of `AddonManifest`, a `Cbox\Cms\Contracts\PanelPoints\PanelContributions` (`sdk` a `PanelApiVersion`, read as `^major.minor`, `current()` 1.0; `bundle`, the absolute directory of the prebuilt bundle; `acceptsExperimental`, point ids; `contributions`), with `AddonCapabilities::$issues` (command classes the addon's UI may run, sorted, `mayIssue()`) and `$uiTheme`. A contribution implements `PanelContribution` (`id(): ContributionId`, `point()` a point id as text, `kind()`, `priority()` default `DEFAULT_PRIORITY` 1000, `scope()`, `runsCode()`), as `SlotFill`, `ActionContribution`, `NavContribution`, `PageContribution`, `DecoratorContribution`, `ReplacementContribution`, `FormCheck`, `FlowStep`, `ObserverContribution`, `ProviderContribution` and `LoginNotice` (`Confirm`, `Tone`, `Severity`, `StepPosition`); their values throw `InvalidAddonManifest` (`#[Internal]` `ContributionRules`), a scope's `InvalidPanelPoint`, both `registry_invalid_manifest` in `ProviderAddonManifests`, which also reads each manifest's bundle through `Registry\Boundary\PanelBundles` (`panel-manifest.json`, the core's schema `panel-bundle.v1.json` with the generated `PanelBundleCodecV1` over `Registry\Domain\Dto\BundleManifest` and `BundleFile`, `BundlePath`, `BundleIntegrity` (SRI sha384), `BundleFileKind`; each file's hash, and each stylesheet held to `@layer cms.addon` by `Domain\AddonLayer`) into `DeclaredAddons::$bundles`. `RegistryCompiler::compile(Discovery, DeclaredAddons, BuildSettings, ContractShapes)` first refuses a manifest whose package `BuildSettings::allows()` does not (`registry_addon_not_allowed`; `BuildCommand` reads `cbox-cms.addons.allowed`, `cbox-cms.panel.contributions` and `cbox-cms.panel.replacements` through `Registry\Boundary\BuildSettingsConfig`; the compiler's own default allows all), then `Registry\Domain\PanelCompiler` (with `PanelContext`) checks every manifest and contribution and reports `registry_incompatible_panel_api` and each `registry_panel_*` code of `BuildErrorCode` (unknown, internal and experimental-not-accepted points, kind mismatch, duplicate contribution or page path or an addon in the core's namespace `cms`, unknown command, command not issuable, action prefill and data query against the schemas, nav target, undeclared tightening, the mirror rule for an error check or a disabled reason, flow paths, unowned replacement targets, replacement conflicts, the bundle, overrides), warns with `BuildWarning::CODE_POINT_EXPERIMENTAL` and `CODE_POINT_DEPRECATED` (`CompiledRegistry::$warnings`, not cached; `BuildCommand` prints them), applies the replacement choices and overrides, and gives each addon an `AddonEntry` in `addons.php` (`RegistryName::Addons`; reads, `IssuedCommand`s, uiTheme, `AddonPanel` with `CompiledBundle`). The schemas are the port `Registry\Domain\ContractSchemas` (`shapes(): ContractShapes` of `SchemaNode`s), bound to `Adapter\CodecContractSchemas` (the command and query codecs, and point props schemas `<name>.v<version>.json` in each `PointSchemaDirectory` tagged `PointSchemaDirectory::TAG`; the panel tags `packages/panel/resources/schemas/points`), read by `Boundary\JsonSchemaNodes`; files through `Boundary\LocalFiles`. `Discovery::$packages` maps every scanned class to its package for ownership. The activation state is the port `Registry\Domain\PanelActivation` (`ConfigPanelActivation`, `cbox-cms.panel.disabled` read at each call, `InvalidPanelActivation`), which `MapPanelFills` applies (`DisabledContributions::apply()`), so cms:panel:fills shows each fill's order and enabled state and their sources; `Actions\DiscloseAddons` gives the install screen's `AddonDisclosure`s. Fakes `FakeContractSchemas` and `FakePanelActivation` with `ContractSchemasBehaviour` and `PanelActivationBehaviour`; the build tests are `packages/core/tests/Actions/BuildRegistryPanelTest.php` (`Tests\Registry\PanelBuildWorld`, fixtures `PanelHost` and `PanelAddon`, one failing case per code), and `packages/cli/tests/Console/PanelContributionOverridesTest.php`. `docs/addons/panel-contributions.md` documents it.

## The workbench's fixture addon

The workbench's fixture addon (MILESTONES M1 point 7, PRD 13.1 to 13.3, 13.7) is the Composer package `cboxdk/cms-fixture-addon` in `workbench/addons/fixtureaddon`, PHP namespace `Workbench\FixtureAddon`, addon namespace `fixtureaddon`. The root's one path repository brings it, with the options `reference: config` (the lock's reference is a hash of its composer.json, not a commit, so it is the same on every branch and in a git archive) and `versions` (1.0.0, never guessed from git), and `require-dev` requires it. It requires `cboxdk/cms: ^1.0`, which the root satisfies through its branch alias `dev-main: 1.x-dev`: Composer reads a feature branch or a detached HEAD as the nearest non-feature branch, `main`, and `docker/ci-entry.sh` commits the archive on `main`. Its manifest (`FixtureAddonServiceProvider`) reads public fields, allows the transform hook `DeriveSlug` on entry.create, which derives `ext.fixtureaddon.fixture_slug` from the owner's `fixture_title` when the revision sets none, and the validate hook `RequireSlugOnRelease` on variant.release, which requires that field on a released revision of `app:fixture_article` through `PlanView::releases()`, and extends `app:fixture_article` with `schema/fixture_article.yaml`. Testbench's package discovery registers its provider, so `cms:build` compiles its hooks; `WorkbenchServiceProvider` adds its schema root to `cbox-cms.generators.roots` under the owner `fixtureaddon`, as an application names the schema root of an addon it installs. Version 2 of `fixture_article` adds the owner's own `fixture_slug`, a field beside the addon's: the columns `fixture_slug` and `ext__fixtureaddon__fixture_slug` (the migrations `app__fixture_article_0002_add_columns` and `_0003_add_columns`). The addon's own tests are PHPUnit classes in `workbench/addons/fixtureaddon/tests` on its own Testbench test case with package discovery and a temporary bootstrap directory, in the Unit suite (`phpunit.xml` lists `workbench/addons/*/tests`); `tests/Postgres/WalkingSkeleton/AddonExtensionTest.php` runs the hooks and the field through the pipeline on Postgres with the compiled registry's hooks (`EntryWorld`'s `hooks`). After a change of the addon's composer.json, run `composer update cboxdk/cms-fixture-addon`, because the lock holds its hash.
