# The doctor, the error catalog and telemetry

Every failure of the kernel carries a code of the catalog, the doctor reports the runtime contract with the same codes, and telemetry carries codes and ids only.

## cms:doctor

`cms:doctor` (the cli's `Console\DoctorCommand`, which calls the action `Cbox\Cms\Core\Doctor\Actions\RunDoctor`) checks the installation and the runtime contract (PRD 3.3, 4.2, 13.2). A check implements the contract `Cbox\Cms\Contracts\Doctor\DoctorCheck`: `id()` (a `CheckId` such as `postgres.reachable`), `blocking()` (whether the kernel may not start while it fails; not blocking means readiness only), `requires()` (checks listed earlier that must pass, or the doctor skips it; a blocking check requires only blocking checks) and `run()`, which only looks, never throws and returns a `CheckResult`: Pass, or Fail with a `FailureKind` (`Violation` or `Unavailable`), an error code, the cause and the fix. Skip comes only from the doctor, and a check that throws, answers for another id or returns a skip from `run()` becomes the failure `doctor_check_crashed`, a violation. The exit codes are defined once, in `Contracts\Doctor\DoctorExitCode` (PRD 3.3), whose values come from the error catalog's `Contracts\Errors\ExitCode`: `Ok` (0), `Unavailable` (75, EX_TEMPFAIL), `Violation` (78, EX_CONFIG) and `NotReady` (79, status `not_ready`). When a blocking check fails, the blocking failures alone decide the code and a violation wins; when only checks that do not block fail, the code is 79, whatever their kind. The kernel may start at 0 and 79 (`allowsStart()`) and is ready only at 0. `--json` prints the document described by `packages/contracts/resources/schemas/doctor.v1.json`, encoded by the Boundary `DoctorReportJson` with every key present and keys sorted; the Codecs suite validates it with opis/json-schema. The core's checks live in `Core\Doctor\Domain\Checks` and ask `#[Internal]` probe interfaces in `Doctor\Domain\Probes`, implemented in `Doctor\Adapter`; a test swaps a probe by binding its interface, with the fakes in `packages/core/tests/Doctor/Fakes`. The runtime checks are `php.version`, `php.allow_url_fopen` (`allow_url_fopen` must be off, or the file functions fetch URLs past the SSRF guard: `doctor_php_allow_url_fopen`; a running process cannot change it, so the in-process Postgres tests fake `PhpSettingsProbe` and the command-line ones start PHP with `-d allow_url_fopen=0`), `laravel.version`, `postgres.reachable`, `postgres.version`, `postgres.app_role` (no SUPERUSER, BYPASSRLS or CREATEROLE (`doctor_app_role_createrole`), and no membership, direct or indirect and with or without INHERIT or SET, of a role that has one of them, owns relations, owns the database or a schema or has CREATE on one granted to it and not to PUBLIC, or is one of `RoleMembership::PREDEFINED_ROLES` (`pg_read_all_data`, `pg_write_all_data`, `pg_maintain`, the server file and program roles, `pg_signal_backend`, which cancels and terminates the owner role's sessions, and `pg_read_all_stats` and `pg_monitor`, which show the query text of every session): `doctor_app_role_privileged_membership`; `pg_database_owner` is fixed by the ownership of the database, not by REVOKE), `postgres.transaction_timeout` (above zero and from the role: `pg_settings.source`, which the probe parses into the enum `Doctor\Domain\SettingSource` and fails on an unknown text, is `user` or `database user`), `postgres.idle_in_transaction_timeout` (the same rule for `idle_in_transaction_session_timeout`, PRD 7.4: `doctor_idle_in_transaction_timeout_missing`; `roles.sql` sets it on the app role at the command budget), `postgres.prepared_transactions`, `postgres.lc_messages` (lc_messages of the app role and of the owner role, the owner's read as the app role from `pg_db_role_setting` with the server default of the app role's session as the fallback, and LC_MESSAGES of the PHP process, which libpq follows, must be `C`, `POSIX`, `C.<charset>` or `en_*`, because `MissingPartitionMapper` and `PostgresErrors` match English text; `docker/postgres/conf.d/cms.conf` sets `lc_messages = 'C'` as the server default and `roles.sql` on both roles), `postgres.ddl_privileges` (counts the relations owned by the role or by any role it is a member of, `pg_has_role(current_user, relowner, 'MEMBER')`), `postgres.row_security` (every table and partitioned table outside the system schemas, partitions included, with `relrowsecurity` also has `relforcerowsecurity`, so the policies hold for the owner too: `doctor_row_security_not_forced`), `postgres.extensions` (the extensions the core's tables need, `ExtensionsCheck::REQUIRED`, which is ltree, are installed in the database, as `pg_extension` lists them: `doctor_extension_missing`), `postgres.oldest_xact` (not blocking; the two alarms of the horizon, PRD 4.2, 7.4: the oldest client backend on the server that holds a transaction id, `doctor_horizon_held`, and the oldest of the current database that holds a snapshot, `doctor_snapshot_held`, each older than 5 s, the command budget, measured from `xact_start` in `pg_stat_activity`; the app role sees `xact_start` only for its own sessions, so the sessions of other roles are counted and named without an age and never fail it), `valkey.reachable`, `partitions.runway` (not blocking; the unbroken run of partitions from now must reach `partition_runway_days` ahead) and `registry.cache` (not older than `vendor/composer/installed.json`), `events.lag` (not blocking; `EventLagCheck`, with the probe `EventLogProbe`, bound to `Doctor\Adapter\ConnectionEventLogProbe`: for each subscription of the registry cache the first event past its cursor, per stream in (xid, event_id) order, of a type it receives, committed and whether or not below the horizon, whose age at the Clock's time must be within the lag target of its lane, `EventLagCheck::targetMilliseconds()`: critical 500 ms, standard 60 s, external 5 min, revalidate 2 s, background best effort and never failing: `doctor_events_lag`, or `doctor_event_log_unreadable`), `events.parked` (not blocking; no row of `event_parked_aggregates` without `released_at`: `doctor_events_parked`) and `postgres.owner_credentials` (not blocking; fails with `doctor_owner_credentials_exposed` when the owner connection is configured in a process whose environment does not declare it the maintenance process with `CBOX_CMS_MAINTENANCE_PROCESS` (`true` or `1`; read by `DoctorConfig`, never from the configuration, which the processes may share through one cache), or that serves HTTP or runs queued jobs); `--dev` adds `dev.node`, `dev.playwright` and `dev.chromium`, which do not block. The Postgres probes share the scoped connection `cms_doctor`, a copy of the app role's connection with `PDO::ATTR_TIMEOUT`, because pdo_pgsql ignores `connect_timeout` in the DSN; The doctor never logs in as the owner role (PRD 4.2): the owner role is `cbox-cms.doctor.owner_role`, or when that is null the username of `cbox-cms.doctor.owner_connection` (null means `cbox-cms.database.owner_connection`) when this process has that connection. Only the maintenance process, which runs the migrations and `cms:partitions:maintain` and serves no HTTP, gets the owner connection: `CoreServiceProvider::boot()` throws `Process\Domain\OwnerCredentialsExposed` (`owner_credentials_exposed`) in a process that serves HTTP or runs queued jobs with the owner connection (`cbox-cms.database.owner_connection` or `cbox-cms.doctor.owner_connection`) configured, as the Boundary `Process\Boundary\ProcessWorkload` reads it from the process: not in the console or `LARAVEL_OCTANE` set is HTTP, and the artisan command `queue:work`, `queue:listen`, `horizon`, `horizon:supervisor` or `horizon:work` is a queue. The workbench gives `pgsql_owner` to its console processes only, and phpunit.xml and testbench.yaml set `CBOX_CMS_MAINTENANCE_PROCESS=true`; a test runs in another process's environment with `Cbox\Cms\Core\Tests\Process\ProcessEnvironment::during()`. The settings are `cbox-cms.doctor`; an invalid one gives the single failing check `doctor.config`. An application or addon adds checks by class name in `cbox-cms.doctor.checks`, run after the core's runtime checks, and `cbox-cms.doctor.dev_checks`, run with `--dev` after the development checks; the container builds them (`Doctor\Adapter\ContainerDoctorChecks`), `OrderedDoctorChecks::with()` holds them to the core's rules, and a class that cannot be used, a repeated id, a requirement that does not run before the check or a blocking check that requires one that does not block also gives `doctor.config`. The workbench's doctor reads the dev database `cms`: run `composer services:up` and then `composer dev:prepare` from the main checkout first, or `partitions.runway` fails with `doctor_partition_table_unmanageable`. The testkit has `FakeDoctorCheck` and the shared suite `DoctorCheckContract`, which every core check runs in `packages/core/tests/Contract` with fake probes.

## The error catalog

The error catalog (PRD 6.1, GUARDRAILS 2.1, 7.2) is the enum `Cbox\Cms\Contracts\Errors\ErrorCode` in the contracts module: every error code of the kernel, lowercase words joined by underscores (`ErrorCode::PATTERN`), never renamed, with the case named after the code in PascalCase. `entry()` gives an `ErrorEntry`: the `HttpStatus`, the CLI `ExitCode` (0, the sysexits codes 64 to 78, and 79 for not ready), the `McpResponse` (a tool result, a tool result with isError, or the JSON-RPC error -32603), whether a retry makes sense, an explanation in plain language that says what to do, and `docs()`, the code's section of `docs/reference/errors.md`. The concrete cause of one failure is not in the entry; the error that carries the code gives it. A class that fails with a code names it in a constant `CODE` or `CODE_<NAME>`, or in an enum whose name ends in `ErrorCode` (`BuildErrorCode`, `GenerateErrorCode`), and adds its entry to the catalog in the same change; `tests/Arch/ErrorCatalogTest.php` (`Cbox\Cms\Tests\Support\Arch\ErrorCodeScan`, covered by `tests/Feature/Tooling/ErrorCodeScanTest.php`) fails when a code of `packages/*/src` has no entry, and when an entry is declared or used by no code; an entry added before its user exists sits in `ErrorCodeScan::RESERVED` with where it will be used, and leaves it with the task that uses it. `cms:generate` and `cms:schema:editor` exit with the entry's exit code, and `DoctorExitCode` takes its values from `ExitCode`. `composer docs:errors` (`tools/bin/docs-errors.php`, `Cbox\Cms\Tooling\Docs\Domain\ErrorReferencePage`) writes `docs/reference/errors.md` from the catalog, and gate 10 fails when the page differs. The kernel's default wait budget for an idempotency claim, after which a command is rejected with the retryable `idempotency_in_flight` (`InFlight::CODE`), is `cbox-cms.idempotency.wait_budget_ms` (2000), read by `IdempotencyStore\Boundary\IdempotencyConfig` into the container's `IdempotencyStore\Domain\Dto\IdempotencySettings`.

## Telemetry

Telemetry export is the contract `Cbox\Cms\Contracts\Telemetry\Telemetry` (GUARDRAILS 2.3, 5): `span(SpanRecord)`, `counter(CounterRecord)` and `histogram(HistogramRecord)`, each exported once in order, and an export never throws, so a record the backend does not take is dropped. Names are `TelemetryName`s (dotted lowercase segments, the kernel's under `cms.`), `Attributes` are scalar `Attribute`s sorted by name, a span's start is the Clock's time in UTC and its duration nanoseconds of the monotonic `Stopwatch`. `cbox-cms.contracts` binds it to `Core\Telemetry\Adapter\LogTelemetry`, which writes each record as a structured entry on Laravel's log (`cms.span`, `cms.counter`, `cms.histogram`, the record in the context, a span with status error at warning) and drops it when the logger throws; an OpenTelemetry exporter on laravel-telemetry belongs to the app template. The testkit has `FakeTelemetry` and the shared suite `TelemetryContract` with its `TelemetryHarness`; the core runs it against `LogTelemetry` in `packages/core/tests/Contract/LogTelemetryContractTest.php`. The command and query pipelines run every call inside `Core\Telemetry\Domain\PipelineTelemetry` (`command()`, `query()`), so no action is instrumented by hand: one span named after the action, ok or error, with `cms.action`, `cms.action.version`, `cms.action.kind`, `cms.outcome` (`exception` for a call that threw, which throws on after the export), the changeset and commit position of a committed command, the correlation id (a `QueryCall` takes an optional `CorrelationId`), the first error's catalog code, and more; the histograms `cms.command.duration` and `cms.query.duration` in milliseconds; and the counters `cms.command.errors` and `cms.query.errors` for a call rejected or thrown. Attributes hold only ids, names, codes and counts: never a field value (invariant 10), an error or exception message or an actor id. `docs/addons/contracts/telemetry.md` lists every attribute; `packages/core/tests/Actions/PipelineTelemetryTest.php` holds the pipelines to it.
