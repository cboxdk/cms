# The registry

`cms:build` compiles every attribute of the scan roots into the registry files the kernel reads at run time; reflection happens at build time only.

## The compiled registry

The registry (PRD 13.2) is compiled by `cms:build` (the cli's `Console\BuildCommand`, which calls the action `Cbox\Cms\Core\Registry\Actions\BuildRegistry`) to `bootstrap/cache/cms/`: `actions.php`, `addons.php`, `commands.php`, `hooks.php`, `panel.php`, `rest.php`, `schema.php` and `subscribers.php`, one per case of `Registry\Domain\RegistryName`, and the REST surface's `openapi.json`. The cache owns that directory: after writing the files, `FileRegistryCache` removes every other file there, but not its lock file `.lock`, subdirectories, the temporary file of a registry, or `openapi.json` and its temporary file, so a registry an earlier version wrote cannot linger. Each file returns `['build' => '<sha256>', 'entries' => [...], 'format' => 11, 'registry' => '<name>']`, sorted and without timestamps or paths, so two builds of the same code give the same bytes; `build` is the sha256 of the entries of every registry, so the files of one build carry the same one and `RegistryCacheCodec::decode()` refuses files of different builds and entries that do not match their build. A write puts every file in a temporary file first and then renames them into place one after the other, so a reader can meet the files of two builds; `FileRegistryCache::read()` then tells OPcache to forget them and loads them again, up to `FileRegistryCache::READ_ATTEMPTS` (10) times 5 ms apart, and so gives the whole old or the whole new registry. Files that stay mixed, as a build that stopped between two renames leaves them, are `MalformedRegistryCache` until cms:build runs again. Writes run one at a time, so two builds that both finish never interleave their renames: a write holds an exclusive `flock()` on `FileRegistryCache::LOCK_FILE` (`.lock` in the directory, never removed) from before its first rename until it has removed the other files, waits for it at most `FileRegistryCache::LOCK_WAIT_MILLISECONDS` (30 s) of real time, and otherwise writes nothing and throws `RegistryCacheUnwritable`; reads take no lock. `packages/core/tests/Registry/FileRegistryCacheInterleavingTest.php` puts a build's renames between a read's files through the stream wrapper `Fakes\InterleavedFiles`. A module's or an addon's service provider implements `Cbox\Cms\Contracts\Build\DeclaresScanRoots` and returns `ScanRoot`s, each a Composer package name and an absolute directory (`__DIR__`); core, http, cli, mcp and generators declare their `src` under the package name `cboxdk/cms`, and deferred providers are asked too. The scanner, `Registry\Infrastructure\AttributeScanner`, reads the classes each `.php` file declares from its tokens, loads them through the autoloader and reads `#[Action]`, `#[Command]`, `#[Query]`, `#[Hook]` and `#[Subscription]` with reflection; reflection is allowed at build time only (GUARDRAILS 2.2). Actions are sorted by the name and version of the command or query they handle, commands by name and version, hooks by command, phase in pipeline order, priority with the lowest first, package and class, and subscribers by subscription name. An `ActionEntry` holds the action class and its package, its `ActionKind` (`write` for a class that implements `WriteAction`, `query` for one that implements `QueryAction`), the command or query it handles by `CommandName`, version and class, and its surfaces in the order of `Surface`; `#[Action(handles: ...)]` names the handled class, which must be a registered `#[Command]` class for a write action and a registered `#[Query]` class for a query action. A command and a query never share a name and version (`registry_duplicate_command`). The build fails with `registry_not_an_action` for an `#[Action]` class that implements neither or both interfaces, `registry_unknown_action_command` for an action whose handled class is not a registered one of its kind, `registry_duplicate_action` for two actions of one command or query, and `registry_unknown_surface` for a surface that is not a case of `Surface` (`UnknownSurface`, or an undefined case such as `Surface::Graphql`). `CompiledRegistry::action($name, $version)` and `actionFor($class)` give the kernel the action of a command or query. A `#[Command]`, `#[Query]`, `#[Action]` or `#[Subscription]` class must be `final readonly` (GUARDRAILS 2.1), or the build fails with `registry_not_final_readonly`; a `#[Hook]` needs a `#[Command]` class and a budget of 1 to 20 ms, and its class must implement the interface of its phase, or the build fails with `registry_not_a_hook`. A build with problems writes nothing and lists every problem with a code from `BuildErrorCode`, such as `registry_duplicate_command` and `registry_unknown_hook_command`; the command then exits 65, and 73 when a cache file cannot be written or removed. At run time the container's `CompiledRegistry` singleton is read through `RegistryCache` and the Boundary `RegistryCacheCodec` into typed entries in `Registry\Domain\Dto`; a missing file throws `RegistryCacheMissing` and a damaged one `MalformedRegistryCache`. A command's name, `CommandEntry::$name` and `HookEntry::$command`, is the id `Cbox\Cms\Contracts\Ids\CommandName` (GUARDRAILS 2.2), never a string: the scanner takes it from `Command::name()`, the codec parses it and reports a bad one at `entries[<n>].name` or `entries[<n>].command`, and the compiler compares names by value. A registry is a case of `RegistryName` only when it has an entry type and a source. The panel registry (PRD 13.4), `panel.php`, holds the panel's extension points: `#[PanelPoint]` (`Cbox\Cms\Contracts\PanelPoints\PanelPoint`, with `PointKind`, `Region`, `Multiplicity`, `Ownership`, `ReplacementKey`, `Tighten`, `Scope`, `PointName`, `PageName`, `PointId`, `ContributionId` and `CommandRef`, which throw `InvalidPanelPoint`) on a final readonly props class with exactly one stability attribute, which is the point's (`Registry\Domain\PointStability`); each point is a `Registry\Domain\Dto\PanelPointEntry` under its id `<name>@<version>`, sorted by name and version, with its contributions (`PanelFill`: the contract contribution as the manifest declares it, package, the compiled priority and `ordering`, `enabled` and `enabling` as `Registry\Domain\FillSource`, the resolved `command` and data `query`) in render order, priority, then namespace, then id; the contributions come from the addon manifests' `panel` member (see [the addons' panel contributions](hooks-and-addons.md#panel-contributions-of-addons)), and a point may carry `deprecated: new PointDeprecation(since, removeIn, replacement)`. The build fails with `registry_duplicate_panel_point`, `registry_panel_point_without_stability` and `registry_panel_point_without_downcast`, an older version of a point whose props class does not implement `Cbox\Cms\Contracts\PanelPoints\DowncastsFromNewest` (template: the newest version's props class; the panel builds the newest props only, and `Registry\Domain\PointDowncasts::props()` gives any version's from them, `PointDowncastRefused` for props of another class), and `CompiledRegistry::panelPoint()` and `panelPointsOf()` read it. `tests/Feature/Panel/RenderedPanelPointsTest.php` (`Tests\Support\Panel\RenderedPanelPoints`) holds the pages of `js/panel/src`, which render a point with `<PointHost point="<name>@<version>">`, to the installation's points: each rendered point is declared and each declared point is rendered. A `SubscriberEntry` (PRD 7.6) holds the subscriber class and its package, its `SubscriptionName`, its `Lane`, the `ProjectionName` it acknowledges on the receipt or null, and its events, each a `SubscribedEvent` of the event class and the `EventType` its `type()` gives, sorted by class; the build fails with `registry_not_a_subscriber` for a `#[Subscription]` class that does not implement `Subscriber`, `registry_unknown_event` for an event class that does not exist, does not implement `Event` or whose `type()` fails, `registry_unknown_lane` for a lane that is not a case of `Lane` (`UnknownLane`, or an undefined case such as `Lane::Urgent`), and `registry_duplicate_subscription` for two subscribers with one name. `CompiledRegistry::subscribersOf($eventClass)` and `projectionsFor($eventClass)` give the kernel the subscribers of an event class and the projections it affects, which a receipt lists (PRD 8.4). The doctor's `registry.cache` check dates the cache by the oldest of the files of `RegistryName`. Composer's `post-autoload-dump` runs `testbench cms:build`, and the cache is not committed. The registry's test fixtures live in `packages/core/tests/Registry/Fixtures`, one directory per scan root.
