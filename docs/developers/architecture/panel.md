# The panel module

The panel is the PHP module `Cbox\Cms\Panel` with its React app in `js/panel` and the SDK in `js/panel-sdk`; `docs/developers/panel.md` is the operator's page, this one is the architecture note.

## The module, its routes and its policy

The panel module (PRD 13.4, GUARDRAILS 6 and 8) is `Cbox\Cms\Panel`, a surface. An application mounts it in its web routes with `PanelRoutes::register($router, $prefix = 'cms')` (`#[Experimental]`); the workbench mounts it at `/cms`. Below the prefix: `GET build/{path}` (`PanelRoutes::ASSET`, `Assets\AssetController`), which serves through `Boundary\PanelAssetResponse` only the files the build's manifest names (`Domain\Dto\PanelBuild::serves()`, `FILE_PATTERN`), with their content type, `Cache-Control: public, max-age=31536000, immutable` and nosniff, and 404 for any other path; then every panel page behind `Middleware\SendContentSecurityPolicy` and `Boundary\HandlePanelRequests` (Inertia's middleware with the root view `cms-panel::app` and the build's version, so a stale page reloads with 409); last, any other path (`PanelRoutes::NOT_FOUND`, `Pages\NotFoundController`), the Inertia page `Errors/NotFound` with 404 (`Boundary\PanelPages`), so a route a later task adds is registered before it. `SendContentSecurityPolicy` makes a `Domain\CspNonce` (16 random bytes in base64) per response for the page's styles, puts it on the request (`NONCE`), records the hash of each inline script the root view writes (`allowInlineScript()`, the import map) and sends `Domain\ContentSecurityPolicy::header()` of a `Domain\Dto\PagePolicy`: `default-src 'self'`, `script-src 'self' 'sha256-…'` (decision D6: no nonce and no `'strict-dynamic'` for scripts, because a browser hands a script's nonce on to what it `import()`s, and only `'self'` with hashes keeps `import()` on the panel's origin), `style-src 'self' 'nonce-…'`, `img-src 'self' data:`, `font-src`, `connect-src` and `form-action` `'self'`, `frame-src`, `object-src`, `base-uri` and `frame-ancestors` `'none'`, `report-uri` and `report-to cms-csp` to `POST <prefix>/csp-report` (`PanelRoute::CspReport`, `Reports\CspReportController`, outside the CSRF check, with `Reporting-Endpoints` on the response), never `unsafe-inline` or `unsafe-eval`; `Boundary\CspReportInput` reads the Reporting API's and a report-uri report and `Actions\RecordCspReports` counts them on `cms.panel.csp_violations` by directive and addon, ids only. The root view's composer `Views\PanelRootView` gives it the nonce, the locale for `<html lang>` and the addresses of the build's entry script, stylesheets and module preloads, each with the nonce, and a `<meta property="csp-nonce">`, from which `js/panel/src/app.tsx` hands Inertia the nonce for the style elements it adds. Addon files (PRD 13.4): `GET addons/{addon}/{hash}/{path}` (`PanelRoute::AddonAsset`, `Assets\AddonAssetController`, `Boundary\AddonAssetResponse`) serves only a file the compiled registry lists for the addon, below the bundle's `Domain\BundleHash` (the SHA-256 of the compiled files' paths and SHA-384s), read from the directory the addon's provider names (`Boundary\ProviderBundleDirectories` into `Domain\Dto\BundleDirectories`, `Boundary\InstalledBundles` into `Domain\Dto\ServedBundles`), immutable, nosniff and `Cross-Origin-Resource-Policy: same-origin`, 404 for any other address, and refuses a file whose bytes are not the compiled SHA-384 with the problem details of `panel_asset_hash_mismatch`. Only a route whose `PanelRoute::allowsAddons()` is true (home and the Inertia command route) carries `PanelRoutes::ADDONS` true in its action; the credential routes, the not-found page and every file route carry false (`packages/panel/tests/Feature/CredentialRoutesWithoutAddonsTest.php`), every redirect across the login boundary (`PanelSessions::redirect()`: a login, a logout, a session that no longer verifies) is a full page load, 303 for a browser and `PanelSessions::FULL_PAGE` (409 with `X-Inertia-Location`) for an Inertia visit, because a document's import map cannot change once it is loaded, and on an allowed page `Boundary\AddonAssetUrls` writes every bundle into the import map (the entry under `cms-addons/<namespace>`, `ImportMap::withAddon()`, a scope with the refused modules and the integrity of each script) and links its stylesheets. `CBOX_CMS_PANEL_DEV_ADDONS=<ns>=<loopback origin>,…` (`Boundary\DevAddonsEnvironment` into `Domain\Dto\DevAddons` of `DevServer`s) maps an addon to its Vite dev server instead (`ImportMap::withDevServer()`: the entry at `<origin>/@cms-panel-addon/entry`, the shared modules at `<origin>/@id/<specifier>`, the server's client on the page, and the origin and its websocket in `script-src` and `connect-src` on addon pages alone); it works only in the local environment: `PanelServiceProvider::boot()` throws `Domain\PanelDevServerForbidden` in a process that serves HTTP or runs queued jobs elsewhere, and `Domain\InvalidDevAddons` for a value it cannot read, while a console process boots so `cms:doctor` can report it. The module's doctor checks are `panel.branding`, `panel.addons` (`Doctor\Domain\Checks\AddonBundlesCheck`, not blocking, requires `registry.cache`: the bundles on disk against the compiled hashes, `doctor_panel_addons_changed`) and `panel.dev_server` (`DevServerCheck`, blocking: the variable unset or local and readable, `doctor_panel_dev_server_forbidden`), with probes in `Doctor\Domain\Probes` and `Doctor\Boundary`. The shared modules are React's four, the SDK's `@cboxdk/cms-panel/ui`, `/extend` and `/experimental` (`ViteManifest::SDK`), and the refused ones `@inertiajs/*`, `react-aria-components` and `@cboxdk/cms-ui-kit` (`js/panel/shared-modules.json`). An addon builds its bundle with `@cboxdk/cms-panel/vite` (`js/panel-sdk/vite.js`: `cmsPanelAddon({ namespace, contributions, budget })`, externals, the refused imports, the lint of built code, layered and scoped CSS, the size budget and `panel-manifest.json` with SHA-384s; `npm run test:js -- vite`). The build is `composer panel:build` (`npm run build --workspace=@cboxdk/cms-panel-app` through `composer image:run`, so it uses the checkout's `node_modules` volume, never the host's macOS one) into `packages/panel/dist`, which git ignores; `PanelServiceProvider` binds `PanelBuild` lazily from `dist/.vite/manifest.json` (`Boundary\ViteManifest`, entry `src/app.tsx`, version the SHA-256 of the manifest), so a process without the build boots and a panel page fails with `Domain\PanelBuildUnavailable`, which names `composer panel:build`. The prebuilt distribution a release carries comes with part 2 of B1; the panel's extension points are in the panel registry `panel.php` (see [the registry](registry.md)). The panel's own tests (`packages/panel/tests`) bind a `FixtureBuild` and never need `composer panel:build`. `docs/developers/panel.md` documents it.

## The login

The panel's login (PRD 5.16, GUARDRAILS 6) is in the panel module and the identity module's feature `Cbox\Cms\Identity\Login`. `PanelRoutes` adds, behind `Middleware\VerifyPanelCsrfToken` (Laravel's `PreventRequestForgery`, which here checks while unit tests run too), `GET <prefix>/login` (`Domain\PanelRoute::Login`, `Pages\LoginPageController`, the Inertia page `Auth/Login`, or the start for a session that verifies) and `POST <prefix>/login` (`LoginSubmit`, `Pages\LoginController`: `Boundary\LoginForm` reads `email` and `password`, the action `Identity\Login\Actions\LogInLocally` decides, `LoginForm` answers); and behind `Middleware\AuthenticatePanelSession` and the CSRF check, `GET <prefix>` (`Home`, the page `Home`), `POST <prefix>/logout` (`Logout`, `EndSessions::logout()`) and the Inertia command profile `POST <prefix>/commands/{command}/v{version}` (`Command`, `InertiaRoutes::register()` with that name). `LogInLocally::login(LocalLoginRequest): LoginOutcome`, whose request `LoginForm` parses with the identity module's `Login\Boundary\LoginInput` (the email as a `Login\Domain\Dto\TypedLogin`, missing, unreadable or a `LoginIdentifier`; the password as a `?Password`; the IP as a `?Login\Domain\ClientAddress`, which refuses an empty or invalid address and holds its canonical text), as `PasswordResetForms` parses `ResetRequest` and `PasswordResetSubmission` (with `PasswordResetToken::parse()`): empty fields are `validation_required` per field and not counted, and an unreadable identifier or a missing client address is `login_rejected`, not counted and not checked (a reset request without an address sends nothing); the port `Login\Domain\LoginThrottle` (bound to `Login\Adapter\ValkeyLoginThrottle`, one Lua script, keys `cms:login_throttle:<identifier|ip>:<HMAC-SHA-256>` under `Login\Domain\Dto\ThrottleSecret`, derived from `app.key` by `Login\Boundary\ThrottleSecretConfig`, never a plain SHA-256 of an email or address, which could be reversed; `FakeLoginThrottle` and `LoginThrottleBehaviour` in `packages/identity/tests/Login`) counts the attempt under the identifier and the IP first, and one above `cbox-cms.identity.login.throttle` (5 per identifier, 50 per IP, in 900 s) is `login_rate_limited` (429) with the counter `cms.login.rate_limited`; then the `LocalConnection` starts and completes in one request, `CheckLoginPolicy` decides with the method password, and any refusal is `login_rejected`; a success takes itself back from the throttle, ends the session the browser carried and issues a new one. The login page hosts `login.notice@1` (`Panel\Login\Domain\Login`, the page `login`; `Login\Domain\Dto\LoginNoticeV1`, a data point without props, schema `points/login.notice.v1.json`, codec `LoginNoticeCodecV1`): `Pages\LoginPageController` hands `PanelPages::login()` the `Login\Domain\Dto\LoginNotices` the action `Login\Actions\ResolveLoginNotices` works out from the registry and the activation state, the enabled `LoginNotice` fills in render order, each a `Domain\Dto\LoginNoticeProp` (addon, id, message key, `Tone`), the prop `notices` of `login.v1.json`; a registry or activation state that cannot be read gives none, recorded as `Withheld` in telemetry, so nothing an addon does keeps a person from the form. The page renders them with `<PointHost point="login.notice@1" notices={notices} />`, the host's `NoticesHost`, which renders each as a kit callout in the scope element of its contribution and loads no addon: a credential page has no `cms.contributions` and no addon in its import map (`CredentialRoutesWithoutAddonsTest`). The tests are `packages/panel/tests/Actions/ResolveLoginNoticesTest.php`, `packages/panel/tests/Feature/LoginNoticesPageTest.php`, `js/panel/tests/host/notices.test.tsx` and the login cases of `tests/Browser/Panel/PanelAddonsTest.php`. `Boundary\PanelSessions` keeps the two sessions: the CMS session cookie (`SessionCookie`, no expiry, left out of `EncryptCookies`) is the only credential; Laravel's session holds Inertia's flash data, the errors prop, the CSRF token and `BINDING`, the SHA-256 of the CMS session id. At a login both get new ids and Laravel's is bound; at every other request the verifier verifies and renews the CMS session, a Laravel session bound to another one is emptied (new id and token) and bound, and the session credential goes on the request for `Http\Credentials\Boundary\RequestCredential`, which the Inertia profile reads before the Bearer header (REST stays Bearer only); a refused or missing session redirects (303) to the login page with `Domain\SignInReason` (`required`, `expired`, `ended`, `revoked`, `signed_out`). At a logout both end and both cookies are cleared, Laravel's after its own middleware by `PanelSessions::clearCookies()` on `RequestHandled`. `Boundary\HandlePanelRequests` shares the Inertia profile's `problem` prop. The tests are `packages/panel/tests/Feature/SessionCookieTest.php`, `InertiaSessionTest.php`, `LoginRateLimitTest.php` (over `Identity\Tests\Login\LocalLoginWorld`), `packages/identity/tests/Actions/LogInLocallyTest.php` and `tests/Browser/Panel/LoginTest.php`; `docs/security/sessions.md` documents it.

## The props of the points

The props of the panel's points (GUARDRAILS 2.2, PRD 13.4) are generated as the pages' are: each contributable (`#[Stable]` or `#[Experimental]`) point has a JSON Schema `packages/panel/resources/schemas/points/<name>.v<version>.json` bound to its props class by the tooling's `Cbox\Cms\Tooling\Protocol\Domain\PanelPointSchemas::all()` (`point()`: codec `<Props without V<n>>CodecV<n>`; `Protocol\Boundary\PointDeclaration` holds the binding to the class's `#[PanelPoint]` and refuses an `#[Internal]` point), and `composer generate:protocol` writes the codecs into `packages/panel/src/Boundary/Generated/Points`, `js/panel-sdk/src/generated/validation.ts` and a module per point `js/panel-sdk/src/generated/points/<Props>.ts` (types, `validate<Props>()` and `sample<Props>()`), and the compatibility lock `packages/panel/resources/points.lock.json` (`Protocol\Boundary\PointsLock`: per `#[Stable]` point its schema, the sha256 of its contract, the schema as canonical JSON without `title`, `description`, `examples` and `$comment`, and the contract itself; it refuses with `generate_schema_invalid` every change to a locked point but an added optional member and a documenting change). The sample props come from the generators' `Protocol\Boundary\SampleProps` (every member; the first of `examples`, which `JsonSchemaContract` accepts and a patterned string must give, the first enum value, or the least value its rules accept). The panel declares no point until a page renders one, so `all()` is empty and the lock holds no point. The pipeline is held on the fixture points of `packages/panel/tests/Points/PanelPointFixtures` (golden codecs, TypeScript and lock below `Fixtures`, `PanelPointGenerationTest`), `tests/Codecs/PanelPointCodecsTest.php` (sample round trips and opis/json-schema), `tests/Codecs/TypeScriptValidatorsTest.php` (the TypeScript validator against the PHP codec on every rule and place, `Tests\Support\Panel\PointViolations`), `tests/Feature/Tooling/Protocol/PointsLockTest.php` and `tests/Feature/Panel/PanelPointSchemasTest.php` (every contributable point of the installation bound, `Tests\Support\Panel\PointBindings`). `docs/addons/panel/points/_index.md` documents it.

## Active contributions

Active contributions (PRD 13.4) are worked out per request and page in the panel's feature `Cbox\Cms\Panel\Contributions`. A page behind the login names the points it renders as `Domain\Dto\RenderedPoint`s (point name and the newest version's props object) in a `Domain\Dto\PanelView` (page name, the viewer's `ActorPrincipal`, the points, and a `ViewSubject` of the command, type and field types it is about), which `Boundary\ContributionProps::view()` builds from the principal `PanelSessions` put on the request. The action `Actions\ResolveContributions` reads the registry through `RegistryCache` and the activation state through `PanelActivation` (either unreadable gives no contributions and the telemetry reason `Domain\Withheld`), takes every version of each rendered point on the page with its props through `PointDowncasts`, keeps the enabled fills whose `Scope` names the page and fits the `ViewSubject` (`ViewSubject::fits()`), asks the core port `Access\Domain\HeldPermissions` (bound to `Access\Adapter\TransactionalHeldPermissions`: one transaction of its own, the `PostgresAccessResolver`, the grants with their roles' permissions, `PermissionRule::query()` for the actor and every actor of its chain) once for every `requires`, drops each fill whose permission the viewer does not hold, and gives `Domain\Dto\ActiveContributions` of `ActiveFill`s at the lower of the viewer's classification access and the addon's `reads`. `Boundary\ContributionProps::props()` writes them as the prop `cms.contributions` with the generated `ContributionsCodecV1` (`packages/panel/resources/schemas/pages/contributions.v1.json`, DTOs `ContributionsProp`, `PointFillsProp`, `FillProp` in `Panel\Domain\Dto`), the viewer's actor id as `viewer`, which the host names in every form check's context (`CheckContext.viewer`), each fill's props written by the point's codec from `Domain\PointCodecs` (the generated `Boundary\Generated\Points\PanelPointCodecs` and every `PointCodec` tagged `PointCodecs::TAG`) at the fill's access; a point without a codec loses its fills. A point whose props exist only in the browser, such as the receipt a command form shows, is rendered with no props (`RenderedPoint::heldByPage()`, `PointInScope::$props` and `ActiveFill::$props` null, which `PointDowncasts::props()` passes through): its fills are resolved as any other, sent with `props: null`, and the page builds the props, typed by the point's generated TypeScript, and hands them to the host, which gives them to each contribution in place of the server's; such a point gives a data query no input (`QueryInput::of()`). Per addon whose fills read data it adds the Inertia `DeferProp` `ext.<namespace>` (group the namespace), which takes each query's input from the fill's props by name (`Boundary\QueryInput`), reads it with the query's codec from `QueryCodecs` and runs the action `Actions\RunContributionData`: the `QueryPipeline` with the viewer's credential, `Surface::Inertia` and the `QueryCall`'s `ceiling` at the fill's access (the `AccessResolver` lowers the context's classification access to it), within the actor's query budget; the result is written by the query's result codec under the contribution's id, and a rejected, refused or failed query leaves it absent while the page answers 200 (a failure goes to the exception handler). A controller hands the action's `run()` and `refused()` to the Boundary as closures. `Domain\ContributionTelemetry` records `cms.panel.data.duration`, `cms.panel.data.errors` and `cms.panel.contributions.withheld` per addon, contribution, point and page with codes only (`docs/addons/contracts/telemetry.md`). The start page sends them for the page `home` (`PanelPages::HOME_PAGE`). The tests: `packages/panel/tests/Actions/ResolveContributionsTest.php` and `RunContributionDataTest.php` (`Tests\Contributions\ContributionWorld` with the fixtures `Desk` and `Tally`, `ResolveWorld`), `packages/panel/tests/Contributions` (`ContributionPropsTest`, `ViewSubjectTest`, `PointCodecsTest`), `packages/panel/tests/Postgres/ActiveContributionsTest.php` and `ContributionDataTest.php` (`DeskWorld`: a test page over HTTP as the app role), `HeldPermissionsBehaviour` and `tests/Codecs/ContributionsCodecTest.php`; `docs/addons/panel/contributions.md` documents it.

The page also carries the addons' texts of its locale, so a contribution's `t()` gives a text and never its key (section 2.6 of the panel extension architecture; `docs/ui/i18n.md`). An addon ships one catalogue per locale the panel ships (`Contracts\PanelPoints\PanelLocale`, `da` and `en`, read from a language tag with `PanelLocale::of()`) in the directory its `PanelContributions::$lang` names, `<locale>.json`, a flat object from a key below the addon's namespace to its text. `cms:build` reads them in `Core\Registry\Boundary\PanelCatalogues` into `Domain\Dto\AddonCatalogues` (a `PanelCatalogue` per locale and the problems of the files on disk), which `ProviderAddonManifests` puts on `DeclaredAddons::$catalogues` by package, as it does the bundles; `Registry\Domain\PanelCompiler::catalogues()` reports every problem of the files and every key outside the addon's namespace as `registry_panel_catalogue_invalid`, and, once the files can be read, a locale without a catalogue or a key one locale has and another has not as `registry_panel_translations_incomplete`, and keeps the rest on `AddonPanel::$catalogues` in `addons.php` (registry format 11). An addon that names no directory ships no texts. Per request, `Contributions\Domain\Catalogues::of()` takes, for each addon with an active contribution on the page, the catalogue of the view's locale alone (`PanelView::$locale`, which `ContributionProps::view()` reads from the application's locale), and `ContributionProps::props()` writes them as `texts` of `cms.contributions` (`AddonTextsProp`, `TextProp`, `#/$defs/texts` and `#/$defs/text`); the core's own namespace `cms` is not listed, because the panel's own catalogue is part of its build. In the browser `PanelRuntime` builds the lookup with `catalogues()` of `host/model.ts` and serves it as `HostServices.text`, so `addonTexts()` gives the text of a key of the addon's own namespace and the key itself for any other or for one the catalogue has not. A credential page carries no catalogue, because no addon code runs there: `Login\Actions\ResolveLoginNotices::resolve(PanelLocale)` reads each notice's text from the addon's compiled catalogue itself, so `LoginNoticeProp::$message` is the text in the page's locale (the key itself when the addon ships none) and the host renders it as it is; `Boundary\PanelPages::locale()` gives the controller the application's locale. The tests: `packages/contracts/tests/PanelPoints/PanelLocaleTest.php`, the catalogue cases of `packages/core/tests/Actions/BuildRegistryPanelTest.php`, the locale cases of `packages/panel/tests/Contributions/ContributionPropsTest.php` and `packages/panel/tests/Actions/ResolveLoginNoticesTest.php`, `js/panel/tests/host/texts.test.tsx` and the browser tests, which read the fixture addon's texts through `PanelPage::addonText()`.

## The props of the pages

The props of the panel's pages (GUARDRAILS 2.2, 2.4) are generated from PHP, never written by hand on either side. Each page has a JSON Schema in `packages/panel/resources/schemas/pages` (`login.v1.json`, `forgot-password.v1.json`, `reset-password.v1.json`, `home.v1.json`, `not-found.v1.json`) bound to a final readonly DTO in `Panel\Domain\Dto` (`LoginPage`, `ForgotPasswordPage`, `ResetPasswordPage`, `HomePage`, `NotFoundPage`, and the `*Refusals` of the three forms) by the repository tooling's `Cbox\Cms\Tooling\Protocol\Domain\PanelPageSchemas`, because the generators may not use the panel. `composer generate:protocol` writes their codecs into `packages/panel/src/Boundary/Generated` and their TypeScript types and validators into `js/panel/src/generated/pages`, next to a copy of the validators' runtime module `validation.ts`; gate 6 holds both directories. `Boundary\PanelPages` renders every page with `InertiaProps::document()` of what its codec writes, and each page in `js/panel/src/pages` takes the generated interface as its props. The login page's reason is `Domain\SignInReason`, and a refusal of a form just posted is the prop `refusals`, by field (`form` for the form as a whole), each an enum of the panel's Domain whose values are the catalog codes of that form (`LoginRefusal`, `ForgotPasswordRefusal`, `ResetFormRefusal`, `ResetPasswordRefusal`; `code()` gives the `ErrorCode`), which `PanelPages` reads back from the errors `LoginForm` and `PasswordResetForms` flash; each page maps every value of its generated union to a text, so a new code fails tsc. `tests/Codecs/PanelPageValidatorsTest.php` runs the generated validators in Node against the props every page renders in each of its states, and `docs/developers/panel.md` documents it.

## The panel SDK

The panel SDK (PRD 13.4, decision D1 of the panel extension architecture; `docs/addons/panel/sdk.md`) is the npm workspace `js/panel-sdk`, `@cboxdk/cms-panel`, private until its release is decided, beside the panel's own app `js/panel`, `@cboxdk/cms-panel-app`, never published. Its subpaths, in package.json's `exports` and pointing at sources: `/ui` (the kit's `@stable` exports), `/extend` (the stable panel API: `definePanelAddon<C>()` with exactly the keys of C, `usePanelHost<I>()` whose `runCommand()` takes only the commands of I, `PanelHostMissing` outside a host, the kinds `SlotComponent`, `PageComponent`, `Decorator`, `Replacement`, `FormCheck`, `FlowStep`, `Observer` and `Provider`, `Lazy`, `NoContributions`, `NoCommands`, the JSON types, `PANEL_API_VERSION` and the generated `ReceiptV1`, `ProblemV1` and stable points' props), `/experimental` (the kit's `@experimental` exports, the experimental points' props, `ActionHandler` and `AsyncFormCheck`), `/tokens.css`, `/vite` (`cmsPanelAddon()`: the shared modules of `js/panel/shared-modules.json` and the SDK external, Inertia, React Aria, `@cboxdk/cms-ui-kit` and URL imports refused), `/testing` (`PanelHostProvider`), `/eslint` (`cmsPanelAddonEslint()` on `@cboxdk/cms-tooling/eslint`), `/stylelint` (stylelint's own rules only; stylelint is not installed here, because its dependencies fail `npm audit`) and `/storybook` (a preset with `storybook/preview.tsx`). `/experimental` exports only `@experimental` API and every other subpath only `@stable` API: `npm run generate:sdk` (`js/panel-sdk/scripts/generate-entries.js`) writes `js/panel-sdk/src/kit/stable.ts` and `experimental.ts` from the kit's tags, `composer generate:protocol` writes `js/panel-sdk/src/generated/stable.ts` and `experimental.ts` (`PanelPointSchemas::STABLE` and `EXPERIMENTAL`, each type once) and `protocol/ReceiptV1.ts` and `ProblemV1.ts` (`PanelPointSchemas::PROTOCOL_CODECS`), and the API report `js/panel-sdk/api/cms-panel.api.md` (`js/panel-sdk/scripts/api-report.js`, API Extractor per subpath, the kit and the tooling external, `npm run api:report` and `api:check` with the kit's) holds every export to its subpath's tag and to the committed report; `js/panel-sdk/tests` (Vitest, gate 5) fails on an unrecorded change, compiles probes with the repository's compiler options (`tests/sdk.js`, below `.cache/panel-sdk-probes`) to name tsc's error for a missing key, an extra key, wrong props and an experimental type imported from `/extend`, and holds `CONTRIBUTION_ID` and `PANEL_API_VERSION` to the PHP side. `cms:panel:types <namespace>` (the generators module's `Cli\Console\PanelTypesCommand`, the action `Cbox\Cms\Generators\PanelTypes\Actions\WritePanelTypes` with `Domain\Dto\PanelTypesRequest`) writes `resources/panel/generated/contributions.ts` below the addon's Composer package (`Boundary\PackageRoot`): the port `Domain\AddonUiSource`, bound to `Adapter\RegistryAddonUiSource`, reads the addon's fills that run code from the compiled registry with each point's props class and stability and the `issues` of `addons.php`, and the JSON Schemas of the data queries' results and the commands from `QueryCodecs` and `CommandCodecs`, read by `Boundary\JsonSchemaShapes` (structure only; `patternProperties`, `prefixItems` and other structural keywords refused with `generate_schema_invalid`); `Domain\ContributionsModule` and `Domain\ShapeDeclarations` print `Contributions`, `Issues` and the documents' types laid out as Prettier prints them (`Domain\TypeScriptLayout`), a stable point's props imported from `/extend` and an experimental one's from `/experimental`; a point whose host adds to its props in the browser names the SDK's type of what a component receives on its props class with the `#[Internal]` attribute `Cbox\Cms\Contracts\PanelPoints\HostProps` (`command.form.field@1` names `FieldInputProps`, its `FieldInputPropsV1` with `onChange`), which `RegistryAddonUiSource` reads by reflection into `PointType::$name`, so a replacement there is typed `Replacement<FieldInputProps>`, the SDK's `FieldInput` (`packages/generators/tests/Actions/WritePanelTypesTest.php` over the fixture point `NoteFieldV1`). Codes: `generate_panel_addon_unknown` (64), `generate_registry_unreadable` (78), `generate_schema_missing`, `generate_name_collision`, `generate_output_unwritable`. The golden module of the fixture addon reviews is `packages/generators/tests/PanelTypes/Fixtures/contributions.ts.golden` (not `.ts`, so the repository's tsc and ESLint, which cannot resolve the fixture points' props, leave it to the test), compiled against the SDK and checked with Prettier by `js/panel-sdk/tests/panel-types.test.ts`; the workbench's fixture addon's is committed in `workbench/addons/fixtureaddon/resources/panel/generated/contributions.ts`, which tsconfig.json includes and `packages/generators/tests/Cli/PanelTypesCommandTest.php` holds to what the command writes.

## The host runtime

The panel's host runtime (PRD 13.4, sections 3 and 5 of the panel extension architecture; `docs/developers/panel.md#the-host-runtime`) is `js/panel/src/host`: `app.tsx` renders every page inside `PanelRuntime`, which reads the page's `cms.contributions` with its generated validator and gives the points the `HostRuntimeProvider` (`runtime.tsx`: the contributions, the deferred data `ext.<addon>`, the `AddonSource` and the services). A page renders a point with `<PointHost point="<name>@<version>">` (a slot with `{point}`, tabs with `tabs` and `label`, an action point with `onAction` and `label`, a decorator with `render`, a replacement with `target`, `props` and `fallback`) and asks one with `usePointHost('<name>@<version>')` (`columns`, `checks(command, document)`, `flow(command, position, draft)` with `FlowHost`, `observe(event)`); `tests/Support/Panel/RenderedPanelPoints.php` reads both literal forms. Contributions render in order by priority, namespace and id (`model.ts`'s `renderOrder`), each in a `ContributionBoundary` and a `ContributionScope` (a `display: contents` element naming addon, point and contribution, with the contribution's own `PanelHost` from `createPanelHost()` in `panel-host.ts`, provided through the SDK's `PanelHostProvider`); decorators never receive the default and tighten most restrictively (`decorators.ts`), replacements fall back to the default and get their data query's result as `data` beside the page's props when they read data (`PointHost.tsx`), checks run on frozen documents within 16 ms, asynchronous ones 300 ms, are skipped for the session after a throw or overrun, and are capped at their declared severity and held to their namespace (`checks.ts`), flows refuse patches outside a step's declared paths, place a value only at a path of names and list indexes, read with the path parser `forms/field-path.ts`, and end only through the core's confirmation (`flow.ts`), observers run on frozen events (`observers.ts`). A slot or a decorator takes the page's `props` for a point whose props the page holds, and a fill of such a point renders nothing until the page gives them; `usePointHost()` names in `loaded` the contributions whose code is registered, so a page runs a point's checks again when an addon's code arrives. Before any contribution of an addon renders, `registration.ts` holds its `definePanelAddon()` registration to the SHA-256 of its compiled ids that run code, sorted and joined by line feeds, which `cms.contributions` carries per addon (`Cbox\Cms\Panel\Contributions\Domain\Registrations`); a mismatch renders none of the addon's contributions and reports `panel_addon_mismatch`. An addon's entry is imported by `cms-addons/<namespace>` through the import map (`PanelRuntime.tsx`); the core's own contributions, in the namespace `cms`, are registered in `core.ts` and declared on the server by the panel's provider through the `#[Internal]` contract `Cbox\Cms\Contracts\Build\DeclaresCoreContributions` (`Contributions\Domain\CoreContributions`), which `ProviderAddonManifests` reads into `DeclaredAddons::$core` (a provider outside `Cbox\Cms` or an anonymous one is `registry_invalid_manifest`) and `PanelCompiler` compiles with the addons' without the rules that limit an addon to what it owns; they get the viewer's access in `ResolveContributions`. The core's contributions that run code are the pickers of the generic command form (`core/pickers.tsx` over `core/lists.ts`, below): `cms.node-picker`, `cms.actor-picker` and `cms.role-picker`, each a `ReplacementContribution` with a `data` query, the kernel's `node.list`, `actor.list` or `role.list`, so a test world that compiles the core's contributions scans those queries and gives their schemas (`ContributionWorld::CORE_QUERIES`, `tests/Support/Registry/InstallationRegistry`). Reports (`reports.ts`: `panel_addon_mismatch`, `panel_contribution_failed`, `panel_check_over_budget`, `panel_step_patch_refused` and the others) carry codes and ids only, are made once per session and dispatched on the window as `cms:panel-report`. `contributions.v1.json` carries each point's kind, region, multiplicity and max, each fill's action, check, step, decorator and replacement descriptor, the addons' registrations and issues, `details`, `pages` and the `commands` address of the Inertia profile (`PanelRoute::COMMANDS_PATH`); `composer generate:protocol` also writes the panel's `js/panel/src/generated/protocol/ReceiptV1.ts` and `ProblemV1.ts` (`PanelPageSchemas::PROTOCOL_CODECS`), which the command transport (`commands.ts`) reads answers with: the receipt and a dry run's summary from the flash, and a rejection's problem from the props of the page Inertia's `success` or `error` event carries, never from `navigate`, which Inertia fires only when the address changes, while the profile's redirect lands back on the page the command was run from. The tests are `js/panel/tests/host` (`npm run test:js -- host`, jsdom through `harness.tsx`), `packages/core/tests/Actions/BuildRegistryCoreContributionsTest.php` and the panel's contribution tests. The Storybook section "Panel points" is generated from `panel.php` by `cms:panel:stories` (the generators module's `Cli\Console\PanelStoriesCommand`, the action `PanelStories\Actions\WritePanelStories`, the port `Domain\PanelPointSource` bound to `Adapter\RegistryPanelPointSource`, `Domain\PanelStoriesModule`) into `js/panel/stories/generated` (`points.ts` and `PanelPoints.stories.tsx`, rendered by `js/panel/stories/PanelPointStory.tsx`, which the kit's Storybook includes; a fill with a data query reads data there as on a page, a page's only on the page itself, so the story's host hands it the state loading, as the core's pickers get it before `ext` arrives); `packages/generators/tests/Cli/PanelStoriesCommandTest.php` holds the committed files to the command, and the golden output of `PanelStoriesWorld` is `js/panel/tests/host/stories-golden/generated`.

## The generic command form

The generic command form (GUARDRAILS 2.2, 8; PRD 6.1, 8.4, 13.4; `docs/addons/panel/command-form.md`, the recipe `docs/recipes/expose-command.md`) is the page of any write action the Inertia profile exposes, at the address the profile runs it at: `GET <prefix>/commands/{command}/v{version}` (`PanelRoute::CommandForm`, `Pages\CommandFormController`, which loads the addons' UI), the page the command palette opens for a command. The Boundary `CommandForm\Boundary\CommandFormRequest` finds the action in `InertiaActions` and its codec in `CommandCodecs`, and gives the props `Domain\Dto\CommandFormPage` (`logout`, `command`, `version`, `schema`; schema `pages/command-form.v1.json`, codec `CommandFormPageCodecV1`, TypeScript `CommandFormPageV1`), the command's JSON Schema as a `JsonDocument` as the codec carries it; a command the profile does not expose, another version or one without a codec is the not-found page with 404. The page `command.form` (`CommandForm\Domain\CommandForm`) declares seven points in `CommandForm\Domain\Dto`, each `#[Experimental]` with its schema in `points/` and its codec: the slot `command.form.aside@1` (`CommandFormContextV1`: the command's name, version and the schema's title, in the aside region), the form check point `command.form.checks@1` (`CommandFormChecksV1`, no props), the flow step point `command.form.steps@1` (`CommandFormStepsV1`, no props), the decorator `command.form.submit@1` (`CommandFormSubmitV1`, the context again; tightens `disabled_reason`, `description` and `tone_towards_danger`), the decorator `command.form.receipt@1` (`CommandFormReceiptV1`: command, version, the receipt and a rejection's problem as `JsonDocument`s; tightens nothing), the replacement `command.form.field@1` (`FieldInputPropsV1`, keyed by `ReplacementKey::ValueClass` with `Ownership::Own`: command, version, the member's path, the control's id (`control` in PHP, a DOM id), label, description, the member's schema node, its value as text, errors, `read_only`, the `Locale` and its `FieldPresence`) and the slot `command.form.dryrun@1` (`DryRunViewV1`: command, version, the dry run's summary and receipt, in the sections region). `CommandFormRequest::view()` renders the aside and the submit decorator with the context, the checks and the steps with their empty props, and the receipt, the field and the dry run as held by the page; its view names the command as its `ViewSubject`, so a contribution whose scope names commands is active on that command's form alone; it is not an `OwnPage`, because its address takes the command, so no nav entry points at it. The page's props also carry `bindings` (`Panel\Domain\Dto\FieldBinding`, `#/$defs/binding` of `pages/command-form.v1.json`), the value class the command binds each member to, which `CommandForm\Boundary\CommandBindings` reads from the command class's promoted constructor parameters whose type is one class, under the member's key in snake_case where the schema has it; the class keys the replacement of the member's input. The form itself is the kit's `SchemaForm` over the model `readCommandSchema()` reads from the schema (`js/ui-kit/src/components/schema-form/model.ts`): the subset of JSON Schema the kernel's command schemas use, objects with `additionalProperties: false`, `properties` and `required`, strings with `pattern`, `minLength`, `maxLength`, `examples` and the `date-time` format, integers with `minimum` and `maximum`, booleans, enums of strings, nullable members as `type` with `null` or an `anyOf` of a `$ref` and `null`, `default`, `$ref` to `#/$defs/<name>`, nested objects, lists with `items`, `minItems` and `maxItems`, and the member that refers to `#/$defs/fields`, the `FieldValues` of a revision, which the form edits as JSON; any other keyword, type or shape throws `SchemaUnsupported` with the keyword and the node's pointer, and the page shows it instead of a form. The form is controlled and names no command: each control is named by its value's path in the document and has the id `<prefix>-<path>`, its texts are the catalogue's `panel.action.<command>.field.<path>.label`, `.description` and `.option.<value>` when present and the schema's title and description otherwise (`js/panel/src/forms/texts.ts`), and the page's title and description are `panel.action.<command>.title` and `.description` or the schema's. Before it submits, `js/panel/src/forms/CommandForm.tsx` validates the document with the generated runtime (`validation.ts`) through the `ObjectRule` `rulesOf()` builds from the model (`js/panel/src/forms/rules.ts`, the same rules cms:generate emits for the schema: a patterned string is the string rule, a date-time the datetime rule, any other string the text rule, and so on; `presence` from required and nullable), shows the first issue at its field and in the kit's `ErrorSummary`, and sends nothing. The form hosts its points (section 8 of the panel extension architecture): `usePointHost('command.form.checks@1').checks()` runs on every edit, each check given the panel's locale and the viewer's actor id from `cms.contributions` as its context, and again when an addon's code arrives (`loaded`), in a `useMemo` whose asynchronous part settles in an effect; an issue of severity error is the field's error beside the validator's (`forms/issues.ts`: `fieldErrors()`, and `atControls()`, which shows an error below a member edited as one control, the `fields` JSON, at that control, both over `forms/field-path.ts`, the panel's twin of the kernel's `FieldPath`, which reads a key segment such as `fields.body[#k3f9]` as the item of a list that carries that key; see [the JSON contracts](json-contracts.md)), the others are listed with their field (`labelAt()`) and a link, an acknowledge issue with the tick `maySubmit()` needs, and a held run sends nothing; a dry run is explicit, its own button, never held and runs no step. The run starts the flow `usePointHost('command.form.steps@1').flow(command, 'before_submit', draft)` and renders it with `FlowHost` (the step's turn, the core's confirmation with the `panel.host.confirm*` texts, the cancelled notice), a form without steps taking the press as the confirmation (`FlowRun::confirm()` at once), sets the document to the confirmed draft (the kit's `JsonMember` follows a value set from outside) and runs the command through the host's `runCommand` with the form instance's idempotency key (`CommandCall::$key`, which `inertiaCommands` sends instead of a new one) and the wait level chosen; once answered, the steps after the receipt run with the answer. The submit decorator wraps the actions (`<PointHost point="command.form.submit@1" render>`: a disabled run with its reasons, the descriptions, the tone), the receipt decorator wraps `ReceiptStatus` with the page's props, the dry run slot follows `DryRunReport` with the page's props, and the kit's `SchemaForm` hands each field to `renderInput` (`SchemaFormField`: the member, its path, value, `onChange`, what it is when emptied, and the default input's id, name, label, description, error, required and disabled), where a member with a binding becomes `<PointHost point="command.form.field@1" target={class} props={fieldInputProps(field)} fallback={input}>` (`forms/field-input.ts`: the props of `FieldInputPropsV1` with the member's schema node rebuilt from the model, `schemaNodeOf()`, and `onChange` reading the text back into the member's kind). It shows the receipt (`ReceiptStatus`), what a dry run would change (`DryRunReport`) and, for a rejection, the problem details and each error at its field from the page's `errors` prop (`serverErrors()`: `command.<path>` by its path, the envelope's and the document's own at the form), which replace the checks' issues at the same paths (`withoutServerPaths()`). A committed outcome ends the instance, so the next run gets a new key; a dry run, a rejection and a lost answer keep it, so the same form submitted twice gives one changeset: the second claim replays the first receipt. ## Themes and branding

The panel's themes and the installation's branding (PRD 13.4, Sylvester, 2 October 2026; `docs/developers/panel-branding.md`). A theme is a JSON file of token values of the form of `js/ui-kit/src/generated/theme.v1.json` (`tokens` and `parts`, a value per token of a semantic or component token of `js/ui-kit/tokens.json` in one string for both modes or exactly `light` and `dark`, a part a curated `data-cms-part`), read by the core's `Cbox\Cms\Core\PanelThemes\Boundary\ThemeDocument` from the same catalogue (`TokenCatalogueJson`), and held to the schema's verdicts by `tests/Codecs/ThemeSchemaParityTest.php`. `cbox-cms.panel.themes` selects and orders them (`ThemeName`: `app`, the file in `cbox-cms.panel.app_theme`, or `<namespace>:<name>` of an allowed addon's `PanelContributions::$themes`, which needs `AddonCapabilities::$uiTheme`), read into `BuildSettings::$themes` (`ThemeSelection`) by `BuildSettingsConfig`; a theme it does not name is never read. `BuildRegistry` runs the action `PanelThemes\Actions\CompilePanelThemes` over the port `Domain\ThemeSources` (bound to `Adapter\FileThemeSources`): `ThemeComposer` composes later over earlier, `ThemeChecks` holds every contrast pair of the catalogue to WCAG 2.2 AA in both modes on the whole panel and each named part after composition (`registry_panel_theme_contrast`; `Contrast` measures hex and oklch as `js/ui-kit/scripts/tokens.js` does) and `--cms-target-size` to 24 px, everything else it cannot use is `registry_panel_theme_invalid`, a token set twice is the warning `registry_panel_theme_overlap`, and `ThemeStylesheet` renders the cascade layer `cms.theme`; the build lists the theme's problems with the registry's and writes nothing on any, else writes `theme.css` next to the registry through the port `Domain\ThemeStylesheets` (`Adapter\FileThemeStylesheets`, which removes it when nothing is selected; `FileRegistryCache` keeps it). `cms:panel:theme:check <theme>` (the cli's `Console\PanelThemeCheckCommand`, action `CheckPanelTheme`) checks one file alone. The panel serves the stylesheet at `GET <prefix>/theme/{version}.css` (`PanelRoute::Theme`, `Assets\ThemeController`, `Boundary\PanelThemeResponse`, `Domain\Dto\PanelTheme` read once per process) and links it with the nonce. Branding is the panel module's feature `Cbox\Cms\Panel\Branding`: `Boundary\BrandingConfig` reads `cbox-cms.panel.branding` (`root`, `name` up to 60 characters, `logo` and `login` as light, dark and alt, `favicon`; files SVG or PNG by their bytes, at most 512 KiB, inside the root, no script in an SVG) into `Domain\Dto\Branding` or `InvalidBranding`, bound once per process, an invalid one as none, so the panel shows Cbox CMS; `cms:doctor`'s non-blocking `panel.branding` (`Panel\Doctor\Domain\Checks\BrandingCheck`, probe `Boundary\ConfigBrandingProbe`) fails with `doctor_panel_branding_invalid`. `GET <prefix>/brand/{name}` (`PanelRoute::Brand`, `Assets\BrandController`, `Boundary\BrandFileResponse`) serves the files by role and hash with `default-src 'none'; sandbox`. Every page shares the prop `brand` (`brand.v1.json`, `PanelBrand`, written by `Boundary\PanelBrandProps`), the root view writes the name into the first title and an `application-name` meta element and the favicon link, and the kit's `Brand` and `ShellHeader` show it. No theme or addon reaches the branding. `tests/Browser/Panel/BrandingTest.php` and `PanelThemeTest.php` cover both in Chromium; with `CMS_DOCS_SCREENSHOTS=1` the first captures `docs/screenshots/branding-*.png`, the `BrowserScreenshot`s of `Screenshots::browser()`.
