# Operations, rebuilds and seeding

Anything longer than a request is an operation of idempotent chunks that resumes where it stopped.

## Operations

Work that takes more than a few seconds is an operation in `cboxdk/laravel-operations` (GUARDRAILS 3, 4.2), pinned in `composer.json` and used directly: `CoreServiceProvider` registers its `OperationsServiceProvider`, so its `Operations` contract and the migration of its `operations` table come with the core. The work is a `Cbox\Cms\Core\Operations\Domain\ChunkedAction` (`kind()`, `chunks()`, a `ChunkPlan` of `ChunkName`s asked once when the operation starts, and `runChunk()`), and `OperationRunner`, bound to `Operations\Adapter\PackageOperationRunner`, runs it: `run(OperationRequest)` (the action and an `OperationKey`) starts an operation with a step per chunk when the kind and key have none or only a failed one, resumes a running one at its first chunk that has not completed with the plan it started with, and returns a completed one without running a chunk; `find()` gives the latest `OperationProgress`. A chunk that throws leaves the operation running and the exception goes to the caller. A chunk is idempotent, because a chunk that committed runs again when the process dies before it is recorded, and runs outside any transaction of the runner's; `run()` inside an open transaction throws `OperationInsideTransaction`. Finding or starting holds `pg_advisory_xact_lock(hashtextextended('cbox-cms.operation:<kind>|<key>', 0))`, and recording a chunk or the completion holds the operation's row lock. No operation runs in an HTTP request. The fake is `packages/core/tests/Operations/Fakes/FakeOperationRunner`, held to the runner by `OperationRunnerBehaviour`, and the test-only chunked action is `RecordingChunkedAction`. What the package lacks (the kernel's Clock and ids, timestamptz, partitions) is recorded in `PROGRESS.md`, not worked around.

## Rebuilding a type table

A type table is derived (PRD 4.1, 11.6, invariant 22), and `cms:types:rebuild <type> [--run=<name>]` (the cli's `Console\RebuildTypeTableCommand`, arguments read by `Cli\Boundary\RebuildArguments`) rebuilds it through the action `Cbox\Cms\Core\ReadModels\Actions\RebuildReadModels::rebuild(RebuildRequest)`, an operation of kind `type_tables.rebuild` (`RebuildChunks`, a `ChunkedAction`) keyed `<type>@<run>`; `--run` defaults to the Clock's time as `Ymd\THis\Z`, and a second run with the same name resumes where the first stopped. It runs as the service actor of `cbox-cms.rebuild.service_actor` (`RebuildConfig` into `RebuildSettings`, with `chunk_size` 1 to 1000, default 100), never as the system: the type must be in the TypeCatalog (`rebuild_type_unknown`), the actor must exist and be of class service (`rebuild_identity_invalid`) and active (`actor_not_active`), and its context comes from `AccessContexts`, so row level security bounds what it rebuilds. Unless the operation is running or completed, it asks the port `ReadModels\Domain\ReadModelStore` for a plan: the type's entry ids in id order, from the index `entries_type_id` on (type_id, id), as `EntryRange`s of at most the chunk size, each a chunk named `entries:<first>:<last>`. The store on Postgres, `ReadModels\Adapter\PostgresReadModelStore`, runs every read of the plan and every chunk in a transaction of its own on the default connection as the app role: READ COMMITTED, `transaction_timeout` turned off and on at `TRANSACTION_MILLISECONDS` (2000), and the context through `ActorContext`. A chunk reads its variant heads with `FOR SHARE` (`HEADS`) and the payloads a head is rebuilt from: its draft revision and, while released, its published revision for history full, its head snapshot otherwise. Each payload must be at the type's current schema version, or the chunk throws `RebuildRefused` with `rebuild_schema_version_unsupported` and rolls back (upcasters are B3), and at `StoredContent::FORMAT_VERSION`. It then deletes the rows of the entries it read by id and writes each variant through the entry commands' `TypeRows`: `release()` with the published content for stages draft-release, then `write()` with the draft. Each chunk's `ChunkResult` (entries, variants, milliseconds) goes to the run's `RebuildTally` and the `RebuildReport`. The fake is `packages/core/tests/ReadModels/Fakes/FakeReadModelStore`, held to the Postgres store by `ReadModelStoreBehaviour`; `RebuildWorld` gives a Postgres test a granted service actor, the type table's rows as the superuser and a truncate as the owner, and `tests/Postgres/WalkingSkeleton/RebuildReadModelsTest.php` rebuilds both workbench types to the same rows.

## Seeding

Seeding (GUARDRAILS 4.3, PRD 23) is `cms:seed-scale --entries=N [--profile=small] [--seed=1]` (the cli's `Console\SeedScaleCommand`, options read by `Boundary\SeedScaleOptions`), which calls the action `Cbox\Cms\Core\Seeding\Actions\SeedDataset` (`run(SeedRequest): SeedReport`) as the service actor `cbox-cms.seeding.service_actor` names (`Boundary\SeedingConfig`; the workbench sets it from `CBOX_CMS_SEEDING_SERVICE_ACTOR`): it must exist, be of class service and be active, or `Domain\SeedRefused` carries the exit (78 config, 77 not active or no node, 70 a rejected chunk; 64 invalid options). Its access context comes from `AccessContexts`; the types are those of the catalog whose required fields it may write (`Domain\SeedTypes`: not above its classification access, not encrypted), the nodes those its regions reach but mounts (the port `Domain\SeedTargets`, bound to `Adapter\TransactionalSeedTargets`, a transaction of its own under the context). The run is an operation (`Actions\SeedChunks`, kind `cms.seed`, key `<profile>@<version>:<seed>:<entries>`, chunks `chunk-<n>`) through `OperationRunner`; each chunk is one call of the command `Domain\Commands\SeedEntries` (`seed.entries` version 1, `#[Experimental]`, surfaces none; its `Domain\Dto\SeededEntry`s: id, type, home, fields, release) through the pipeline with `Envelope::internal(IssuingSurface::Seed, IssuerKind::Seed, ...)` and the unit of work `seed:<profile>@<version>:<seed>:<chunk>:<size>`, so the events go to the bulk stream and a chunk that runs again replays; a chunk whose entries all exist, read through `SeedTargets::existing()` under the run's context, is done without a command, because seed.entries would plan nothing once the idempotency record has expired. `CoreServiceProvider` gives `SeedDataset` a pipeline of its own (contextual binding): the kernel's, with `Domain\SeedAuthorizer` (seed.entries only, no field above the context's classification access or encrypted) and `Boundary\SeedContentHasher` (the chunk's canonical JSON). `Actions\SeedEntriesAction` reads the chunk in two statements through the port `Domain\SeedReader` (bound to `Adapter\PostgresSeedReader`), leaves out entries that exist, and plans four sub-plans, one per step (`EntryCreated`, `RevisionCreated`, `HeadMoved`, `VariantReleased` for released entries), so the commit writes each step of the chunk at once; the pipeline validates a release of a revision its own plan creates as the plan holds it. The versioned profiles are `Domain\SeedProfiles` (`small` 100 and `scale` 200 entries a chunk; `Domain\SeedProfile`): the skew is in the type mix (`Domain\ZipfDistribution` over the types by name), the entries per node (over the nodes by id) and the field values (`Domain\FieldValueGenerator`, from the rules of each type's generated validator, no type or field named: dates crowd towards the anchor, numbers towards their low bound, choices towards the first options, optional fields 80 % filled), never in commit times. `Domain\EntryGenerator` makes entry n from the profile, the seed and n alone (a seeded Xoshiro256** per entry; the id a UUIDv7 at the anchor plus n ms), so the same seed gives the same ids in every run. Fakes: `packages/core/tests/Seeding/Fakes` with `SeedReaderBehaviour` and `SeedTargetsBehaviour`; tests: `packages/core/tests/Actions/SeedEntriesTest.php` and `SeedDatasetTest.php` (`SeedActionWorld`), `packages/core/tests/Postgres/SeedScaleTest.php` (`SeedWorld`: 2,000 entries twice, equal rows and ids; every entry stored as entry.create and variant.release store it; the same statements for a chunk of 20 and of 200). `composer scale:check -- [--entries=1000000] [--runs=11] [--profile=scale] [--seed=1] [--sections=40] [--database=cms_scale] [--keep]` (`tools/bin/scale-check.php`, tooling module `Cbox\Cms\Tooling\Scale`) prints the machine, recreates the dedicated scale database (never the dev database or a test database), migrates it, writes a site with its sections and the service actor with the testkit's fixture writers (`Adapter\ScaleApplication`), runs cms:seed-scale with cms:partitions:maintain every minute, prints the seed's wall time, runs ANALYZE and the workbench listing (the generated builder's newest-first keyset page of 20 of the article type, first page and next) with EXPLAIN (ANALYZE), prints each median and exits 1 above 20 ms; `tests/Postgres/ScaleCheckTest.php` runs it with 300 entries. `docs/developers/seeding.md` documents both.
