# Receipts, idempotency and the commit position

A committed changeset leaves a receipt and completes an idempotency key in the same transaction, both at the transaction's commit position.

## The ReceiptStore contract

The `ReceiptStore` contract (`Cbox\Cms\Contracts\ReceiptStore`) has `store(StoredReceipt)`, `find(ChangesetId): ?StoredReceipt` and `markProjection(ChangesetId, ProjectionStatus): bool`; the status names the projection. A `StoredReceipt` holds only facts about a committed changeset: the `ChangesetId`, the `RetentionClass`, the commit position (`Consistency\CommitPosition`, see below) and the projection statuses. `store()` refuses a receipt whose position is not the commit position of the caller's transaction with `Contracts\Consistency\ForeignPosition` (a `LogicException`) and stores nothing. It has no outcome and no wait level, because the kernel stores it in the command transaction (PRD 6.2 phase 7), before any wait level past commit is reached; the kernel builds each call's `Receipt`, a replay's too (PRD 6.1), from it, the wait level the call asks for and whether that level was reached. `store()` and `markProjection()` run on the caller's connection and never begin, end or savepoint a transaction. `store()` runs only inside the caller's open transaction and throws `TransactionRequired` (in `Contracts\Consistency`, a `LogicException`) and stores nothing without one, so a store holds no lock or other state past its transaction, which a pooler in transaction mode (PRD 5.10) could leave behind on a server connection; `markProjection()` runs inside the caller's transaction when one is open and otherwise commits on its own. A second receipt for a changeset throws `DuplicateReceipt` (in `Contracts\Consistency`). A changeset time that no partition covers throws `Contracts\Storage\PartitionMissing` (`CODE` `partition_missing`) and stores nothing; the caller rolls back, because Postgres has failed the transaction. `markProjection()` is idempotent, an acknowledgement is final, and it returns false and changes nothing when no live receipt lists the projection. Expiry is logical: `find()` returns null once the Clock is later than `RetentionClass::expiresAt()`, the changeset id's time plus 7 days for Standard; Evidence has none. A `store()` of a changeset that another open transaction stored waits for that transaction and then throws `DuplicateReceipt` or stores; the duplicate comes from `store()`, never from commit. A store on a database may need the caller's transaction at READ COMMITTED, so that it sees a receipt committed while it waited, and throws `Contracts\Consistency\UnsupportedIsolation` at another level. The testkit's `FakeReceiptStore` is the store and the harness; used directly it has no transaction, so its `store()` throws `TransactionRequired`, and `session()` gives connections with `begin`, `commit`, `rollBack` and `position()` (a transaction's position, given when it first asks, counting up from `FakeReceiptStore::FIRST_POSITION`), and `whenWaiting()` schedules what happens while a store waits (a store with nothing scheduled throws a LogicException). The shared suite `ReceiptStoreContract` takes a `ReceiptStoreHarness` that hands out `ReceiptStoreSession`s (`position()` gives the commit position of the session's open transaction) and whose `uncover($from, $to)` takes a range of partition keys out of the partitions: on the fakes exactly that range, on Postgres the test helper `PartitionGaps` drops every managed partition that overlaps it. After a PartitionMissing inside a transaction, a fake session refuses every call and `commit()` with a LogicException until `rollBack()`. Testkit code for the store lives in the feature `ReceiptStore`, not `Receipts`, because of the category rule.

## The IdempotencyStore contract

The `IdempotencyStore` contract (`Cbox\Cms\Contracts\IdempotencyStore`) has `claim(IdempotencyScope, IdempotencyKey, ContentHash, WaitBudget): ClaimResult` and `complete(ClaimToken, ChangesetId)`, and no `release()`. Both run only inside the caller's open command transaction and throw `InvalidClaim` without one. `claim()` takes a claim on (scope, key) that lasts until that transaction ends, waiting at most the `WaitBudget` (0 to 5000 ms, real time, not the Clock; a store ends the wait sooner when the database's time limit on the transaction would end it first) while another transaction holds it, and then looks up the completed record. The result is one of four final readonly classes in `Contracts\Idempotency`: `Fresh` (a `ClaimToken`), `Replay` (the stored `ChangesetId`; the caller resolves the receipt through the `ReceiptStore`), `Conflict` (`Conflict::CODE` is `idempotency_conflict`) or `InFlight` (the budget ran out; holds nothing). Every result but `InFlight` holds the claim. `complete()` writes the record in the same transaction, so a rollback, or a commit without `complete()`, leaves the key fresh. A record expires with the Standard receipt of its changeset, `RetentionClass::Standard->expiresAt()`. The testkit's `FakeIdempotencyStore` is the harness; its `session()` is the fake store, and `whenWaiting()` schedules what happens while a contested claim waits. `complete()` throws `PartitionMissing` and records nothing when no partition covers the record's date, the later of the Clock's time and the changeset's time; the caller rolls back, which leaves the key fresh. The shared suite `IdempotencyStoreContract` takes an `IdempotencyStoreHarness` of `IdempotencyStoreSession`s, with the same `uncover()` as the receipt store's harness. Both session interfaces extend `Cbox\Cms\Testkit\Sessions\TransactionalSession`, so one session for a real database can serve both stores.

## The receipt and idempotency types

The receipt and idempotency types live in the contracts module, because the store contracts take them and the contracts module depends only on PHP: `Receipt` (the result of one call), `StoredReceipt` and `ProjectionStatus` in `Cbox\Cms\Contracts\Receipts` (final readonly DTOs), the enums `Outcome`, `WaitLevel`, `RetentionClass` and `ProjectionState` with `ProjectionName` and `InvalidReceipt` in `Cbox\Cms\Contracts\Consistency`, `ChangesetId`, `PrincipalId` and `CommandName` in `Cbox\Cms\Contracts\Ids`, and `IdempotencyKey`, `IdempotencyScope`, `ContentHash` and `PrincipalKind` in `Cbox\Cms\Contracts\Idempotency`. A committed outcome requires a `ChangesetId`; the others forbid one. An `IdempotencyScope` is a `PrincipalKind`, a `PrincipalId` (the actor's or source's id, 1 to 255 visible ASCII characters, compared exactly; `InvalidPrincipalId` otherwise) and a `CommandName` (the name from `#[Command]` without the version, in the form of `Command::NAME_PATTERN`; `InvalidCommandName` otherwise), and takes no string. A receipt's JSON form is `receipt.v1.json`, written and read only by the generated `ReceiptCodecV1` (GUARDRAILS 2.2). A `Receipts` segment anywhere in a namespace makes it the Receipts category, so a core feature for the stores cannot be called `Receipts`.

## The commit position

The commit position (PRD 7.4, 8.4, 8.12) is `Cbox\Cms\Contracts\Consistency\CommitPosition`: a Postgres xid8 kept as a decimal string without leading zeros (up to `CommitPosition::MAX`, 2^64 - 1), compared by numeric value with `isBelow()`. A changeset's position is the xid8 of its command transaction, `pg_current_xact_id()`: the changeset row's `xid`, each event's `xid` and the receipt's `position` carry the same value. A read's position is the xmin of its snapshot, `pg_snapshot_xmin(pg_current_snapshot())`, and a read at position R saw every changeset whose position is below R (`$changeset->seenBy($read)`), the event horizon of PRD 7.4. `Cbox\Cms\Core\Consistency\Infrastructure\TransactionPosition::current()` (`#[Experimental]`) reads the position of the caller's open transaction on the default or a named connection and throws `TransactionRequired::forPosition()` without one, before any statement. The pipeline's port `Pipeline\Domain\AffectedProjections` (`#[Internal]`, bound to `Pipeline\Domain\RegistryAffectedProjections`, which asks `CompiledRegistry::projectionsFor()`) gives `pendingFor(list<Event>)`, the pending status of each projection whose subscriber receives one of the events and acknowledges on the receipt, each once and sorted; the commit stores the receipt with exactly those. Its fake is `packages/core/tests/Pipeline/Fakes/FakeAffectedProjections.php`, held to the registry by `AffectedProjectionsBehaviour`. `packages/core/tests/Postgres/CommitPositionTest.php` shows the rule on Postgres. The page is `docs/addons/contracts/receipt-store.md`.

## The receipt store on Postgres

The receipt store on Postgres is `Cbox\Cms\Core\ReceiptStore\Adapter\PostgresReceiptStore`, bound to `ReceiptStore` in `cbox-cms.contracts`. It runs on the default connection (or a named one), through the query builder except for that insert, and never begins a transaction. Every read, the lock included, uses the write PDO (`useWritePdo()`), so outside a transaction a lagging read host never hides a stored receipt from `find()` or `markProjection()`. Its tables come from the core migrations `packages/core/database/migrations/*_create_receipts_tables.php` and `*_add_position_to_receipts.php`: `receipts` (one row per changeset with its commit position `position`, an xid8 without a default, and no outcome or wait level) and `receipt_projections` (one row per changeset and projection), both LIST-partitioned on `retention_class` and then RANGE-partitioned on `changeset_id`, managed as `receipts_standard` and `receipt_projections_standard` (per day, `retention_days` 7) and `receipts_evidence` and `receipt_projections_evidence` (per month, never dropped). The primary keys are `(changeset_id, retention_class)` and `(changeset_id, retention_class, projection)`; there is no foreign key between them. `find()` and `markProjection()` filter on the Clock's live window (`PostgresReceiptStore::lowestLiveStandard()`), `markProjection()` updates only a pending row, and `store()` reports a duplicate without aborting the caller's transaction. The database holds the app role to that: it may update only `state` and `acknowledged_at` of `receipt_projections` (column grants from `TablePrivileges::limitColumns()`, on every partition), so an update of any other column fails with SQLSTATE 42501, and the trigger `receipt_projections_acknowledged` refuses every update of an acknowledged projection row with SQLSTATE 23000, for every role, which `markProjection()` never fires. The primary key cannot hold one receipt per changeset across the retention classes, so `store()` first takes the transaction-scoped advisory lock `ReceiptLock::of($changesetId)` (`pg_advisory_xact_lock`, the first 64 bits of a versioned SHA-256 of the changeset id), then looks for a receipt of either class, then inserts the receipt row with `ON CONFLICT DO NOTHING` and its projection rows in one statement (`PostgresReceiptStore::INSERT_RECEIPT`, a data-modifying CTE per table), so they are stored or fail together. Without an open transaction (`transactionLevel()` below 1) `store()` throws `TransactionRequired` before its first statement, so it never takes a session-level lock; a concurrent store of the same changeset waits for the first transaction and, under READ COMMITTED, gets `DuplicateReceipt`. `store()` needs READ COMMITTED, because its lookup must see a receipt committed while it waited: the lock statement `PostgresReceiptStore::LOCK_CHANGESET` also reads `transaction_isolation` and `pg_current_xact_id()`, takes the lock only at that level, and a receipt at another position throws `ForeignPosition` before the lookup, and at REPEATABLE READ or SERIALIZABLE `store()` throws `Cbox\Cms\Contracts\Consistency\UnsupportedIsolation` and holds no lock. The Postgres contract test is `packages/core/tests/Postgres/PostgresReceiptStoreContractTest.php`; it and the adapter tests cover the dates they write at with `PartitionFixtures`.

## The idempotency store on Postgres

The idempotency store on Postgres is `Cbox\Cms\Core\IdempotencyStore\Adapter\PostgresIdempotencyStore`, bound to `IdempotencyStore` in `cbox-cms.contracts`. It runs on the default connection (or a named one), inside the caller's transaction, and never begins one. Its table comes from the core migration `packages/core/database/migrations/*_create_idempotency_keys_table.php`: `idempotency_keys`, RANGE-partitioned per day on `created_at` and managed with `retention_days` 7, with an index on `lock_key`, no primary or unique key, and SELECT and INSERT for the app role. Postgres cannot keep a key unique across daily partitions, so a claim is a transaction-scoped advisory lock on `ClaimLock::of($scope, $key)`, the first 64 bits of a versioned SHA-256 of the scope and key: `pg_try_advisory_xact_lock` polled with a growing sleep (2 ms up to 50 ms) until it is granted or the `WaitBudget` has passed, never a blocking lock or `lock_timeout`, which would abort the caller's transaction. The wait also ends `PostgresIdempotencyStore::TRANSACTION_MARGIN_MILLISECONDS` (250) before the transaction's `transaction_timeout`, read in the first try from `pg_settings`, `transaction_timestamp()` and `clock_timestamp()`, because that timeout counts from the start of the transaction and terminates the session; the effective budget is the lower of the two, and 0 (off) leaves the budget alone. The lookup is a separate statement after the lock, so under READ COMMITTED it sees a commit made while the claim waited; a claim at another isolation level throws `InvalidClaim::isolationLevel()` and takes no lock. The lookup matches the full scope and key, so a lock key collision only makes two keys wait for each other. A Fresh claim is noted in the transaction-local setting `cbox_cms.idempotency_claims`, which `complete()` checks and Postgres resets when the transaction ends. `created_at` is the Clock's time, or the changeset's time when that is later, and `expires_at` is `RetentionClass::Standard->expiresAt()`; the CHECK `idempotency_keys_window` keeps `expires_at` within 168 hours of `created_at`, so every live record has `created_at` at or after `PostgresIdempotencyStore::lowestLiveCreatedAt()`, 7 days before the Clock's time, and the lookup prunes the older partitions. The lookup has no upper bound on `created_at`: a changeset's time, and so a record's `created_at`, can be on a later day than the claimer's Clock (a clock that stepped back, another node's clock ahead), so it reads every partition from then onward, the runway included. The Postgres contract test is `packages/core/tests/Postgres/PostgresIdempotencyStoreContractTest.php`.
