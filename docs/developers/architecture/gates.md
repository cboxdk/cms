# The gates, the dev image and the test databases

The short rules are in `CLAUDE.md` under "Hard rules". This page holds the full description of each.

## The dev image

The gates run in the php-baseimages dev image `ghcr.io/cboxdk/php-baseimages/php-cli:8.5-bookworm-dev-v1` (PHP 8.5, PCOV, Xdebug, Node 22, Playwright's Chromium in `/ms-playwright`), locally as in CI (Sylvester, 30 September). `composer check` started on the host checks its options and runs itself again in a container of the image (module `Cbox\Cms\Tooling\DevImage`, `DevImageRun`), for the current checkout, a linked worktree included: the checkout is mounted at its own absolute path and is the working directory, so the testkit derives the checkout's own test database and the reports name host paths; a linked worktree also gets the main checkout's `.git` at its path; `node_modules` is a Docker volume of the checkout's own, `laravel-cms-node-modules-<12 hex digits of the SHA-256 of the checkout's path>`, which `tools/bin/dev-image-entry.php` fills with `npm ci` in the image whenever `package-lock.json` changed (the host's `node_modules` holds macOS binaries); the host's `~/.pest` is `/tmp/.pest` with `HOME=/tmp`; it runs as the host user's uid and gid with the host's name, never as root; `.cache` and the Testbench application's bootstrap cache are Docker volumes of the checkout's own too (`VolumeKind`), because on Docker Desktop's bind mount a file another process replaces with a rename is missing for a moment to a reader in the container, and parallel workers then failed to open PHPStan's container or `bootstrap/cache/services.php`; the entry mirrors the host's bootstrap cache, mounted read-only, into its volume at the start of each run; and it joins the network of the main checkout's `compose.yaml` and reaches the services as `postgres` and `valkey`. It never starts or recreates them: when Postgres or Valkey is not running and healthy, it fails with exit 1 and says to run `composer services:up` in the main checkout. A report file outside the checkout has its directory mounted too, and a run that serves, `composer workbench:serve`, publishes its port on the host's `127.0.0.1` only. A process already in the image, where the image's `CBOX_IMAGE_TIER` is `dev` (CI, the php service, the container itself), runs the gates in place. `composer image:run -- <command>` runs any command the same way, such as `composer image:run -- vendor/bin/pest --testsuite=Browser` or `--testsuite=Mutation`, and `composer image:prune [-- --dry-run]` removes the volumes (`laravel-cms-<node-modules|cache|bootstrap-cache>-<hash>`, labelled with the checkout's path) of checkouts that are gone (`composer check:selftest` removes its own). `tests/Feature/Tooling/DevImage` covers the docker command with a fake docker.

## composer test:affected

`composer test:affected [-- <pest arguments>]` is fast feedback while working, not a gate: in the dev image, `vendor/bin/pest --parallel --tia` with Pest 5's test impact analysis, which records per test the files and tables it touches through PCOV (`tools/tia/pcov.ini`) in the graph below `~/.pest/tia`, and then reruns only the tests that depend on what changed and replays the rest. The analysis takes Pest files only and stops at a PHPUnit test class, so `tools/bin/test-affected.php` runs the Pest files with `--tia` from `.cache/test-affected/pest.xml` and then every PHPUnit test class, such as the contract suites' classes, from `.cache/test-affected/classes.xml`, both derived from `phpunit.xml` (`Affected\Boundary\PhpunitConfiguration`). An argument that selects tests, such as `--filter` or `--testsuite`, makes Pest run the selection without the analysis.

## CI and mutation testing

CI is `bin/ci`, the single entry script: `.github/workflows/ci.yml` runs it on every pull request, and `docker compose -f compose.ci.yaml run --rm ci` runs it locally in a container on a clean git archive of HEAD (commit first; `docker compose -f compose.ci.yaml down` stops its services). It installs the locked dependencies and runs `composer check -- --pr`: the same scripts as `composer check`, plus gate 7 (the component kit's Storybook: `npm run storybook:build`, `npm run storybook:exports` and `npm run storybook:stories`), gate 8 (the Browser suite), gate 9 (`composer audit --locked --abandoned=report` and `npm audit`) and gate 10 (`composer docs:check`), with gate 11 reported as not run with its reason.

The two slow suites run in shards, because the gates job took 14 minutes 50 seconds of the 15-minute budget in B1 and B2 roughly doubles them (B2-T64): the `Postgres` suite of gate 5 and the `Browser` suite of gate 8 are split over the `SHARDS` (4) shards of a declared plan, `Check\Domain\ShardPlan`, with Pest's own `--shard=<i>/<n>`, which splits a suite by test class and balances the shards by the timings in `tests/.pest/shards.json` when that file is there. The plan is declared, not computed, so `ci.yml` can name the matrix and the verdict knows which shards must report; `bin/ci`'s `suite_shards` and the matrix of `ci.yml` carry the same number, and `tests/Feature/Tooling/Ci/CiWorkflowTest.php` holds the three equal. The parts (`PrPart`): the `gates` job runs `composer check -- --pr --only=gates`, every gate but those two steps, which it reports as run in the shard jobs (`PrProfile::SUITES_IN_SHARDS`, the status `elsewhere`, never `not run`); each `shards` job runs `composer check -- --pr --shard=<i>/4 --shard-report=<file>`, its share of them and the steps the share needs (`ShardPlan::PREPARES`, `composer panel:build`, which the browser tests' pages need), and reports every other gate as run in the gates job (`PrProfile::GATE_IN_GATES_JOB`); and the `verdict` job runs `composer shards:verdict` (`Check\Domain\ShardVerdict`, `tools/bin/shard-verdict.php`), which fails unless the gates part and the shard jobs passed and every shard of the plan reported exactly once, having run every sharded step, each report a `ShardReport` in `suite-shard.json` (`Check\Boundary\ShardReportJson`). So a shard job that never ran fails the run instead of passing as a missing report, and the budget is met by parallelising, never by dropping or thinning a gate (GUARDRAILS 10, GUARDRAILS 7.3). The `verdict` job is the run's result and the status check to require; it runs after the others whatever they did. `composer check -- --pr` without a part runs every gate in one run, the suites whole, as a developer runs it, and a run with mutation testing keeps them whole in its gates job, where its own shards are the shards of mutation on changed files.

Mutation testing, the `Mutation` suite and mutation on changed files in gate 5, is deferred until after v1 and runs only on demand (Sylvester, 2 October 2026: it made every merge take far longer, and the architecture will change before v1; the ordinary tests stay required): without it gate 5 reports both steps as not run with that reason (`PrProfile::MUTATION_DEFERRED`), and nothing of the mutation plan, its shards or its judgement runs; the shards above and their verdict are the ordinary run's. A pull request and a push to main run the `gates` job, the four `shards` jobs of the two slow suites and the `verdict` job, which is the run's result and the status check to require. `composer check -- --pr --mutation` opts in (`PrPart`), and so does `CMS_CI_MUTATION=1` for `bin/ci` (`CMS_CI_MUTATION=1 docker compose -f compose.ci.yaml run --rm ci`) and the boolean input `mutation` of a run of `ci.yml` started by hand (`workflow_dispatch`), which sets it for every job; only then do the `plan` and `mutation` jobs below run, the `shards` jobs of the two suites do not, and the `verdict` judges mutation on changed files instead, as before the decision. With mutation testing, `ci.yml` runs it as parallel jobs (Sylvester, 1 October), each `bin/ci` with `CMS_CI_PART`: `plan` (`composer mutation:plan`, feature `Cbox\Cms\Tooling\Mutation`: `Domain\MutationShards` splits the changed sources into shards by file, one per `FILES_PER_SHARD` (10) files and at most `MAX_SHARDS` (100), dealt out by size, Adapter and Infrastructure in shards of their own with their bytes counted `POSTGRES_WEIGHT` (2) times, each source in exactly one; the shard numbers are the matrix), `gates` (`composer check -- --pr --mutation --only=gates`, which runs the `Mutation` suite and reports mutation on changed files as not run), one job per shard (`shard:<i>/<n>`, `composer check -- --pr --mutation --shard=<i>/<n> --mutation-report=<file>`, only that shard's mutation steps and a `MutationShardReport` with each class's count) and `verdict` (`composer mutation:verdict`, `Domain\MutationVerdict`: fails unless the plan, the gates and every shard succeeded, every shard of the plan reported once with its sources, and every changed class reaches 80 % over all its mutations; a step fails per class too). The containerized run's `bin/ci` (`CMS_CI_PART` unset or `all`) runs the gates, each shard of the two slow suites and the verdict one after the other, and with `CMS_CI_MUTATION=1` the mutation plan, the gates, each mutation shard and the verdict instead, and times each part against the budget on its own, which `PROGRESS.md` records; `CMS_CI_PART=<part>` runs one, such as `CMS_CI_PART=shard:3/4`, and `bin/ci` refuses `plan` without `CMS_CI_MUTATION=1`, and a shard whose count is not the plan's, with exit 2. The reason for gate 11: review by someone other than the author needs branch protection on main that requires it, a repository setting on github.com/cboxdk/cms that Sylvester makes. `composer check -- --gate=<n>` (repeatable, `GateSelection`) runs only those gates of the profile and reports the others as not run, such as `composer check -- --pr --gate=7`. Mutation on changed files needs `CMS_CI_BASE_REF`, the base of the change: `ci.yml` sets it to the pull request's base commit (the commit before the push for a push to main), or a run's input `base_ref`, and checks out with `fetch-depth: 0`; for the containerized run, it may be set on the host, as in `CMS_CI_MUTATION=1 CMS_CI_BASE_REF=HEAD~3 docker compose -f compose.ci.yaml run --rm ci`, and `docker/ci-entry.sh` builds the archive as two commits, the merge base's tree and HEAD's, with `CMS_CI_BASE_REF=HEAD~1` inside. Unset, empty or 40 zeros (the commit before a push that creates a branch), the base is derived from the checkout, by `GitMutationScope` in `bin/ci` and by `docker/ci-entry.sh` in the mounted repository: HEAD~1 when HEAD is the branch `main`, the merge base with `origin/main` (`main` when there is no `origin/main`) on another branch or a detached HEAD, and the empty tree when HEAD is the only commit or the first commit of `main`, so every file counts as changed. An unknown ref, or a base that cannot be derived, fails the mutation step with the reason. Before `bin/ci`, `docker/ci-setup.sh` runs from the checkout in both places; it fails when PCOV is not loaded, and gives the image Chromium for the Playwright that `package-lock.json` pins, and fails when it cannot. Every action in `ci.yml` is pinned to a commit SHA with its tag as a comment. It never runs the gates as root, because the tests of file permissions skip as root. Run the containerized run after changing `bin/ci`, the CI files or the environment the gates need, and record its wall time in `PROGRESS.md` against the 15-minute budget of GUARDRAILS 10.

## The selftest

Run `composer check:selftest` after changing a gate, the tool configuration or the check itself. It makes a git worktree of HEAD in the system temp directory, runs `composer install` and `npm ci` there, plants one known violation per gate, runs `composer check` and then `composer check -- --pr --gate=7` for the gate of the PR profile it plants in too (`Plants::PR_GATES`), and passes only when each gate fails with a path inside the worktree; then it removes the worktree. It checks HEAD, so commit first. It takes about four minutes. The worktree's suites run in the worktree's own test database, and the selftest drops it as the owner role before it removes the worktree, also after a failure, so it can run next to the suites of another checkout.

## The JS gates, the kit and Storybook

The JS gates run from the root after `npm ci`: `npm run typecheck`, `npm run lint` and `npm run format:check`. The shared tsconfig, ESLint and Prettier configuration lives in the `js/tooling` workspace; the root files only point at it. The panel is the workspace `js/panel` and its components the workspace `js/ui-kit` (working names). The kit's design tokens have one source, `js/ui-kit/tokens.json` (tiers primitive, semantic and component, the contrast pairs and the curated `data-cms-part` hooks): `npm run generate:tokens` (`js/ui-kit/scripts/generate-tokens.js`, a step of gate 6) writes `js/ui-kit/src/tokens.css`, `js/ui-kit/src/generated/tokens.ts` (`TokenName`, `ThemeTokenName`, `PartName`), the theme schema `js/ui-kit/src/generated/theme.v1.json` and `docs/ui/tokens.md`; never edit those by hand. `js/ui-kit/src/layers.css` declares the cascade layers `cms.reset, cms.tokens, cms.addon, cms.kit, cms.panel, cms.theme` and the panel imports it first; every kit stylesheet keeps its rules in its layer. The JS unit suite is Vitest (decision D11): `vitest.config.ts` at the root has the project `unit` (every `js/<workspace>/tests/**/*.test.{js,ts,tsx}` and the TypeScript examples of the docs, `examples/Vitest/**/*.test.{ts,tsx}`, in Node, or in jsdom for a file that asks for it with `@vitest-environment jsdom`, such as the kit's keyboard tests of Dialog, Menu, Combobox, CommandPalette, DataTable and Wizard in `js/ui-kit/tests/keyboard`), which `npm run test:js` runs as the step `Vitest` of gate 5 (`LocalProfile::VITEST`), with the reporter `js/tooling/vitest-no-skipped.js` failing a skipped test, and the project `storybook`. `npm run test:kit [-- <name>]` runs the kit's tests in `js/ui-kit/tests` (contrast pairs in both modes, layers, part hooks, catalogues, the story-per-export check), part of that suite, and `tests/Feature/Tooling/ComponentKitTest.php` runs them with planted failures in gate 5. Vitest's cache is `.cache/vitest`. The kit's Storybook (gate 7, `PrProfile::STORYBOOK_STEPS`) is Storybook 10 with React and Vite in `js/ui-kit/.storybook`, its stories in `js/ui-kit/stories`, one file per component, typed by `js/ui-kit/stories/csf.ts` (Storybook's own declarations do not compile under the repository's tsconfig, so no file imports them) and reading their texts from `js/ui-kit/stories/texts.ts`: `npm run storybook:build` builds it into `.cache/storybook/static`; `npm run storybook:exports` (`js/ui-kit/scripts/story-exports.js`) fails on a component the kit's entry exports, a value named in PascalCase, that is the `component` of no story file's meta, imported from `@cboxdk/cms-ui-kit`; `npm run storybook:stories` (`js/ui-kit/scripts/story-tests.js`) runs every story as a test of the `storybook` project in Chromium (its play function, axe through `@storybook/addon-a11y` with `a11y.test: 'error'`, and a screenshot of the page compared with `js/ui-kit/visual-baselines/<story id>.png`, decision D10) and refuses to run outside the dev image, where the baselines are rendered: `composer image:run -- npm run storybook:test` runs the export check and the story tests, and `composer image:run -- npm run storybook:baselines` writes every baseline anew after a change meant to change how the kit looks, and then records the SHA-256 of `js/ui-kit/scripts/rendered-from.js`'s `PANEL_POINT_SOURCES` (`PanelPointStory.tsx` and the generated `points.ts` and `PanelPoints.stories.tsx`) in `js/ui-kit/visual-baselines/rendered-from.json`; `js/ui-kit/tests/story-screenshots.test.js`, in gate 5, fails a story without a baseline (its id read with the TypeScript parser and named as Storybook and Vitest's `toMatchScreenshot` name it), a baseline without a story, and a recorded digest that differs from the file, so story data that `cms:panel:stories` writes anew without new baselines fails locally rather than only in gate 7. Every new kit component gets a story file, with a story for each state (empty, loading and failed for one that shows data) and the stories `Dark`, `ForcedColors` and `Danish` (`inDark`, `inForcedColours`, `inDanish`; the story tests emulate forced colours for the story named Forced Colors and reduced motion for all), an MDX page beside it (`<Name>.mdx`, through `@storybook/addon-docs`), both held by `js/ui-kit/tests/story-variants.test.js`, and a new story its baseline. Every kit export carries one stability tag, `@stable` or `@experimental` (B1 components are experimental), and `js/ui-kit/api/cms-ui-kit.api.md` is the committed API report (`js/ui-kit/scripts/api-report.js`: TypeScript declarations into `.cache/ui-kit-api`, API Extractor, each export's stability tag in place of `@public`): the test `js/ui-kit/tests/api/report.test.js` fails when it differs from what the kit exports or a tag is missing, and `npm run api:report` writes it anew after an intended change. `tests/Feature/Tooling/StorybookTest.php` holds the configuration. The kit's own texts are `js/ui-kit/src/i18n/catalogues` through `KitI18nProvider`. ESLint's `cms/no-literal-ui-text` rejects literal text in JSX, `cms-kit/no-style-props` a kit component that accepts `className` or `style`, and `no-restricted-imports` React Aria outside the kit and from `react-aria-components`' root inside it (import by component module); `npm run lint:translations` (run by `tests/Feature/Tooling/JsWorkspacesTest.php` in gate 5) holds the panel's and the kit's catalogues to the same keys in `da` and `en`.

## The Pest suites

The Pest suites are gate 5 of GUARDRAILS 10: `Unit`, `Codecs`, `Contract`, `Postgres`, `Arch` and `Actions` in `phpunit.xml`. In CI the `Postgres` suite runs in the shards of `ShardPlan`, one job each (see [CI](#ci-and-mutation-testing)); locally it runs whole. A module puts tests for a suite in `packages/<module>/tests/<Suite>`; its other tests are `Unit`. The `Postgres` suite needs `composer services:up` and runs through the testkit's `RealPostgres` harness: this checkout's own test database, `cms_test_<hash of the checkout's path>`, created by the owner role when it is missing (see [the test databases](#a-test-database-per-checkout)), the app role on the default connection, migrations by the owner role (`migrate:fresh` once per process, after `Infrastructure\PartitionSweep` has dropped the leaf partitions an earlier run left, one statement each, so no statement runs out of the server's shared lock table), no wrapping transaction, after each test the owner drops every leaf partition (`PartitionSweep`, so a test covers the dates it writes at itself) and truncates, and a nested transaction fails the test. Helpers: `app(IndependentConnections::class)` and `app(ChildProcesses::class)`. A test that needs cluster-wide roles, such as `packages/core/tests/Postgres/DoctorRoleMembershipTest.php`, connects as the superuser of compose.yaml from `DB_SUPERUSER_USERNAME` and `DB_SUPERUSER_PASSWORD` in `phpunit.xml`, makes scratch roles under random names and drops them after the test; the application never connects as it. The testkit's `RealValkey` harness runs there too: every Redis connection uses database index 15 and a key prefix per PHP process, `cms_test_<run id>_`, and the keys under it are removed with SCAN and UNLINK after each test and when the process ends. The run is `app(ValkeyRun::class)`.

## The Browser suite

The `Browser` suite is gate 8 of GUARDRAILS 10, and in CI it runs in the shards of `ShardPlan` as the `Postgres` suite does, one job each with its own `composer panel:build` (see [CI](#ci-and-mutation-testing)): Pest 5 browser tests in `tests/Browser`, run with `composer panel:build` and then `composer image:run -- vendor/bin/pest --testsuite=Browser`, in the dev image with the image's Chromium for the Playwright that `package.json` pins; the PR profile's gate 8 runs `composer panel:build` (`PrProfile::PANEL_BUILD`) before the suite, and then the suite's group `browser-matrix` (`PrProfile::BROWSER_MATRIX_GROUP`, `->group('browser-matrix')`) in Firefox and WebKit too (`--browser firefox`, `--browser safari`), which `docker/ci-setup.sh` installs, with WebKit's system libraries, because the image ships Chromium only; put a test there when it holds something every browser must do, such as the panel's shared modules and import map under its policy (`tests/Browser/Panel/SharedExternalsTest.php`, `PanelCspAddonModulesTest.php`, with the test-only modules of `tests/Browser/Fixtures/PanelModules` built by `Tests\Support\Browser\PanelModules` and put on a real panel page by `PanelProbe`). The browser plugin serves the Testbench workbench application in-process on a free port, so a test calls `visit('/')` with a path; routes live in `workbench/routes/web.php` with the web middleware group, and a test may add its own with `Route::get()`. The suite runs on the testkit's `RealPostgres` and `RealValkey` harnesses as the `Postgres` suite does (`tests/Pest.php`): the checkout's, or a parallel worker's, own migrated test database as the app role and Valkey under the run's prefix, so it needs `composer services:up`; `tests/Browser/HarnessTest.php` proves it through a page. Each page test asserts its visible text, `assertNoConsoleLogs()` and `assertNoJavaScriptErrors()`, and every panel page test calls `Cbox\Cms\Tests\Support\Browser\PanelPage::assertPage($page, [<translation keys>])`, which also asserts each text from the panel's English catalogue, `assertNoAccessibilityIssues()` at every impact, axe's WCAG 2.0, 2.1 and 2.2 A and AA rules (`WCAG_22_AA`, GUARDRAILS 8) and no Content-Security-Policy violation the browser reported; `tests/Browser/Panel/PublicPageTest.php` is the first, with negative controls. Screenshots of failures land in `tests/Browser/Screenshots`, which git ignores.

## The Mutation suite

The `Mutation` suite holds the tests that need a coverage driver, in `tests/Mutation`: mutation on changed files for real, on a scratch repository. The local profile leaves the suite out (`LocalProfile::OTHER_SUITES`), and the PR profile runs it in gate 5 only with `--mutation`, because mutation testing is deferred until after v1 (Sylvester, 2 October 2026). Run it with `composer image:run -- vendor/bin/pest --testsuite=Mutation`, which has PCOV in the dev image, from any checkout. Mutation on changed files itself runs with `CMS_CI_BASE_REF=<base> composer check -- --pr --mutation`, which passes `CMS_CI_BASE_REF` into the image.

## The gate runner

The gate runner behind `composer check` and `composer check:selftest` is repository tooling in `tools/` (`Cbox\Cms\Tooling`, autoload-dev, entry scripts in `tools/bin`), not a module of the package. PHPStan, Rector and Pint cover it; the Arch suite does not, as for `tests/Support`. `Check\Domain\LocalProfile` defines the gates: each gate runs the Composer or npm script a developer runs by hand (`lint:check`, `format:check`, `rector:check`, `analyse`, `typecheck`, `lint`, `check:generated`), and gate 5 first runs `composer install:check` (step `Installation`), then `npm run test:js` (step `Vitest`, the JS unit suite), then `vendor/bin/pest --testsuite=<suite> --fail-on-skipped --fail-on-incomplete --parallel` for each suite (`LocalProfile::suiteStep()`): each suite spread over one worker process per CPU, every worker of the `Postgres` suite in a test database of its own (see [the test databases](#a-test-database-per-checkout)). The PR profile's `Mutation` suite runs in one process (`parallel: false`), because each of its tests starts a parallel Pest run of its own. `install:check` (`tools/bin/install-check.php`, `Install\Domain\InstallAudit`) fails when vendor/ is not what composer.lock and composer.json describe: a package that differs from the lock by version or reference, or a PSR-4, PSR-0 or files rule of the root's autoload or autoload-dev that the dumped autoloader lacks or maps elsewhere. A checkout that moved without `composer install`, such as the main checkout after the merge queue fast-forwards it, fails there with the fix instead of failing a suite at load with "Class not found". A new suite in `phpunit.xml` must be added there; a test fails until it is. `Check\Domain\PrProfile` is the PR profile as CI runs it (`composer check -- --pr`, from `bin/ci`): the same steps for gates 1 to 6, gate 7 (`PrProfile::STORYBOOK_STEPS`: `npm run storybook:build`, `storybook:exports` and `storybook:stories`), gate 8, gate 9 and gate 10, whose one step is `composer docs:check`, and gate 11, which CI does not run, as not run with its reason. Gate 5 reports the `Mutation` suite and mutation on changed files as not run with `PrProfile::MUTATION_DEFERRED` (Sylvester, 2 October 2026), unless `--mutation` opts in (`Check\Domain\PrPart`: `withoutMutation()` by default, `suiteGates()` for `--only=gates` and `suiteShard()` for `--shard`, and with `--mutation` `all()`, `gates()` for `--only=gates` and `shard()` for `--shard`), when gate 5 adds both as before; everything below about mutation on changed files holds for a run with `--mutation`. The local profile leaves gate 10 out, as GUARDRAILS 10 says, but `tests/Feature/Tooling/Docs/RepositoryDocsTest.php` runs the same audit on the repository in the Unit suite of gate 5, so `composer check` fails on every finding of gate 10 too (GUARDRAILS 7.3). Mutation on changed files is the feature `Cbox\Cms\Tooling\Mutation`: `Boundary\GitMutationScope` finds the PHP files below `packages/*/src` added or changed between the base of the change (the merge base of `CMS_CI_BASE_REF` and HEAD, or the base it derives) and HEAD and the class, enum, interface or trait each declares; `Domain\MutationSteps` makes the steps: `vendor/bin/pest --mutate --everything --path=<files>` with PCOV from `tools/mutation/pcov.ini` (through `PHP_INI_SCAN_DIR`, because the image loads PCOV but leaves it off). The fast suites' step mutates every changed file with `--parallel` against `Unit`, `Codecs`, `Contract`, `Actions` and `Arch` and records each mutation's outcome without judging; the step with Postgres mutates every changed file again with `--parallel` against `Postgres` alone, each worker and each run of a single mutation in a test database of its own (see [the test databases](#a-test-database-per-checkout)), judges every class, and counts a mutation as caught when either run caught it (`Domain\MutationLedger`), as one run of every suite would, without one PHP process holding every suite's tests and coverage, which ran out of memory. Every class is mutated against `Postgres`, not only Adapter and Infrastructure, because a class of any layer, such as an Artisan command, can have its tests there. When the fast suites caught every mutation, the step with Postgres passes without running (`Domain\CaughtByFastSuites`, a `Check\Domain\StepPrecheck`). Otherwise it runs only the mutations the fast suites did not catch: `CaughtByFastSuites` is also a `Check\Domain\StepPreparation`, which writes the caught ones to `.cache/mutation/caught.json` and names the file in `CMS_MUTATION_CAUGHT`, and the plugin's `Adapter\SkipCaughtMutations` removes them from the run, which the ledger counts as caught. In pest-plugin-mutate 5, `--everything` ignores `--class`, so the files are named with `--path`. No changed file passes the step with "0 changed classes"; a missing base fails it. The Pest plugin `Mutation\Adapter\PestMutationReport`, in `composer.json`'s `extra.pest.plugins`, prints each file's mutations, by Pest's id, with whether a test caught each, the line it starts on and its mutator, on one line when `CMS_MUTATION_REPORT=1`, and `Domain\MutationReportReader` lists each class with its score and fails the step when a class is below 80 over its mutations, naming each such class; Pest's own `--min` is not used, because the step with Postgres counts the fast suites' run as well. pest-plugin-mutate starts each mutation's Pest process with every test that covered the mutated lines in one `--filter` argument, which Linux refuses past 128 KiB (MAX_ARG_STRLEN), so the plugin also registers `Adapter\CoverageFilterWidener`, which rewrites Pest's coverage file before the mutations are made: each file whose covering tests together would make a longer argument, such as a service provider every test boots, has its lines covered by their test classes instead (`Domain\TestFilterWidth`), so its mutations run every test of those classes, a superset of the covering tests. ## A test database per checkout

Each checkout, a git worktree included, runs its tests in a Postgres test database of its own, so parallel worktrees never share rows. The name is `TestDatabaseName::for($base, $root)` in the testkit's feature `Cbox\Cms\Testkit\Postgres`: the configured database (`DB_DATABASE`, `cms_test`), `_`, and the first 12 hex digits of the SHA-256 of the real path of the checkout root, the directory of the Composer root package of the autoloader that loads the testkit (`Boundary\CheckoutRoot`); at most 63 bytes. A worker of a parallel run (Pest's `--parallel`, and the mutation plugin's runs of single mutations), which has `TEST_TOKEN` (`Boundary\TestWorker`; `PARATEST` without it is refused), runs in a database of its own, `TestDatabaseName::for($base, $root, $worker)`: the checkout's name, `_w` and the worker's number, such as `cms_test_3f9a0c21d4e7_w2`, at most 63 bytes and the same for the same checkout and worker, so the workers never share rows. `tests/TestCase.php` points every pgsql connection that names the configured database, the checkout's database or a worker's at the checkout's database, or in a worker at the worker's, before the first connection opens (`Boundary\CheckoutConnections::point()`, which reads the process's worker from `TestWorker::current()`; `pointAt()` takes it explicitly), so the owner connection, `IndependentConnections`, `ChildProcesses` and the doctor's `cms_doctor` and `cms_doctor_owner` follow; the `RealPostgres` harness does it too and then calls `TestDatabase::ensure()`, which runs `TestDatabase::provision()` once per process for the process's database, the checkout's or its worker's, and keeps a failure, before `migrate:fresh`. `provision()` is the one entry point, also for a child process with another root (`TestDatabase::command()`, `packages/testkit/bin/test-database.php`, payload `Boundary\TestDatabasePayload` on stdin): it connects as the owner role to the configured database, fails fast when the server does not answer or the owner role lacks CREATEDB (the message names the role, CREATEDB, the database and `composer services:up`), and under a transaction-scoped advisory lock in the configured database, keyed by the name of the checkout's database for the checkout's and its workers' alike (`Infrastructure\PostgresTestDatabases::lockKey()`), runs `Infrastructure\TestDatabaseSetup`, a copy of `docker/postgres/sql/database.sql` with the role names and the schema read from the connections, where SQLSTATE 42P04 on CREATE DATABASE counts as done; `composer check:selftest` drops its worktree's through `tools/bin/drop-test-database.php`, which reads the owner connection from `phpunit.xml` and the environment (`Cbox\Cms\Tooling\TestDatabase\Boundary\PhpunitDatabase`). `composer test-db:prune` (`tools/bin/prune-test-databases.php`, feature `Cbox\Cms\Tooling\TestDatabase`: `Domain\PrunePlan` decides, `Adapter\PostgresTestDatabaseCatalog` lists and drops) cleans up after checkouts removed without the selftest: as the owner role on the configured database it looks at every database named `<configured>_<12 hex digits>` and every worker's named `<configured>_<12 hex digits>_w<n>` and drops, with `DROP DATABASE ... WITH (FORCE)`, exactly those whose comment names this host and a checkout that is no longer a directory or no longer derives the checkout's name; it keeps the configured database, this checkout's and its workers', other hosts' and those without a valid comment, prints each name with its verdict and reason, and `composer test-db:prune -- --dry-run` drops nothing. ## Tool caches

Gate tools keep their caches in the checkout, in the git-ignored `.cache/` with a directory per tool, never in the shared system temp directory, so parallel worktrees and the selftest's worktree never share them: PHPStan's `tmpDir` is `.cache/phpstan` (`phpstan.neon`; result cache, container cache and Larastan's migration cache), Rector's file cache is `.cache/rector/files` and the container cache of its PHPStan `.cache/rector/container` (`rector.php` creates that one, because Rector requires it to exist), and Pint's cache file is `.cache/pint/pint.cache` (`pint.json`, relative to the root, where the Composer scripts run it). Pint compiles the Blade views of its console summary into the system temp directory, which `pint.json` cannot move, so the `lint` and `lint:check` scripts run it through `tools/bin/pint.php`, which sets `TMPDIR` to `.cache/pint/tmp`; a coding agent does not see those views, because Pint prints JSON under an agent. PHPUnit's cache stays in `.phpunit.cache`, and the mutation plugin's in `vendor/pestphp/pest-plugin-mutate/.temp`, both in the checkout already. tsc, ESLint and Prettier run without a cache; a cache for one of them gets a directory in `.cache/` first. The only file a gate leaves in the system temp directory is the PHPStan boot lock, named by a hash of the checkout's path, and paratest's worker files, named per run and removed at its end. `tests/Feature/Tooling/ToolCachesTest.php` holds the configuration to this and runs each tool with `TMPDIR` pointed at an empty directory, in a terminal's environment without the variables of a coding agent.

## The services

`composer services:up` and `composer services:down` run `tools/bin/services.php` (feature `Cbox\Cms\Tooling\Services`). It finds the main checkout from `git rev-parse --path-format=absolute --git-common-dir` and always runs docker compose with the main checkout's `compose.yaml` and `--project-directory`, so no container of compose.yaml ever mounts a worktree. From the main checkout, services:up runs `up -d --wait` and then the idempotent `10-cms.sh`, and services:down stops the services and keeps the volumes. The services are shared by the main checkout and every linked worktree: from a worktree, services:up runs `up -d --wait --no-recreate postgres valkey`, so it never recreates a running container and never starts php, then runs `10-cms.sh`, and says that the php container mounts the main checkout; services:down refuses with exit 1. `docker compose exec php ...` therefore always runs the main checkout's code, not a worktree's; `composer check`, `composer test:affected` and `composer image:run` run the current checkout's code in a container of their own. `tests/Feature/Tooling/Ci/ServicesScriptTest.php` covers it with a fake docker.

## cms:doctor and the dev database

`cms:doctor` checks the workbench's dev database `cms`, which every checkout shares. In the php container, `docker compose exec php vendor/bin/testbench cms:doctor` needs no flag: compose.yaml mounts the drop-in `docker/php/conf.d/cms.ini` read-only as `/usr/local/etc/php/conf.d/zz-cms.ini`, after the image's `99-cbox.ini`, and it sets `allow_url_fopen = Off`; Composer there downloads through the curl extension. On a host whose php.ini has `allow_url_fopen = On`, such as Herd's, run `php -d allow_url_fopen=0 vendor/bin/testbench cms:doctor`; without the flag `php.allow_url_fopen` fails and the doctor exits 78. The CI files keep the image's default. Prepare the database from the main checkout, never from a worktree: `composer services:up`, then `composer dev:prepare`, whose every step runs in the dev image through `tools/bin/dev-image.php` (`tests/Feature/Tooling/DevPrepareTest.php`): `tools/bin/workbench-env.php` (feature `Cbox\Cms\Tooling\Workbench`, `WorkbenchEnvironment`), which gives `workbench/.env` an `APP_KEY` once, from `workbench/.env.example` when the file is missing, and copies the file to Testbench's application, which copies it itself only when it has none; the migrations as the owner role (`migrate --database=pgsql_owner`, the connection in `cbox-cms.database.owner_connection`); `cms:partitions:maintain` for the partition runway; `cms:build`; `cms:install`; `cms:sites:sync`, which prints the root node of the workbench's site, also when it was registered before; and `composer panel:build`. ## composer progress:check

`composer progress:check -- <block>-<task> [--changed-checks] [--range=main..HEAD]` fails unless the task is recorded: an entry naming it under "Kontroller kørt" in `PROGRESS.md` with the gates it ran, with `--changed-checks` also its entry in `CHECKS-LOG.md` under its block that says GUARDRAILS 7.3 (an entry under "Til review af Sylvester" does not count), and with `--range` no commit of the range that changes no file (feature `Cbox\Cms\Tooling\Progress`, `tools/bin/progress-check.php`). The merge queue of `.claude/workflows/cms-milestone.js` writes each task's entries in a commit `<block>-<task>: progress` and runs it before it moves main; a task reports its changed checks in `changedChecks` and never commits without a change. `composer progress:test` runs the tests that read `PROGRESS.md`, `CHECKS-LOG.md` and this checkout's review commits, which all live in `tests/Feature/Tooling/Progress` (a test there keeps them there), on the working tree and HEAD. `composer check` runs before the progress commit exists, so every agent of the workflow that commits entries, the merge queue, the regression fix and the exit phase, runs `composer progress:test` on that commit, and the merge queue moves main only after it passed.

## Review fixes on main

A review fix committed straight on main, with a message that starts `<block>-review:`, never passes the merge queue, so it adds its own entries in the same commit: one naming `<block>-review` under "Kontroller kørt" in `PROGRESS.md` with the gates it ran, and, when it changes or removes a check file (a file below a `tests` directory, the testkit, `examples/`, `tools/`, `js/tooling/`, `.github/`, `docker/`, `phpunit.xml`, `phpstan.neon`, `rector.php`, `pint.json`, `composer.json`, `package.json`, `eslint.config.js`, `tsconfig.json`, `.prettierrc`, `.prettierignore`, `bin/ci`, `compose.ci.yaml` or `compose.yaml` that loses lines, as `Progress\Domain\CheckPaths` lists them), one naming `<block>-review` in `CHECKS-LOG.md` under its block that says GUARDRAILS 7.3. `tests/Feature/Tooling/Progress/ProgressCheckTest.php` holds every such commit in the history to it (`Progress\Domain\ReviewCommitAudit`, read with `Progress\Boundary\GitReviewCommits`; a commit from before `CHECKS-LOG.md` existed is held to the entry it added under "Til review af Sylvester"); a commit that missed them is recorded afterwards only by entries that name its hash, under "Kontroller kørt" and in `CHECKS-LOG.md`.
