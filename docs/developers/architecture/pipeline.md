# The command and query pipelines

Every write and every read of the kernel runs through one of two actions, `CommandPipeline` and `QueryPipeline`. This page follows a call from its DTOs to its commit or answer.

## The shapes in the contracts module

The pipeline's shapes live in the contracts module (GUARDRAILS 2.1, PRD 5.5, 6.1, 6.2; `docs/addons/commands.md`, `plans.md` and `queries.md`). `Pipeline\Command` and `Pipeline\Query` are marker interfaces for the command and query DTOs, which declare their name and version with `#[Command]` and `#[Query]` (one namespace of `CommandName`s for both), and `Pipeline\Result` for a read's result. `Pipeline\WriteAction<TCommand, TAggregates>` has the two pure steps `resolve(Command): Aggregates` and `plan(Command, Aggregates): Plan`; `Pipeline\Aggregates::versions()` gives the `ReadVersions` the kernel checks at commit, each an `AggregateRef` (the typed ids and `Content\VariantRef`, keyed `<kind>:<id>` by `aggregateKey()`) with its `AggregateVersion`, or null when it was absent. `Pipeline\QueryAction<TQuery, TResult>` has `handle(Query): Result`. `Plans\Plan` is an ordered list of `Plans\Mutation`s and sub-plans, applied depth first (`mutations()`); the mutations are in `Plans\Mutations`: `EntryCreated`, `RevisionCreated`, `HeadMoved`, `VariantReleased`, `VariantUnreleased`, `PlacementCreated`, `PlacementWindowSet` and `ActorDeactivated` (`RevisionCreated` names the entry's `TypeId`, so the kernel validates its fields), over the ids `EntryId`, `NodeId`, `PlacementId`, `SiteId`, `ActorId` and `TypeId` in `Ids` and `Locale`, `VariantKey`, `RevisionNumber` and `TimeWindow` in `Content`. A revision's fields are `Fields\FieldValues`: the owner's `FieldMap` by `FieldHandle` and each extender's under its `FieldNamespace`, with the values in `Fields` (`NullValue`, `TextValue`, `IntegerValue`, `DecimalValue`, `BooleanValue`, `DateValue`, `DateTimeValue`, `ListValue`, `GroupValue`, `MapValue`). `Envelope\Envelope` is built by a surface, never an action: `Envelope::external()` requires the caller's `IdempotencyKey` and takes only an exposed `IssuingSurface`, and `Envelope::internal()` takes only an internal issuer (`Job`, `Scheduler`, `Subscriber`, `Sidecar`, `Seed`) and derives the key from its `UnitOfWork` as `<issuer>:<sha256 of the unit>` (`Envelope::deriveKey()`). The wait level defaults to `Commit`; the actor never appears in its `OnBehalfOf` chain; the reason's `ReasonText` has no public property and is read only with `classifiedContent()`, and `auditReason()` gives the audit chain and events the `ReasonCode` alone. A write ends in `Results\WriteResult`: the `Receipt`, at least one `CatalogError` (an `ErrorCode`, an optional `FieldPath` and the cause) when rejected, and for a dry run a `Results\DryRunReport`: the `Plan`, its `BlastRadius` (the mutations and the aggregates changed, by kind) and its diff, an `AggregateChange` per aggregate with the version read and the version the commit would give it. A command that carries the versions its caller saw implements `Pipeline\ExpectsVersions` (`expectedVersions(): ReadVersions`). The receipt, a rejection's problem details and the envelope fields a caller sends have generated JSON forms (see [the JSON contracts](json-contracts.md)); no code serialises them by hand.

## The command pipeline

The command pipeline (GUARDRAILS 2.1, 4.1, PRD 6.1, 6.2) is the action `Cbox\Cms\Core\Pipeline\Actions\CommandPipeline` (`#[Internal]`): `run(CommandCall): WriteResult`, where the `Domain\Dto\CommandCall` holds the command, the envelope and the `AccessContext`, whose principal must be the envelope's actor with its chain in order (`InvalidCommandCall` otherwise). The whole call runs in the port `Domain\CommandTransaction` (`run(AccessContext, Closure(): WriteResult)`), bound to `Adapter\ConnectionCommandTransaction` on the default connection: it begins the transaction, sets READ COMMITTED as its first statement, then `transaction_timeout` to `CommandTransaction::TIMEOUT_MILLISECONDS` (5000, PRD 7.4) by turning it off and on in one statement (`ConnectionCommandTransaction::TIMEOUT`), because Postgres restarts the timer only when the setting goes from off to on, then the call's access context through `ActorContext`; while the work runs, the process's `Adapter\SavepointRefusal` (a singleton, callbacks registered once per connection object) refuses a nested `beginTransaction()` and a `SAVEPOINT`, `RELEASE` or `ROLLBACK TO` statement on the connection with `Domain\SavepointRefused` before it reaches Postgres. It commits only a result that committed a changeset, rolls back every other result and work that throws (then throws the same exception), rolls back a commit that fails, and refuses to run inside an open transaction with `Domain\CommandTransactionOpen`; the pipeline itself never begins or ends one. It owns every phase: idempotency first (PRD 6.1; not for a dry run, which claims nothing): the `IdempotencyStore` claims the envelope's key (an internal issuer's is the key `Envelope::internal()` derived from its unit of work) in `Envelope::idempotencyScope()` with the command's content hash from the port `Domain\CommandContentHasher` (name, version and input) and the wait budget of `IdempotencySettings` (`cbox-cms.idempotency.wait_budget_ms`); `Fresh` runs the phases below and a commit completes the key with the changeset in the same transaction, `Replay` returns the first call's receipt from the `ReceiptStore` built by `Domain\ReplayReceipt` for this call's wait level (Commit is reached; a level past commit only when every listed projection has acknowledged, else `committed_wait_timeout`; the stored commit position and no consistency token) and runs nothing, a missing receipt throws `Domain\MissingReplayReceipt`, `Conflict` is `idempotency_conflict` and `InFlight` is `idempotency_in_flight`; then resolve (the actor and each actor of its on-behalf-of chain read through the `ActorDirectory` as aggregates at their version, `actor_not_active` when one is missing or not active, invariant 37; then the action's `resolve()`; `version_conflict` when a command that `ExpectsVersions` saw another version, or when the action read an actor at another version than the kernel), authorize (the port `Domain\CommandAuthorizer` with the access context, the command's name, the command and the aggregates; a `Dto\Authorization` refusal is `unauthorized` with its reason), plan (the action's `plan()`, then its shape: every aggregate a mutation changes was read, or `InvalidCommandCall`, a bug of the action, and every `RevisionCreated`'s type is in the `TypeCatalog`, or `validation_failed`; then a value other than null for a field the caller may not read, classified above the call's classification access or, for a call `CommandCall::issuedByAgent()`, a field or nested group field with `agents: false`, is `unauthorized` at its path below `fields`, by `Domain\WritableFields`, PRD 2.31, 12.2), the hooks' phases, and validate (first every such closed field of a revision takes the value of the revision the plan's `HeadMoved` moves the head from, read through `RevisionContents`, which gives the head snapshot for a type whose history is audit-only or none, so a revise never erases what its caller cannot see, and a head it cannot read under the type's schema version is `validation_failed`; then on the plan as the transform hooks left it, invariant 12: the fields of every revision pass the port `Domain\FieldValidation` at the Write stage, with paths below `fields`, then the validate hooks add theirs; errors reject with `validation_failed` followed by each error), the dry-run exit (`WriteResult::dryRun()` with `DryRunReport::of($plan, $reads)`) and commit (the port `Domain\ChangesetCommitter`, given a `Dto\PendingChangeset` with the command's name, version and input, the envelope, the access context, the plan and every read, actors included; it writes in the command transaction and answers `Dto\Committed` with the receipt and its changeset id or `Dto\VersionConflict` of `StaleRead`s, mapped to `version_conflict`; a `PartitionMissing` from the commit or from the completion of the key is `partition_missing`, and the transaction rolls back everything). Rejected and dry-run receipts use the envelope's wait level and `RetentionClass::Standard`. The action of a command comes from the port `Domain\WriteActions`, bound to `Adapter\RegistryWriteActions` (the compiled registry's `actionFor()` and the container; `UnknownCommand` for a class no write action handles), and `FieldValidation` is bound to `Boundary\TypeRulesFieldValidation`, which finds the type's validator through `TypeValidators`, puts the `FieldValues` in the input form with `Boundary\FieldValuesInput` (objects for groups and maps, lists for lists, a UTC date-time with microseconds) and runs the `InputValidator`. `CommandAuthorizer` is bound to `Access\Adapter\PostgresCommandAuthorizer`: a command is allowed only through a role of the actor whose permissions (`role_permissions`) name it and that reaches every `AuthorizationTarget` (a `NodeId` and a `Locale`, or null for every locale) of the action's `Aggregates::authorizationScope()`, as `Access\Domain\PermissionRule` decides with the AccessCompiler's nearest-grant rule per role and locale; a target in every locale must be reached in each, `AuthorizationScope::anywhere()` (no node, or the aggregate read as absent) needs the permission on some node, and the anonymous principal is refused. It reads the grants and the targets' paths through `Access\Adapter\PostgresGrants` under the command transaction's actor context. `FakeCommandAuthorizer::granting()` decides the same from `Tests\Access\Fakes\FakePermissions`, held to it by `CommandAuthorizerBehaviour`. The content hasher is `CodecCommandContentHasher` (over the command's canonical form from its generated codec). `resolve()` and `plan()` get the command and the aggregates and nothing else, and `tests/Arch/ActionsTest.php` (`Cbox\Cms\Tests\Support\Arch\ActionPlacement`, covered by `tests/Feature/Tooling/ActionPlacementTest.php`) holds every `WriteAction` and `QueryAction` of `packages/*/src` and `workbench/app` to an `Actions` namespace, where the layer's rules forbid connections and transactions. The pipeline's tests are `packages/core/tests/Actions/CommandPipelineTest.php` and `CommandPipelineIdempotencyTest.php` (with the testkit's fake idempotency and receipt stores) with the test-only command `probe.rename` (`packages/core/tests/Pipeline/Probe`) and the fakes in `packages/core/tests/Pipeline/Fakes`; `WriteActionsBehaviour`, `FieldValidationBehaviour` and `CommandTransactionBehaviour` hold the fakes of the three bound ports to their implementations. `docs/addons/commands.md` describes the phases.

## The commit

The commit (PRD 6.2 phase 7, 7.3, 8.4, GUARDRAILS 4.1) is `Cbox\Cms\Core\Pipeline\Adapter\PostgresChangesetCommitter`, bound to `ChangesetCommitter`, on the command transaction's connection and under its actor context; it never begins, ends or savepoints a transaction and throws `TransactionRequired::forChangeset()` outside one. It locks every read aggregate, actors included, one at a time in aggregate key order through the `Domain\VersionLock` of its kind (the part of the key before the first colon), with `Domain\LockStrength::Update` for an aggregate the plan changes and `Share` for one it only read; an aggregate read as absent first takes the transaction-scoped advisory lock `Adapter\AggregateLock::of($aggregate)` (first 64 bits of a versioned SHA-256 of the key), so two creates of one aggregate end in `version_conflict`, not a unique violation. Any stale read answers `VersionConflict` and writes nothing. Then it writes the changeset through `Changesets\Infrastructure\ChangesetWriter` (`changeset_register` with retention class Standard, `changesets` with `format_version` 1 and the commit position as the `xid` default, `changeset_principals` from position 1, the reason's text in `changeset_reason_texts` classified `personal`, and one `audit` row with the changed aggregates' keys and no legal basis, from a `Changesets\Domain\Dto\ChangesetRecord`), each mutation in plan order through the `Domain\MutationWriter` of its class with a `Dto\MutationContext` (changeset id, the Clock's time, the actor, and the aggregate's new version: one above the version read, 1 for an absent one, the same for every mutation of one aggregate), the returned events through the `EventWriter` (bulk stream for the issuers `migration` and `seed`, interactive otherwise), and the `StoredReceipt` with `TransactionPosition::current()` and the projections of `AffectedProjections`. An empty plan, a mutation without a writer, a kind without a lock, two writers or locks for one class or kind, or an event about another version than the context's throws `Domain\UncommittableChangeset`. The registries are `Domain\MutationWriters` and `Domain\VersionLocks`, built from the container tags `MutationWriters::TAG` and `VersionLocks::TAG`: a command task tags its writers and locks; the core tags `Identity\Adapter\PostgresActorVersionLock`, which locks through the SECURITY DEFINER lookup `cms_identity_lock_actor(uuid, boolean)` (FOR SHARE, or FOR NO KEY UPDATE for a change) because the app role reads no identity row. The migration `*_add_commit_locks_and_audit_variants.php` adds that function and lets `audit.aggregates` hold a variant's key `variant:<uuid>:<variant>`. The tests run the real pipeline with the test-only command `tally.add` and its writer, lock and scratch table `tally_counters` (`packages/core/tests/Pipeline/Tally`, `TallyWorld`): `packages/core/tests/Postgres/PostgresChangesetCommitterTest.php` (all or nothing across changeset, audit, events, idempotency record and receipt, `partition_missing`, `version_conflict`) and `tests/Postgres/WalkingSkeleton/IdempotentRepeatsTest.php`. The reads are locked in runs of one kind and strength, which the key order groups because a key starts with its kind: the advisory locks of a run's absent aggregates in one statement (`PostgresChangesetCommitter::LOCK_ABSENT_ALL`), and its rows in one when the kind's lock is a `Domain\BatchVersionLock` (`lockAll()`; the entry, variant and node locks are). A run of mutations of one class that follow each other in the plan goes to a `Domain\BatchMutationWriter` at once (`writeAll()` of `Dto\PendingMutation`s; the four entry writers are one, their `write()` is `writeAll()` of one mutation, and `TypeRows` has `writeAll()` and `releaseAll()`), each event still held to its mutation's version; `packages/core/tests/Postgres/BatchCommitTest.php` covers the runs. `ChangesetCommitterBehaviour` (`packages/core/tests/Pipeline`) holds the action tests' `FakeChangesetCommitter` to it, with the tally: an empty plan and a plan that changes an unread aggregate are refused, a stale read (an absent aggregate created twice included) is `VersionConflict` with every stale read and commits nothing, the receipt lists the projections of the events, and an uncovered time throws `PartitionMissing`; the fake compares each read with the versions a test states with `at()` and the versions its own commits left.

## The wait after commit

The wait after commit (PRD 8.4, MILESTONES M1 point 5) is phase 8 of `CommandPipeline`: once the command transaction has committed, a committed call waits for its envelope's wait level through the action `Cbox\Cms\Core\Pipeline\Actions\AwaitWaitLevel` (`#[Internal]`), which reads the receipt from the `ReceiptStore` with a growing pause (2 ms up to 50 ms) on real time, the event runner's `Subscriptions\Domain\Pacing`, never the Clock, at most `cbox-cms.receipts.wait_budget_ms` (default 5000, 0 to 30000; `Pipeline\Domain\Dto\WaitSettings`, read by `Pipeline\Boundary\WaitConfig`). Whether a level is reached is `Pipeline\Domain\WaitLevelRule::reached()`, which `ReplayReceipt` uses too: commit at once, origin once the projection `WaitLevelRule::ORIGIN` (`InvalidateFragments::PROJECTION`) has acknowledged or when the receipt does not list it, and edge, verified and propagated once every projection the receipt lists has acknowledged, until the invalidation in full scale (M3) narrows them. A level not reached within the budget gives `committed_wait_timeout` with the statuses read last; the wait holds no transaction or lock, rejections and dry runs never wait, and a replay does not wait again. Test worlds pass the pipeline an `AwaitWaitLevel` with a budget of 0 unless a test waits: `PipelineWorld::$waitBudget` and `$pacing` (with `Tests\Pipeline\Fakes\MeanwhilePacing`), and `PublishingWorld`'s `waitBudget`. The walking skeleton is `tests/Postgres/WalkingSkeleton/PublishResolveReviseTest.php`: publish, `GET /v1/resolve` served from the fragment, and a revise at origin that returns once a real `cms:events:run` process has invalidated the fragment, or `committed_wait_timeout` without one.

## The query pipeline

The query pipeline (PRD 6.2 "Læsninger", GUARDRAILS 2.1) is the action `Cbox\Cms\Core\Reads\Actions\QueryPipeline`, called with a `QueryCall`: the query and the credential the transport carried, or null for the anonymous principal, and never an actor from the input. A `QueryAction` has `cost(Query): QueryCost` and `handle(Query): Result`; a result that carries entries' fields implements `Contracts\Pipeline\ReadsContent` with `Contracts\Results\ReadContent` entries (entry, node, type, fields). The whole read runs in one `QueryTransaction`, `ConnectionQueryTransaction` on the default connection (the primary, since a transaction reads from the write PDO), at REPEATABLE READ, committed only when answered, refusing to nest (`QueryTransactionOpen`), and its `position()` is the snapshot's xmin. In it the pipeline verifies the credential through the `CredentialVerifier` (a refused one is rejected with its code, an actor that is not active with `actor_not_active`), sets the actor context through the port `Access\Domain\AccessResolver` (`PostgresAccessResolver`; a `QueryCall` with a `ceiling` gets a context whose classification access is at most it), asks the `QueryAuthorizer`, bound to `Access\Adapter\PostgresQueryAuthorizer` (a `Contracts\Pipeline\PublicQuery`, such as `path.resolve`, for anyone; any other read only through a role whose permissions name it and that reaches some node; `QueryAuthorizerBehaviour` holds `FakeQueryAuthorizer::granting()` to it), checks the action's cost against `cbox-cms.queries.budgets.anonymous` or `.actor` (`query_over_budget`), runs `handle()`, strips a `ReadsContent` result's fields above the classification access or undeclared by the type (`Reads\Domain\ReadableFields`, from the `TypeCatalog`), writes the read audit of the sensitive fields left through the `ReadAudit` (`PostgresReadAudit`), and answers with a `Contracts\Results\QueryResult`: the result, the content keys `e-{entry}` and `n-{node}` each once and sorted, and the position; a rejection has only its catalog errors. The read audit is the core migration `*_create_read_audit_table.php`: `read_audit`, one row per audited entry of a read (read id, entry, actor, query and version, highest classification, field addresses, position), RANGE-partitioned per day on `read_id` and never dropped, with an insert policy for the context's actor only and no read policy. Routing a read to a replica by consistency token comes with the replicas (B4, B5).

## Ports, fakes and action tests

The actions' ports that are not contracts (`PartitionMaintenance`, `AccessContexts`, `DeclarationScanner`, `RegistryCache`, `DoctorChecks`, `BlueprintSource`, `GeneratedOutput`, `SchemaFiles`, `SubscriptionLog`, `LaneSubscribers`, `Pacing`, `QueryActions`, `QueryTransaction`, `ReadAudit`, `AccessResolver`, `ReadModelStore`, `SeedReader`, `SeedTargets`, `OpenApiDocuments`, `PublicPlacements`, `HeldPermissions`) have hand-written fakes in `packages/<module>/tests/<Feature>/Fakes`, as the doctor's probes do, and no fakes in the testkit. Each fake is held to the real implementation by a behaviour trait `<Port>Behaviour` in `packages/<module>/tests/<Feature>`, which a test class per implementation uses, named `<Implementation><Port>BehaviourTest` or `Fake<Port>BehaviourTest`: each in the suite its implementation needs: `PostgresPartitionMaintenanceBehaviourTest` in `Postgres`, the rest next to the trait in `Unit`, because the ports are not contracts and `Contract` holds the contracts' shared suites. `vendor/bin/pest --filter=<Port>Behaviour` runs both. The action tests are the `Actions` suite, in `packages/<module>/tests/Actions` (`BuildRegistryTest`, `MaintainPartitionsTest`, `RunDoctorTest`, `GenerateCodeTest`, `WriteEditorLinesTest`): each calls its action directly with its DTOs and these fakes (GUARDRAILS 9) and covers success, rejection and, where the action has one, the conflict. An action takes DTOs from its feature's `Domain\Dto`, never primitives: `MaintainPartitions::cover(PartitionRange)`, `RunDoctor::run(DoctorRunOptions)`, `BuildRegistry::build(ScanRoots)` and `WriteEditorLines::write(EditorTarget)`; a cli command builds them in a Boundary (`Cli\Boundary\PartitionRangeOptions`, `Cli\Boundary\DoctorOptions`, the core's `Registry\Boundary\ProviderScanRoots`). `DoctorChecks` is the port, and `OrderedDoctorChecks` the list `CoreServiceProvider` builds.
