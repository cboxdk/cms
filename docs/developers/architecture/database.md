# Migrations, tables and partitions

Migrations run as the owner role, every kernel table is described here, and the partition manager keeps the range partitions ahead of the clock and the sequences.

## Migrations and the kernel tables

Migrations live in `packages/<module>/database/migrations`, run as the owner role and may use raw SQL. A migration whose table needs less than the owner's default privileges (SELECT, INSERT, UPDATE and DELETE for the app role) narrows them with `Cbox\Cms\Core\Database\Infrastructure\TablePrivileges::limitTo()`, which takes a list of the enum `Cbox\Cms\Core\Database\Domain\TablePrivilege`, applies to every partition below the table and names no role. It only takes privileges away: every role with grants on the table, PUBLIC included, keeps the privileges in the list it already holds, with their grant option, and gains none, and the partitions below then get the table's grants with `TablePrivileges::copy()`, which copies the column grants too. A table whose rows change only in some columns narrows UPDATE to them with `TablePrivileges::limitColumns($table, TablePrivilege::Update, $columns)`: every role with the privilege on the whole table, PUBLIC included, gets it on those columns alone, with its grant option, and so cannot rewrite a key or move a row to another partition. The receipt tables give the app role SELECT and INSERT on `receipts` and SELECT and INSERT on `receipt_projections` with UPDATE of `state` and `acknowledged_at` alone, and `idempotency_keys` gives it SELECT and INSERT; the identity tables give it SELECT alone. The migration `*_create_ltree_extension.php` creates ltree as the owner role; ltree is a trusted extension, so the owner needs only CREATE on the database, which it has as the owner of the database that `docker/postgres/sql/database.sql` and the testkit's `TestDatabaseSetup` create. The structure and entry tables of `*_create_structure_and_entry_tables.php` (PRD 4.1, 5.2 to 5.9) are `nodes` (one tree for every site; `path` is an ltree of the ids of the node's ancestors and its own as 32 hex digits, with a GiST index), `sites` with their root node, `site_locales`, `node_routes` (primary key (site, locale, route) for the longest-prefix lookup, and a foreign key to `site_locales`, so a route carries a locale of its site), `entries` (type, home node, owner actor, lifecycle, version) and `variant_heads` (one per entry and variant, `shared` or a locale, with fillfactor 80); their forced row level security holds the access migration's policies (see [access](access.md)), and they give the app role SELECT, INSERT and UPDATE. The placement tables of `*_create_placement_and_mount_tables.php` (PRD 4.1, 5.7 to 5.9) are `placements` (the stable identity: the entry and a version), `placement_generations` (one row per placement and stage, `released`, `draft` or `staged`, with the node the placement sits under) and `placement_locales` (per placement, stage and locale: slug, visibility `hidden`, `scheduled`, `live`, `expired` or `withdrawn`, `live_from`, `live_until`, `next_transition_at` and `canonical`; the entry and the node are repeated there, held by composite foreign keys, the node with ON UPDATE CASCADE, so the partial unique indexes `placement_locales_slug_key` on (node, locale, slug, stage) where not withdrawn and `placement_locales_canonical_key` on (entry, locale, stage) where canonical enforce invariants 15 and 14 per stage), all three with fillfactor 80; a mount is a node of kind `mount` with `mount_source_id`, and `mount_overrides` (per mount node and entry, `hidden` and an optional `priority_cap`) references `nodes (id, mount_source_id)`, so only a mount node takes one. They have forced row level security with the access migration's policies too (none yet on `mount_overrides`), and give the app role SELECT, INSERT and UPDATE, with DELETE on all but `placements`. `packages/core/tests/Postgres/StorageSchemaTest.php` reads them from the catalog. The changeset, revision, head snapshot and release log tables of `*_create_revision_and_changeset_tables.php` (PRD 4.1, 5.4 to 5.6, 6.1) are `changeset_register` (the narrow, unpartitioned register, primary key changeset_id and the retention class, so a changeset is unique across retention classes; the target of the foreign keys that name a changeset), `changesets` (the metadata: command and version, actor, issuer kind, surface, reason code, idempotency key, correlation id, provenance, format version and the commit position `xid`, an xid8 whose default is `pg_current_xact_id()`) and `changeset_principals` (the on-behalf-of chain in order), both RANGE-partitioned per day on changeset_id and never dropped, `changeset_reason_texts` (the reason's free text with its classification, classified content kept apart from the metadata), `revisions` (the unpartitioned key register, revision_id from `revisions_revision_id_seq`, unique (entry_id, variant, rev_no), the target of `variant_heads`' draft and published revision and of the release log), `revision_payloads` (LIST-partitioned on kind, then RANGE on revision_id, managed as `revision_payloads_draft` and `revision_payloads_published` with a width of ten million ids, never dropped, and no foreign key), `head_snapshots` (one per variant head of a type with history audit-only or none, fillfactor 80) and `release_log` (each release and withdrawal with its effective time and changeset); every one has forced row level security with the access migration's policies, and the app role keeps SELECT and INSERT, with UPDATE on `head_snapshots` alone. `packages/core/tests/Postgres/RevisionStorageSchemaTest.php` reads them from the catalog. The trigger `receipt_projections_acknowledged` refuses every update of an acknowledged projection row with SQLSTATE 23000, for every role, so an acknowledgement is final in the database too. Every foreign key has a non-partial index that leads with its columns (PRD 4.1); `tests/Postgres/ForeignKeyIndexTest.php` checks the whole schema.

## Range partitions on time

Range partitions are kept by the partition manager in `Cbox\Cms\Core\Partitions` (PRD 4, 4.2). A partitioned table is listed in `cbox-cms.database.partitions.tables` with its key (`uuid7`: bounds are `Uuid7::lowestAt()` of the span's first millisecond and of the next span's; or `timestamp`), its interval (`day` or `month`, spans start at midnight UTC) and `retention_days` (null keeps all). Partitions are named `<table>_p<YYYYMMDD>` or `<table>_p<YYYYMM>`, and only those names are managed. There is no DEFAULT partition, so a write outside the partitions fails; an adapter that writes to a partitioned table catches the `QueryException` and throws `MissingPartitionMapper::map()`, which turns SQLSTATE 23514 "no partition of relation" into `Cbox\Cms\Contracts\Storage\PartitionMissing` (`CODE` `partition_missing`). `cms:partitions:maintain` (scheduled hourly by `CoreServiceProvider` in a process where the owner connection is configured, `CoreServiceProvider::ownerConnectionConfigured()`) runs the action `MaintainPartitions` at the Clock's time: it creates partitions from now to `runway_days` ahead (default 14) and removes partitions past retention with `DETACH PARTITION CONCURRENTLY` and `DROP TABLE`, never `DELETE`. Because autovacuum never analyzes a partitioned table (PRD 4.2), a maintain run then runs `ANALYZE` on the root of each partition tree whose partitions it changed (`pg_partition_root()`, so `receipts` for `receipts_standard` and `receipts_evidence`), once per root, as step `DdlStep::Analyze` under the same lock timeout and retry, and names the roots in `PartitionReport::$analyzed` (the command prints `analyzed <root>`); `ANALYZE ONLY` is Postgres 18 and not used, and `--from` and `--to` analyze nothing. A new partition gets its parent's row security flags and its parent's grants (`TablePrivileges::copy()`), so the owner's default privileges never reach a partition. A table with a managed name that is not a partition (detached by hand, or by a run whose Clock was ahead) and not past retention is attached again when a run needs its span (`PartitionChangeKind::Reattached`, step `DdlStep::Attach`, with the parent's row security and grants), and one left pending detach is finalized first; when Postgres refuses the attach (other columns or constraints, rows outside the span) the create phase of that table stops there with `UnmanageableTable::detachedPartition()` naming the table. It runs only on `cbox-cms.database.owner_connection` and throws `OwnerConnectionRequired` on the app connection. Every step runs with `lock_timeout` 2 s and a bounded retry with backoff, and gives up with `LockTimeout`. A run creates the partitions of every table before it retires any, and a step that gives up on one table's lock ends that phase for that table only: the `LockTimeout` goes in `PartitionReport::$gaveUp` as a `Domain\Dto\GaveUpStep` (its step, table, partition, attempts, message and the message of its cause, no exception) and the run goes on with the other tables; only a busy maintenance lock is thrown. An `UnmanageableTable` (`CODE` `partition_table_unmanageable`) also stops its table only: a table that is missing, not partitioned by range or has a DEFAULT partition gets no phase and no runway, a refused attach ends that table's create phase, and any other step on a partition that Postgres refuses for another reason than a lock wait (a DROP that a view on the partition blocks, a CREATE of a managed name that a view or a partition of another parent holds) ends that phase of that table as `UnmanageableTable::stepRefused()`; it goes in `PartitionReport::$failed` as a `Domain\Dto\FailedTable` (table, partition, message and the message of its cause) and the run goes on, so a table listed before its migration has run never stops the runway of the others. Only `UnmanageableTable::inTransaction()` is thrown. The command answers through the cli's `Boundary\PartitionReportOutput` (a `CliAnswer`, exit codes from the error catalog): it prints the report, then each step that gave up and each table that failed on standard error, and exits with the exit code of `partition_table_unmanageable` (78) when a table failed, else of `partition_lock_timeout` (75) when anything gave up, and 64 for invalid --from and --to. The doctor's `partitions.runway` fails with `doctor_partition_table_unmanageable` for such a table and still gives the runway of the others. `--from` and `--to` only create the partitions of a range. A run's report gives each table's runway from the Clock's time, with or without `--from` and `--to`: the end of the unbroken run of attached partitions from the partition that holds now, so a gap ends it. `Partitions\Domain\PartitionRunway::end()` computes it for the report and for the doctor's `partitions.runway`. Tests that write to a partitioned table first call the testkit's `app(PartitionFixtures::class)->cover($from, $to)` or `coverClock($clock, $interval)` for the dates they write at.

## Partitions on a sequence

Tables partitioned on a `bigint` that a sequence feeds (PRD 4.1, 7.2: `revision_payloads` on `revision_id`, `events` on `event_id`) are listed in `cbox-cms.database.partitions.tables` with the key `bigint`, no interval, `width` (ids per partition), `sequence` (unqualified, in the search path) and optionally `retention_days` with `retention_column`, a timestamptz column (both or neither). `Boundary\PartitionConfig` puts them in `PartitionPolicy::$sequenceTables` as `Domain\SequencePartitionedTable`s (retention a `Domain\SequenceRetention`), apart from the tables on time in `$tables`; a name is unique across both, and the manager, its report and the doctor take the tables on time first. A partition holds `width` ids from a multiple of `width` and is named `<table>_p<lower bound zero-padded to 19 digits>` (`SequencePartitionedTable::BOUND_DIGITS`), and only those names are managed; the last one ends at `PHP_INT_MAX`, and an id below 0 has none. The runway is counted in empty partitions ahead of the sequence's current value, `last_value` less 1 when `is_called` is false (`PartitionCatalog::sequenceValue()`): a run creates the partition that holds the current value and `partitions.runway_partitions` (default 2, 1 to 100) partitions whose lower bound is above it (`SequencePartitionedTable::runway()`), and a cover run (`--from`, `--to`) creates that runway too. `PartitionCatalog::table()` also checks the sequence (it exists, increment at least 1 and minimum at least 0, the role may SELECT it) and the retention column (a timestamptz column of the table), and throws `UnmanageableTable::sequenceMissing()`, `sequenceNotAscending()`, `sequenceUnreadable()` or `retentionColumn()`, so the table gets no phase. Retirement walks the managed partitions in id order and stops at the first it keeps: a partition is retired when the sequence has passed it (upper bound at most the current value, `SequencePartition::isPassed()`) and its newest `retention_column` value, read under step `DdlStep::Detach` with `row_security` off (`PartitionCatalog::newestRow()`), is at least `retention_days` old or the partition is empty (`SequencePartition::isExpiredAt()`), then DETACH CONCURRENTLY and DROP; a read that row security would filter is refused by Postgres and recorded as `UnmanageableTable::stepRefused()`, never taken as empty. A table with a LIST level above the range is listed once per leaf parent with the shared sequence, and its root is analyzed once. `PartitionRunway::ahead()` gives a `Domain\Dto\SequenceRunway` (current value, `coveredUntil` id or null, `partitionsAhead`) for `TableRunway::$sequence` and the doctor's `PartitionCoverage::$sequence`; the command prints `runway <table> until id <end> (<n> partitions ahead of id <current>)`, and `partitions.runway` fails when a table has fewer than `cbox-cms.doctor.partition_runway_partitions` (default 1) empty partitions ahead. The Postgres tests use the scratch tables `partition_scratch_seq` and `partition_scratch_kind` (LIST) of `PartitionScratch`, and `FakePartitionMaintenance` has `advanceSequence()` and `insertRow()`.
