# The generators

The type chain is generated from the blueprint files; no generated file is edited by hand, and gate 6 holds the committed output to the generators.

## The type chain

The type chain (PRD 11.12) is generated by `cms:generate`, the generators module's `Cli\Console\GenerateCommand`, which calls the action `Cbox\Cms\Generators\Generation\Actions\GenerateCode`. It reads the blueprint schema v1 (`packages/contracts/resources/schemas/blueprint.v1.json`) through the port `Schema\Domain\BlueprintSource`, bound to `Schema\Boundary\YamlBlueprintSource`: every `*.yaml` below the schema roots in `cbox-cms.generators.roots`, a map from owner to directory below `root` (the default is `['app' => 'schema']`), each file validated against the installed schema, and the owner taken from the root. The reader, `Schema\Boundary\BlueprintDocumentReader`, resolves the `type` of every field, the core's types included, in `Schema\Domain\FieldTypeRegistry` (GUARDRAILS 2.4): a `FieldType` has its name, its option keys and reads its options through the port `FieldValues` (implemented by `Schema\Boundary\DocumentValues`), and the options it returns (`FieldOptions`) carry the type's own rules (`problems()`, which `BlueprintRules` runs for every field) and its nested fields. The core registers its ten types through its own `FieldTypeContributor`, `Schema\Domain\FieldTypes\CoreFieldTypes`, and every addon that `schema.php` lists with field types registers them through the contributor its manifest names (PRD 13.3, `docs/addons/field-types.md`): `Schema\Boundary\RegisteredFieldTypes`, which `GeneratorsServiceProvider` builds the `FieldTypeRegistry` singleton with, reads the `CompiledRegistry`, makes each `Cbox\Cms\Contracts\FieldTypes\FieldTypeContributor` through the container and registers its `FieldTypeContribution`s as `Schema\Domain\FieldTypes\AddonFieldTypes` in the addon's namespace, and stops with `generate_invalid_config` (exit 78) when the registry cannot be read, a contributor cannot be made, does not implement the contract or returns other field types than the manifest lists, or an options schema cannot be used; `GenerateCommand` makes `GenerateCode` inside its error handling for that reason. A `<namespace>:<handle>` of a namespace no addon registers still fails with `generate_unknown_field_type`. A contribution names its options schema, an absolute JSON Schema file that `Schema\Boundary\OptionsSchemas` checks a field's `options` against (`generate_schema_invalid` at each JSON pointer), and gives a `FieldShape` of the options (one of the contracts' eight shapes, one per `FieldBase`), which `Schema\Domain\FieldTypes\ShapeOptions` turns into the core options of the base, held as `Schema\Domain\Dto\ShapedOptions`; the descriptor's `FieldDescriptor::$base` is that core field type, every generator writes the field by its base and names it by its type, and the generated `FieldDefinition` carries `base`, whose `valueType()` the kernel's `TypeTableColumns` reads and writes by. `GeneratorCoverageTest` holds every `FieldBase` to a core field type that every generator maps. A contributor's `owner()` is the module or addon whose name is its namespace, or null for `CoreFieldTypes` alone: the registry takes bare handles only from `CoreFieldTypes` and `<namespace>:<handle>` from every other contributor only in its own namespace, never `app` or `ext` (PRD 11.12, 13.1), and throws `InvalidFieldTypeName` otherwise, as it throws `DuplicateFieldType` for a name registered twice; `blueprint.v1.json` refuses `app:` and `ext:` too; `GeneratorCoverageTest` holds the core's types to the schema's enum. A missing root exits 66; an existing root without `*.yaml` files is valid and gives a PHP enum without cases and `type TypeHandle = never`. The reader's `Schema\Domain\BlueprintRules` checks the rules across files, each with its own code (exit 65), such as `generate_duplicate_type_id`, `generate_duplicate_type_handle` (one owner), `generate_duplicate_field_handle`, `generate_unknown_extends_target`, `generate_extension_of_own_type` (an owner extending its own type), `generate_extension_version_mismatch` (two extension files of one owner for one type with different versions), `generate_column_name_too_long` and `generate_too_many_fields` (a type with more than 200 top-level fields, its own and its extensions' together, PRD 11.6; `Schema\Domain\TypeFieldLimit`). `Generation\Domain\SchemaResolver` then applies each extension to the type whose `type_id` it extends; it refuses what BlueprintRules refuses with the same codes, because it takes any blueprints. Two owners may each have a type with the same handle (PRD 11.2, 11.12 point 2, 13.3): the generated code names a type by its owner and handle, `ResolvedType::name()`, `<owner>:<handle>` such as `app:fixture_article`, so a module release that adds a type the app already has changes none of the app's names. `Descriptor\Domain\DescriptorCompiler` then compiles each resolved type into a `Descriptor\Domain\Dto\TypeDescriptor` (PRD 11.2, 11.12), and every generator reads the descriptors of the `CompiledSchema`, never a blueprint. A descriptor holds the type's id, owner, handle, owner's version, the version of each extender's namespace (`Generation\Domain\Dto\ExtensionVersion`, which the resolver collects), its capabilities and its top-level fields sorted by column; a `FieldDescriptor` holds the column (the handle, or `ext__<namespace>__<handle>`, refused over 63 bytes with `generate_column_name_too_long`; none inside a group), the Postgres type, NOT NULL and CHECK expressions over the quoted column, the PHP type (native, PHPDoc, nullable), the TypeScript type, the runtime validator's rules (`Descriptor\Domain\ValidationRuleName`, `required` or `nullable` first), the classification, `agents`, `filterable`, `sortable`, whether it is encrypted, the choices of a select and the nested fields of a group, sorted by handle. Each field type describes its own column and value through `FieldOptions::describeColumn()` and `describeValue()`, so an addon's field type compiles like the core's. A confidential field is encrypted (PRD 12.2): `bytea` without checks. An owner's required field is NOT NULL and not nullable; an extension field never is, because its `required` is enforced at publication (PRD 11.12 point 1). `Descriptor\Boundary\TypeDescriptorJson::encode()` gives the canonical JSON: sorted keys, every key present, four-space pretty print, one trailing newline, no source locations. The comprehensive example type (MILESTONES M1 point 1) is a generator fixture, `packages/generators/tests/Descriptor/Fixtures/Comprehensive`: the type `product` of the module `shop`, with all ten core field types, select options, a group once and repeated, required, filterable and sortable fields, every classification and both agents flags, extended by `app`; `TypeDescriptorTest` compares its descriptor with the committed golden file `descriptor.json` there, which is changed by hand only when a change to the descriptor is intended. The workbench's schema roots are `workbench/schema` (owner `app`) and the fixture addon's `workbench/addons/fixtureaddon/schema` (owner `fixtureaddon`), both set by `WorkbenchServiceProvider`. The first has two blueprint v1 files: `fixture_article.yaml`, the type `fixture_article` (history `full`, stages `draft-release`, routable, version 2) with the fields `fixture_title`, `fixture_slug` and `fixture_body` among others, which the addon extends with `ext.fixtureaddon.fixture_slug`, and `fixture_measurement.yaml`, the type `fixture_measurement` (history `none`, stages `none`, not routable) with other fields, all prefixed `fixture_`. The M0 generators write a PHP enum `TypeHandle` with `fields()` and `extensionFields()` to `workbench/app/Cms/Generated` and the TypeScript union `TypeHandle` with `TypeFields` to `workbench/resources/js/cms/generated/index.ts`; both are committed and never edited by hand. An enum case is the owner and the handle in TitleCase with the name as its value (`AppFixtureArticle = 'app:fixture_article'`), and the union's members and the keys of `TypeFields` are the names; `generate_invalid_case_name` refuses two types of one owner that give the same case, such as `item_2` and `item2`. They map the owner's fields by handle to their field types and put extension fields under their namespace, as the code addresses them (`ext.app.tax_code`): `fields()` holds the owner's fields and `extensionFields()` namespace to handle to field type, and each `TypeFields` entry has the owner's fields and, when the type is extended, `ext: { <namespace>: { <handle>: ... } }`. The column name `ext__<namespace>__<handle>` belongs to the type table only and never appears in generated code. Each generator maps every core field type and every kind of the installed `blueprint.v1.json` in its `FIELD_TYPES` and `KINDS`, and `packages/generators/tests/Generation/GeneratorCoverageTest.php` fails when the schema has a value a generator does not map, or a generator maps a value the schema does not have. A generator implements `Cbox\Cms\Generators\Generation\Domain\Generator` (`#[Internal]`, not a contract, so no fake), is a pure function of the compiled schema and the target, and owns a directory named `Generated` or `generated`: the `GeneratorRunner` sorts the output, and cms:generate writes only files whose bytes differ and removes the other files in the owned directories. Output is sorted and has no timestamps or absolute paths. Errors carry a code from `GenerateErrorCode`, such as `generate_schema_invalid`, and the command exits 65 for an invalid schema or one that needs a newer `cboxdk/cms` (`generate_schema_unsupported_version`), 66 for a missing schema root or file, 70 for invalid generator output, 73 when a file cannot be written and 78 for invalid configuration. Gate 6 is `composer check:generated`: it fails on unstaged changes or untracked files under the generated paths (the workbench's and `packages/core/src/Codecs/Boundary/Generated`), runs cms:generate and `composer generate:protocol`, and checks again. The generators need symfony/yaml and opis/json-schema (blueprint decision 5), which `cboxdk/cms` suggests and requires for development only (GUARDRAILS 2.6); `YamlBlueprintSource::read()` first checks them with `Schema\Boundary\SuggestedPackages` and fails with `generate_invalid_config` naming each missing package. `tests/Arch/ModulesTest.php` fails when the generators' src uses a package `composer.json` neither requires nor suggests.

## The PHP records and the type catalog

The PHP records and the type catalog (PRD 11.12 point 4, GUARDRAILS 2.4) are written by two more generators, `Generation\Domain\Generators\PhpRecords` and `PhpTypeCatalog`, into the PHP directory (`workbench/app/Cms/Generated` in the workbench). `PhpRecords` writes a directory per type, `Records/<Case>` named by its `TypeHandle` case, in the namespace `<php_namespace>\Records\<Case>`: the owner's interface `<Case>Record` (a get-only property per owner's field in camelCase, PHP 8.4 property hooks, and `toFieldValues()`), the factory interface `<Case>RecordFactory`, per extender's namespace `<Case><Ns>Extension` (property `ext`), `<Case><Ns>Ext` (property `<ns>`) and the final readonly class `<Case><Ns>Fields`, the composite record `<Case>` that implements the owner's interface and every extender's with `<Case>Ext`, its factory `<Case>Factory`, a string-backed enum `<Field>Choice` per select field, and a class `<Field>Group` per group or `<Field>Item` per item of a repeated group (a nested field's name starts with its group's, an extension field's with its namespace in TitleCase). A record converts to and from the kernel's generic `Cbox\Cms\Contracts\Fields\FieldValues` with `fromFieldValues()` and `toFieldValues()` through the contracts' `FieldReader` (`text()` and `textOrNull()` and so on per field type, `InvalidFieldValue` with the field's path for a missing required value, a wrong kind or an unknown option) and `FieldWriter`; rich text is the kernel's `ListValue`. Two fields, options or namespaces of one type that give the same PHP name without case, and a field `this` or an option `class`, fail with `generate_name_collision` (exit 65). `PhpTypeCatalog` writes `GeneratedTypeCatalog`, which implements the contract `Cbox\Cms\Contracts\Schema\TypeCatalog` (`all()`, `find(TypeId)`, `named(TypeName)`) with a `TypeDefinition` per type: id, `TypeName` `<owner>:<handle>`, the owner's version, an `ExtensionVersion` per namespace, `TypeCapabilities` (`History`, `Stages`, `Localization`, routable) and a `FieldDefinition` per top-level field (namespace, handle, field type, `ClassificationAccess`, agents, encrypted, required, filterable, sortable, `ColumnDefinition` and nested fields); these contract types refuse contradictions with `InvalidTypeDefinition`. It also writes `GeneratedTypeValidators`, which implements the contract `Cbox\Cms\Contracts\Validation\TypeValidators` (`all()` sorted by type id, `find(TypeId)`) with the generated validator of every type, and `GeneratedTypesServiceProvider`, which binds `TypeCatalog` to the catalog, `TypeValidators` to the validators and each `<Case>RecordFactory` to `<Case>Factory`; `TypeCatalog` has no entry in `cbox-cms.contracts`, because the kernel cannot name the application's class, and `WorkbenchServiceProvider` registers the provider, as an application does. `PhpTypeCatalog` takes the class the provider extends from `GeneratorsServiceProvider`, because the domain does not use the framework. The generated code uses only the public API of `cboxdk/cms` and passes PHPStan level 10, Rector and Pint unchanged. The testkit has `Schema\FakeTypeCatalog` and the shared suite `Schema\TypeCatalogContract`, run against the fake, the workbench's catalog from the container and the comprehensive example's golden catalog (`vendor/bin/pest --testsuite=Contract --filter=TypeCatalog`), and `Validation\FakeTypeValidators` with the shared suite `Validation\TypeValidatorsContract`, run against the fake and the workbench's validators (`--filter=TypeValidators`; documented in `docs/addons/validation.md`). The comprehensive example's generated PHP is committed as golden files in `packages/generators/tests/Descriptor/Fixtures/Comprehensive/Generated` (namespace `Cbox\Cms\Generators\Tests\Descriptor\Fixtures\Comprehensive\Generated`); `packages/generators/tests/Records/PhpRecordsTest.php` compares them with what the generators write, and `RecordRoundTripTest.php` round-trips its record through the generic field values for every field type. The contract is documented in `docs/addons/contracts/type-catalog.md`.

## The typed query builders

The typed query builders (PRD 8.8, 11.12, 5.10) are written by cms:generate's `Generation\Domain\Generators\PhpTypeQueries` into `QueryBuilders/<Case>` below the PHP directory (`workbench/app/Cms/Generated/QueryBuilders`): per type the enums `<Case>FilterField` and `<Case>SortField` of the owner's filterable and sortable fields, valued by column, and the final readonly builder `<Case>Query` (`where()` with a filter field, a `FilterOperator` and field values, a typed `where<Field>()` per filterable field, `orderBy()`, `after()`, `limit()` and `page(AccessContext): RecordPage<<Case>Record>`), which hydrates through the owner's record factory. A wrong field is a type error (`packages/generators/tests/QueryBuilders/QueryBuilderTypeErrorsTest.php`); the builder knows the owner's fields only; a filterable or sortable `select` with `multiple: true` is refused with `generate_field_not_queryable`. The builder runs on the contract `Cbox\Cms\Contracts\TypeTables\TypeTableReader` (`page(TypeTableQuery, AccessContext): TypeTablePage`), bound to `Cbox\Cms\Core\TypeTables\Adapter\PostgresTypeTableReader` in `cbox-cms.contracts`: the released rows of the variant, filters only on filterable and order only on sortable fields (else `InvalidTypeTableQuery`), keyset pagination with the entry id as the last key and null as the greatest value, and always the explicit access predicate as bound parameters, `cms_owner_actor` equal to the actor or `cms_home_node` in the nodes the regions reach when they are at most `REGION_NODE_LIMIT` (100), else a left join to `nodes` with `path <@` each region; two queries a page, whatever the number of matching rows. Each row's fields are those the context may read, `TypeDefinition::readable()` (the rule `Reads\Domain\ReadableFields::strip()` applies too: nothing above the classification access, nothing the type does not declare, and for an agent nothing closed to agents), a filter or order on a field the context may not read is `InvalidTypeTableQuery` (`TypeTableQuery::assertReadableBy()`), and a page that gives an actor a sensitive field writes the read audit through `ReadAudit` under `type_tables.page` version 1 (`packages/core/tests/Postgres/TypeTableReadAuditTest.php`). It runs inside the caller's read transaction with the actor context set and uses the query builder only. `Core\TypeTables\Boundary\TypeTableColumns` is the column form of every core field type, `decode()` of a row and `encode()` of field values (a group and rich text as jsonb, a multiple select as `text[]`, an encrypted field left out). The testkit has `FakeTypeTableReader` and the shared suite `TypeTableReaderContract`, run by `packages/testkit/tests/Contract/FakeTypeTableReaderContractTest.php` and, on Postgres, by `packages/core/tests/Contract/PostgresTypeTableReaderContractTest.php` and `PostgresJoinedTypeTableReaderContractTest.php` through `packages/core/tests/TypeTables/PostgresTypeTables`; `tests/Postgres/TypeTables/WorkbenchQueryBuildersTest.php` runs the workbench's builders. Docs: `docs/addons/contracts/type-table-reader.md`.

## The record DTOs and JSON codecs

The record DTOs and JSON codecs (PRD 8.9, GUARDRAILS 2.2) are generated by cms:generate's `Generation\Domain\Generators\PhpRecordDtos` from the type descriptors: for each type and the record contract version 1, a final readonly DTO per object in `<php_directory>/Domain/Dto` (`<Owner><Handle>V1`, a group adds its handle in TitleCase, the extension fields sit under `ext` with a class per namespace, `<Root>Ext<Namespace>`) and a codec `<Owner><Handle>CodecV1` in `<php_directory>/Boundary` that implements the contract `Cbox\Cms\Contracts\Codecs\JsonCodec` (`encode(object $dto, ClassificationAccess $access): string`, `decode(string $json, ClassificationAccess $access): object`, typed by `@implements JsonCodec<Dto>`). `Dto` sits below `Domain` because of the category rule, and the codec in `Boundary` because it reads `mixed`. The model the emitters take lives in the generators' feature `Codec` (`Domain\Dto\CodecContract`, `CodecObject`, `CodecProperty`, `CodecValue` of a `CodecKind`), so another generator, such as one for receipts, emits its DTOs and codec with `PhpDtoEmitter` and `PhpCodecEmitter`; `RecordContracts` maps a descriptor into it, and `CodecKind::rules()` lists the rules each kind takes, refusing any other. The JSON form is fixed at run time by the core's `Codecs\Boundary\JsonText` (decode refuses a key twice, which `json_decode` would keep, a document that is not an object and more than 63 levels; encode writes no whitespace with slashes and Unicode unescaped) and `Codecs\Boundary\JsonValues` (`#[Experimental]`: one reader per kind with the blueprint's rules as named arguments, `required`, `nullable`, `requiredClassified` and `nullableClassified` for presence and classification, and the writers): keys sorted, the entry's id under `cms_id`, decimals as strings with the field's scale, dates `YYYY-MM-DD`, date-times read with any offset and written in UTC with six decimals, rich text checked by `Codecs\Domain\PortableText`. A field classified above the caller's `ClassificationAccess` (the AccessContext's) is left out of the encoding and refused in a document; the DTO's `visibleTo()` holds it as `Cbox\Cms\Contracts\Fields\Omitted`, the marker for a field a DTO leaves out, also for an optional field missing from a document, never `null`. Decoding throws `Codecs\Domain\DecodingFailed` with `json_malformed` (no path) or `json_invalid` and the `FieldPath` of the value; encoding a DTO with a value that has no form throws `EncodingFailed`. Two handles that give one PHP name are refused with `generate_name_collision`. The golden output of the comprehensive example is committed in `packages/generators/tests/Descriptor/Fixtures/Comprehensive/Generated` and held by `packages/generators/tests/Codec/RecordCodecGoldenTest.php`; the workbench's fixture types together use every core field type, and `tests/Codecs/WorkbenchRecordCodecsTest.php` round-trips them. The page is `docs/addons/codecs.md`.

## The runtime validators

The runtime validators (PRD 11.8, 11.12 "Hvor statiske typer slutter", MILESTONES M1 point 2) check input from outside the repository, a command's fields from the REST API, MCP, the CLI or a sidecar as JSON decodes them. The generator `Generation\Domain\Generators\PhpTypeValidators` writes one class per type to `Validators` below the PHP directory (`workbench/app/Cms/Generated/Validators`), named after the `TypeHandle` case (`AppFixtureMeasurementValidator`); it implements the contract shape `Cbox\Cms\Contracts\Validation\TypeValidator`, `type()` and `rules()`, and declares the descriptor's rules as `TypeRules`: the owner's `FieldRules` by handle, each extender's in an `ExtensionRules` under its namespace (the input's `ext.<namespace>`), a group's nested fields below it. The rules are `Contracts\Validation\RuleName`, the descriptor's vocabulary without `required` and `nullable`, which become the field's `Presence`: `Required`, `Optional`, or `RequiredOnRelease` for an extension field its blueprint marks required (PRD 11.12 point 1, invariant 36); a select of one choice gets `string` before its `in`, because a field's rules start with one type rule. `FieldRules`, `Rule` and `TypeRules` throw `InvalidRules` for rules that contradict themselves. The engine is `Cbox\Cms\Core\Validation\Boundary\InputValidator` (`#[Experimental]`): `validate(TypeRules, mixed, ValidationStage, ?FieldPath)` and `validateWith(TypeValidator, ...)` never throw for bad input and return a `Contracts\Validation\ValidationReport` of at most `MAX_ERRORS` (100) `CatalogError`s, each with the value's `FieldPath` and a per-rule code of the catalog (`validation_required`, `validation_wrong_type`, `validation_unknown_field`, `validation_too_long` and the others); a report with errors rejects the input as `validation_failed` (`code()`). `docs/addons/validation.md` documents it. The comprehensive example's validator is the golden file `packages/generators/tests/Descriptor/Fixtures/Comprehensive/Generated/Validators/ShopProductValidator.php` (`packages/generators/tests/Validators`), and `tests/Feature/Validation/WorkbenchValidatorsTest.php` feeds valid input and one invalid input per rule per field type through the workbench's validators; `fixture_measurement` has every core field type and every rule for it.

## cms:schema:editor

`cms:schema:editor` (blueprint decision 3, PRD 14.1), the generators module's `Cli\Console\SchemaEditorCommand`, which calls the action `Cbox\Cms\Generators\Editor\Actions\WriteEditorLines`, points editors at the blueprint schema: it gives every `*.yaml` file below the schema roots of `cbox-cms.generators.roots`, the files cms:generate reads (both find them with `Schema\Boundary\BlueprintFiles`), the first line `# yaml-language-server: $schema=<path>`. The path is relative from the file's directory to `packages/contracts/resources/schemas/blueprint.v1.json` in the installed `cboxdk/cms`, found through Composer's `InstalledVersions` by `Schema\Boundary\BlueprintSchemaFile::editorPath()`: in an application it resolves the directories above the package's install directory and keeps that directory as installed, so it goes through `vendor/cboxdk/cms`; where `cboxdk/cms` is the root package, as in this repository, a checkout and a worktree, it goes through the root, so the workbench's line is `../../packages/contracts/resources/schemas/blueprint.v1.json`. `Editor\Domain\EditorLine` owns the lines of the file's leading block (blank lines, comments, directives and `---`) that set yaml-language-server's `$schema`: a wrong one is replaced, never duplicated; every other byte, a byte order mark and the first line's CRLF or LF are kept, and a line after the leading block is never touched. It writes only files whose bytes change, all or nothing through a temporary file with the file's permissions, names each changed file, and a second run changes nothing. A file that fails does not stop the others. It skips every schema root whose directory below its base starts with the segment `vendor` (`SchemaRoot::belowVendor()`, compared without case), names it as `skipped:` and never lists, reads or writes its files, because Composer installs them; cms:generate still reads them. Exit codes, as cms:generate's: 0, 66 when a schema root or a file cannot be read, 73 when a file cannot be written (`generate_schema_unwritable`), 78 for invalid configuration or a missing blueprint schema. The files of `workbench/schema` are committed with the line, and `packages/generators/tests/WorkbenchFixtureTest.php` fails when one lacks it or cms:schema:editor would change it; run `vendor/bin/testbench cms:schema:editor` after adding a blueprint file.
