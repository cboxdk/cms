# The surfaces

Each surface builds the envelope and reads the document with the generated codecs, then hands the call to the shared core action; the surface contract tests run every exposed action through every surface.

## The REST surface

The REST surface (GUARDRAILS 2.1: JSON and problem details; PRD 6.1, 8.8) is `Cbox\Cms\Http\Rest`, compiled by `cms:build` from the registry. `RegistryCompiler` turns every action whose `#[Action]` lists `Surface::Rest` into a `Registry\Domain\Dto\RestRoute` (`RestRoute::of()`: a write is `POST /v1/commands/<name>/v<version>`, a read `GET /v1/queries/<name>/v<version>`, `RestMethod::of()` gives the method), kept in `CompiledRegistry::$rest` in the order of the actions and written to `rest.php` (`RegistryName::Rest`, entry keys `kind`, `method`, `name`, `path`, `version`; the codec refuses a method or path that is not the route's). `BuildRegistry` then describes the routes with the port `Registry\Domain\OpenApiDocuments` before it writes anything, writes the registry, and writes the document: `Registry\Adapter\FileOpenApiDocuments` takes each route's JSON Schemas from the codecs, a command's `CommandCodec` (`Pipeline\Domain\Dto`, which now carries the command's `Cbox\Cms\Contracts\Codecs\JsonSchema`) tagged `CommandCodecs::TAG` and a query's `Reads\Domain\Dto\QueryCodec` (the codec and schema of the query and of its result) tagged `QueryCodecs::TAG` (`cbox-cms.query-codecs`), fails the build with `registry_surface_without_codec` for a route without them, reads the kernel's `receipt.v1.json` and `problem.v1.json` from `packages/contracts/resources/schemas`, and writes `openapi.json` (OpenAPI 3.1.1, built by the Boundary `Registry\Boundary\OpenApiJson`: every object's keys sorted, pretty-printed, each schema a component with an `$id` of its own, `urn:cbox-cms:<component>`, so its `#/$defs/...` resolve inside it) next to the registry files through a temporary file and a rename; `FileRegistryCache` keeps `openapi.json` and its temporary file. An application registers the routes with `RestRoutes::register($router, $registry)`, each with the route defaults `RestRoutes::NAME` and `RestRoutes::VERSION` and named `cbox-cms.rest.<commands|queries>.<name>.v<version>`; the provider registers none itself, so no process reads the registry cache at boot. `RestCommandController` and `RestQueryController` hold no logic, and `tests/Arch/RestControllersTest.php` keeps them to actions, `Dto` classes, Boundary, the contracts' attributes and the framework's request and response, final readonly with only `__construct` and `__invoke`. `Boundary\RestRequest` reads a write's credential (`BearerCredential`), its envelope from the headers `Idempotency-Key` (required: `idempotency_key_required`), `Cbox-Wait-Level`, `Cbox-Dry-Run` and `Cbox-Correlation-Id` (`request_header_invalid`; the names are constants of `OpenApiJson`) through the generated `EnvelopeCodecV1`, and hands the body to `RunExposedCommand` with the route's codec; a read's query document comes from the query parameter `query` (`RestRoute::QUERY_PARAMETER`, `{}` when it is left out), read by the query's codec at public classification access, with its errors below `query`. `Boundary\RestResponse` answers 200 with the receipt for committed and `dry_run`, 202 for `committed_wait_timeout`, 200 with the result written by the query's result codec at `QueryResult::$access`, the principal's classification access the query pipeline now gives on the answer, and problem details (`application/problem+json`) with the first error's catalog code and status and every error, always with `Cache-Control: no-store, private`. `packages/http/tests/Rest/RestSurfaceTest.php` runs the test-only `probe.rename` and `probe.cards` through routes compiled from `packages/http/tests/Rest/Fixtures/Surface`, and `OpenApiDocumentTest.php` validates the written document against the OpenAPI 3.1 schema of `devizzent/cebe-php-openapi` (require-dev) with opis's `CompliantValidator`.

## The Inertia profile

The Inertia profile (GUARDRAILS 2.1: redirects, and errors in page props) is `Cbox\Cms\Http\Inertia`. `InertiaRoutes::register($router, $prefix)` adds `POST <prefix>/{command}/v{version}`, named `cbox-cms.inertia.command`, to the route group of the application's panel, behind `Inertia\Adapter\InertiaMiddleware` (Inertia's middleware, which also shares the prop `problem`). The body is `{"envelope": <envelope.v1.json>, "command": <the command's document>}`: `Boundary\InertiaDocument` splits it, `Boundary\InertiaRequest` reads the envelope with the generated `EnvelopeCodecV1` and the credential from the Bearer header (`Cbox\Cms\Http\Credentials\Boundary\BearerCredential`). The controller finds the command in `Domain\InertiaActions`, the write actions of the compiled registry that list `Surface::Inertia` (404 for any other), and runs the core action `Core\Pipeline\Actions\RunExposedCommand` with an `ExposedCall`, the part every exposed surface shares: it verifies the credential (a refused one rejects with the verifier's code, none is `unauthorized`), takes the on-behalf-of chain from the credential (an envelope that names another is `unauthorized`), gets the `AccessContext` from the port `Core\Access\Domain\AccessContexts` (bound to `TransactionalAccessContexts`: the `PostgresAccessResolver` in a transaction of its own, rolled back), reads the command with its generated codec from `Core\Pipeline\Domain\CommandCodecs` (the `CommandCodec`s tagged `CommandCodecs::TAG`, one per name and version) at the context's classification access, builds the `Envelope` (a person's session as `human`, an agent's credential as `agent`, a service's as `system`, the caller's correlation id or one from the `IdGenerator`) and runs the `CommandPipeline`. `Boundary\InertiaOutcome` answers every call with a 303 back to the form's page: the receipt (receipt.v1.json) in Inertia's flash data under `receipt` for every outcome, committed, `committed_wait_timeout`, `dry_run` and rejected, and for a rejection the field errors in the `errors` prop by their path in the body (`command.fields.label`, `envelope.wait_level`) and the problem details (problem.v1.json) with every catalog code as the prop `problem`. The panel and REST stay in parity (Sylvester, 29 September): `InertiaActions` throws `SurfaceParityBroken` for a registry with an action on Inertia and not on REST, and `tests/Feature/Surfaces/SurfaceParityTest.php` compiles the installation's registry from its scan roots and fails on one. `InertiaRoutes::queries($router, $component, $prefix)` adds `GET <prefix>/{query}/v{version}`, named `cbox-cms.inertia.query`, for the query actions that list `Surface::Inertia` (`InertiaActions::query()`): `InertiaQueryController` reads the query's document from the query parameter `query` as REST does (`Boundary\InertiaQueryRequest`, a refusal `InertiaQueryRefused` at its path below `query`), runs the `QueryPipeline` with `Surface::Inertia` and renders the route's page component (its default `InertiaRoutes::COMPONENT`) through `Boundary\InertiaQueryOutcome`: the result's document, as the result codec writes it at the read's access, in the prop `result`, or the problem details in the prop `problem`. The workbench's test page is `/workbench/inertia` (`Workbench/Commands`, rendered by `workbench/resources/views/app.blade.php`, with no server-side rendering and no page components until B1), with the profile's routes below it (reads render `Workbench/Query`); `packages/http/tests/Inertia/InertiaProfileTest.php` posts the test-only `probe.rename` there.

## The MCP surface

The MCP surface (GUARDRAILS 1, 2.1: MCP with tool errors; PRD 2.31, 12.2, 14.5, 22) is the module `Cbox\Cms\Mcp` in `packages/mcp`, a surface in the layer table and a module in `ModuleDependencies` (`tests/Arch/McpSurfaceTest.php`, `tests/Arch/ModulesTest.php`). `laravel/mcp`, pinned to the minor 1.0 (`~1.0.1`), is used only in `Mcp\Adapter`: `McpServer` (tools only) answers tools/list and tools/call with `ListToolsMethod` and `CallToolMethod`, which ask the port `Mcp\Domain\McpEndpoint`, implemented by the surface `Mcp\McpSurface`; an application serves it with `Mcp\Adapter\McpRoutes::register(app(Registrar::class), $path)`, `POST /mcp` by default, named `cbox-cms.mcp`, outside the web group (the workbench's `workbench/routes/api.php`). `Mcp\Domain\McpTools`, a singleton, holds one `Domain\Dto\McpTool` per action of the compiled registry that lists `Surface::Mcp`, compiled by `Boundary\ToolCompiler`: named by `Domain\ToolName` (`entry-create-v1`: dots as hyphens, `-v<version>`, at most 64 characters), with the input schema `{command, envelope}` for a write (the `CommandCodec`'s JSON Schema and envelope.v1.json, read by `Boundary\KernelSchemas`) and `{query}` for a read (the `QueryCodec`'s), each embedded with an `$id` of its own, and the title and description from the schema. An action whose command or query no codec reads is not offered and is listed in `McpTools::$undescribed` with the reason; the kernel's M1 commands have no codec yet. `Boundary\ToolInput` reads a call: an unknown tool is JSON-RPC -32602, the arguments are split by `Boundary\ToolArguments` and read by the generated codecs (refusals `json_invalid` at `command.<...>`, `envelope.<...>` or `query.<...>`), and the credential is the request's Bearer token, taken with the arguments' JSON text from the raw body, because laravel/mcp decodes `{}` into `[]`. A write runs `RunExposedCommand` with `Surface::Mcp`, a read the `QueryPipeline` with `QueryCall(..., Surface::Mcp)`; both refuse a credential not issued for an agent as `unauthorized` (`Surface::requiresAgent()`). For every read by an agent's credential, through any surface, `ReadableFields::strip(..., agent: true)` also leaves out every field whose `FieldDefinition::$agents` is false, nested group fields included, so public and internal fields reach agents unless the blueprint says `agents: false`, confidential ones only with `agents: true`, and personal and sensitive ones never; an agent's ceiling is at most confidential (`IssuerKind::maximumCeiling()`). `Boundary\ToolOutput` answers with a tool result of the receipt or the result (the query's result codec at the reader's access), and a rejection by its first error's `McpResponse`: a tool error with the problem details, or JSON-RPC -32603 with them as data. `packages/mcp/tests/McpSurfaceTest.php` runs the test-only `probe.rename` and `probe.agent_cards` over HTTP; `WorkbenchToolsTest.php` lists the workbench's tools.

## The CLI surface

The CLI surface (GUARDRAILS 2.1: exit codes from the error catalog) is one generic command, `cms:run <name> <version> <document>` (the cli's `Console\RunCommand`), which runs every write action whose `#[Action]` lists `Surface::Cli`: `Cli\Domain\CliActions`, bound once per process from the compiled registry, holds them by name and version, and any other name or version exits 64 and lists `signatures()`. `Cli\Boundary\ExposedCommandInput` reads the call into an `ExposedCall`: the options `--idempotency-key`, `--dry-run` and `--wait-level` are written as envelope.v1.json and read through the generated `EnvelopeCodecV1` (a refused value is `json_invalid` at `envelope.<field>`), the codec comes from `CommandCodecs`, and the credential is the process's configured service credential, `cbox-cms.cli.credential` (`Cli\Boundary\CliCredential`; null is none, and the write is `unauthorized`), never an argument or an option. The command runs the shared core action `RunExposedCommand`, and `Cli\Boundary\ExposedCommandOutput` gives the `Cli\Domain\Dto\CliAnswer`: exit 0 for committed and `committed_wait_timeout`, the catalog's exit code of `dry_run` for a dry run and of the first error for a rejection (65 for validation, JSON and version conflicts, 77 for `unauthorized` and refused credentials), and with `--json` one line of receipt.v1.json or problem.v1.json on standard output. A refusal before the kernel runs is `Cli\Domain\CliCallRefused`: a catalog code (registry cache, envelope options) or a usage error (64), an invalid setting (78) or an exposed command without a codec (70). `tests/Arch/CliSurfaceTest.php` holds `RunCommand` to actions, DTOs and Boundary; `packages/cli/tests/Console/RunCommandTest.php` runs the test-only `probe.rename` through it.

## The surface contract tests

The surface contract tests (GUARDRAILS 2.1, 9: one per action and surface; MILESTONES M1 point 6) are `tests/Feature/Surfaces/SurfaceContractTest.php`, in the Unit suite (`vendor/bin/pest --filter=SurfaceContract`). Its data set is built from the installation's registry, compiled from the providers' scan roots as cms:build compiles it in an application booted for the data set (`SurfaceContractCases::booted()`, because PHPUnit resolves a data set before any test sets up), with one `SurfaceContractCase` per write action and surface its `#[Action]` lists, so a new action gets its surface tests from its `#[Action]` alone: 28 in M1, the seven exposed commands on REST, Inertia, MCP and the CLI, and none for `actor.deactivate`, which lists no surface. Each case sends every `Scenario` through the surface's own transport: a document its generated codec refuses (the first required property left out, `json_invalid` at its path), a field error from validation (`validation_required` at `fields.label`), a version conflict, a dry run and a receipt committed without reaching wait level origin (`committed_wait_timeout`). The document is the smallest one the command's JSON Schema accepts (`SampleDocument`, from the schema alone, with strings for a pattern from its `CANDIDATES`). Below the surface run the real `RunExposedCommand` and `CommandPipeline` over the `ExposedWorld`'s fakes (`ContractKernel`): every command of the registry is bound to `ContractAction`, which plans a probe.rename for any command and reads what the command expects at the expected versions, and each scenario sets the plan's fields and the committer (`ContractCommitter`). A case checks the outcome, the catalog code, each error's path, the changesets that reached the committer with the real command and the envelope's surface, and the transport's signal its `SurfaceProfile` gives: `RestProfile` (the catalog's HTTP status with problem details, 200 or 202 with the receipt), `InertiaProfile` (303 back to the page, field errors in the errors prop below `command`), `McpProfile` (the catalog's MCP response, an agent's credential) and `CliProfile` (cms:run with the catalog's exit code). The support lives in `tests/Support/SurfaceContract`; `SurfaceProfiles::all()` has one profile per case of `Surface`, and a case whose surface has no profile fails.

## The inspecting commands

The inspecting commands (GUARDRAILS 5 and 7.1, PRD 13.2, `docs/developers/inspecting.md`) each call an action and take `--json`. `cms:actions` (the cli's `Console\ActionsCommand`) calls `Cbox\Cms\Core\Registry\Actions\DescribeActions::describe()`, which reads the `RegistryCache` and gives an `ActionDescription` per action in the registry's order: its `ActionEntry`, the permission a grant needs (`permission`, the name of the command or query, as `role_permissions` holds it) and, for a write, its hooks in run order; `Cli\Boundary\ActionsOutput` prints them. `cms:hooks <name>` (`Console\HooksCommand`, `Cli\Boundary\HookMapInput` and `HookMapOutput`) calls `Registry\Actions\MapHooks::map(HookMapRequest)`, which gives a `HookMap` of `VersionHooks` per registered version of the command, lowest first, and throws `Registry\Domain\UnknownCommand` (exit 64) for a name no `CommandEntry` has, a query's included. The pipeline's `RegistryCommandHooks` and both actions take a command version's hooks from `CompiledRegistry::hooksOf()`, so the map is in the order they run. `cms:explain <url> --locale=<locale>` (`Console\ExplainCommand`) reads the URL's host and percent-decoded path, without the query and the fragment, into a `QueryCall` of `path.resolve` as the anonymous principal (`Cli\Boundary\ExplainInput`, a bad URL or locale exits 64), runs it through the `QueryPipeline` and prints the `PathExplanation` of the `ResolvedPath` with the content keys and the read's position (`Cli\Boundary\ExplainOutput`); an answered read exits 0 whatever its outcome, a rejected one with the catalog's exit code of its first error. The JSON form of an explanation is `path-explanation.v1.json`, written only by the generated `PathExplanationCodecV1`, the one encoding of it that every surface showing an explanation uses, `GET /v1/resolve` included; `--json` prints one line of `explained-path.v1.json` (`Routing\Domain\Dto\ExplainedPath`: content keys, the explanation embedded, the read position) through `ExplainedPathCodecV1`. `Cli\Boundary\RefusalOutput` prints refusals and rejected reads (problem.v1.json with `--json`), and `Cli\Boundary\RegistryRefusal` turns an unreadable registry cache into `registry_cache_missing` or `registry_cache_malformed` (exit 78). The actions' tests are `DescribeActionsTest` and `MapHooksTest` in the Actions suite; `packages/cli/tests/Console` runs the commands against the workbench's registry, compiled from its scan roots (`WorkbenchRegistry`), and `packages/cli/tests/Postgres/ExplainCommandTest.php` explains a placement and a mount URL on a second site and holds the `--json` document to `PathExplanationJson` of the explanation the query pipeline answers the same read with. `cms:panel:points [selector]` (`Console\PanelPointsCommand`, `Cli\Boundary\PanelPointsInput` and `PanelPointsOutput`) calls `Registry\Actions\DescribePanelPoints::describe(PanelPointsRequest)`, every point or those an id `<name>@<version>`, a point's name or a page selects, and `cms:panel:fills <point>` (`Console\PanelFillsCommand`) calls `Registry\Actions\MapPanelFills::map(PanelFillsRequest)`, the point's contributions in render order; a selection or id the registry does not hold is `Registry\Domain\UnknownPanelPoint`, exit 64. Their tests are `DescribePanelPointsTest` and `MapPanelFillsTest` in the Actions suite and `packages/cli/tests/Console/PanelPointsCommandTest.php` and `PanelFillsCommandTest.php`.
