# Access and row level security

Access is decided by grants compiled into regions and set on the connection as the actor context; the policies of every table read it and fail closed without it.

## Access

Access (PRD 5.10, 12.2, 12.12) is the core migration `*_create_access_tables.php` and the core feature `Cbox\Cms\Core\Access`. `roles` (handle, classification ceiling), `role_permissions` (the command names a role may run) and `grants` (actor, role, node, `effect` `allow` or `deny`, `locales` a text array or null for every locale, one per actor, role and node) are written in M1 only by the testkit's `Cbox\Cms\Testkit\FixtureWriters\Access\Adapter\PostgresAccessFixtures` as the owner role, whose policy is the only write policy; the grant commands come in B1. `audit` has one row per changeset (actor, command and version, issuer kind, surface, reason code, legal basis, the changed aggregates as their keys, `<kind>:<uuid>` or a variant's `variant:<uuid>:<variant>`, `xid`), no text content, CHECKs on every form, RANGE-partitioned per day on changeset_id in `cbox-cms.database.partitions.tables` and never dropped; the app role has SELECT and INSERT and a policy only to insert its own actor's row. The actor context is set by `Access\Infrastructure\ActorContext::set(AccessContext)` (`#[Internal]`), the one writer of the settings: one statement of `set_config(..., true)` for `cbox_cms.principal` (`actor` or `anonymous`), `cbox_cms.actor`, `cbox_cms.access_allowed` and `cbox_cms.access_denied` (the region paths and their exceptions as ltree arrays), `cbox_cms.classification` and `plan_cache_mode` `force_custom_plan`, inside the caller's open transaction, reads included; without one it throws `TransactionRequired::forAccessContext()` and sets nothing. `Access\Adapter\PostgresAccessResolver::resolve(Principal)` sets the anonymous context, or for an actor a context naming only the actor, reads its grants (the app role reads only the grants of the context's actor and the nodes they name), compiles them with `Access\Domain\AccessCompiler` and sets the compiled context. An actor that acts on behalf of others (PRD 5.16, 2.31, 22) gets the intersection of its own compiled context and that of every actor of its chain, each from that actor's current grants (`AccessCompiler::intersect()`: a node is reached only when every context reaches it, the classification access is the lowest, capped by the credential's ceiling), so a delegated credential reaches nothing its person does not and loses what the person loses; the chain's grants are read through `PostgresGrants::ofDelegator()`, the owner function `cms_delegator_grants(actor, command)` (migration `*_add_delegated_grants.php`), which raises 42501 without an actor context and returns no grant of an actor no credential of the context's actor is issued on behalf of, so such a chain reaches nothing, and the command and query authorizers require the permission of every actor of the chain too. `packages/core/tests/Postgres/DelegatedAccessTest.php` holds it. The compiler: a role reaches a node in a locale when its nearest grant above or on the node that holds in that locale allows (a deny beats an inherited allow, the most specific grant wins, a deny wins over an allow on the same node); a node is reached when a role reaches it in some locale; the regions are the fewest that say the same, so a region can lie in another's exception; the classification access is the one that holds on every node reached, the lowest over the nodes of the highest ceiling among the roles that reach each node, capped by the credential's ceiling, public with none, so a role with a high ceiling on some nodes never lifts the fields of the others (a ceiling per region is a follow-up). The migration's functions read the context and fail closed without one: `cms_access_context()`, `cms_access_actor()`, `cms_access_reaches(ltree)` (the deepest region path or exception above the node is a region path), `cms_access_classification_allows(text)`, `cms_access_home(home_node, owner_actor)` (the owner, or EXISTS against `nodes` on the home node) and `cms_access_released(entry, stage)` (the released stage of an entry with a live released placement locale). A policy names another table only through a PL/pgSQL function (`cms_access_node`, `cms_access_entry` and the others), because Postgres plans a function's query apart, while policies expanded inline pulled each other in and made one read take seconds. Every table with row level security holds without a context no row for the app role: `tests/Postgres/WalkingSkeleton/RlsWithoutActorContextTest.php` lists every such relation from pg_class, partitions and generated type tables included. An actor reads and writes `nodes` its regions reach (and reads the nodes its grants name), entries by home or ownership, heads, revisions, payloads, snapshots and the release log through their entry, placement generations and locales through the placement's node, placements through either, its own changesets, their principals and audit inserts, and reason texts of changesets it sees up to its classification access; every context also reads what is public: live released placement locales and the active entries, released heads, published revisions and payloads and snapshots behind them. The anonymous context writes nothing. An actor also writes a node its regions reach (`nodes_actor` is FOR ALL) and a route of such a node (`node_routes_write`), which the node commands go through; the owner reads `nodes` and `node_routes` past the regions through `nodes_owner_read` and `node_routes_owner_read` for the node lookups and writes neither, and the narrow `nodes_site_root` and `node_routes_site_root` take the root node and the route `/` of a site's registration while `cms_structure_registering()` holds. Sites, site locales, mount overrides and reads of the changeset register have no policy of the actor's own yet. A generated type table gets its two policies from `Access\Infrastructure\TypeTableAccess::protect($table)` (`#[Experimental]`): `<table>_actor` with `cms_access_home(cms_home_node, cms_owner_actor)` for every command and `<table>_released` with `cms_access_released(cms_entry_id, cms_stage)` for reads. `packages/core/tests/Postgres/AccessPoliciesTest.php` shows it end to end with `AccessWorld`. Each PL/pgSQL `cms_access_*` function, and each PL/pgSQL function a policy calls, sets `plan_cache_mode = auto` for itself (migration `*_cache_access_function_plans.php`; an access function a later migration creates or replaces sets it in its definition), so its lookups by key keep their cached plans while the context's `force_custom_plan` still plans the queries the policies filter; `packages/core/tests/Postgres/AccessFunctionPlansTest.php` holds every such function to it.
