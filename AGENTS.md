## Commands

- `composer services:up` starts PHP 8.5, Postgres and Valkey from `compose.yaml` and runs the idempotent Postgres init script again, so an existing volume gets the current roles; `composer services:down` stops them. Both run `tools/bin/services.php`, which always uses the main checkout's `compose.yaml` and the main checkout as `--project-directory`, found from `git rev-parse --path-format=absolute --git-common-dir`, so no container mounts a worktree. The services are shared: in a linked worktree, services:up starts only Postgres and Valkey with `up -d --wait --no-recreate postgres valkey`, never recreates a running container, runs the init script and says that the php container mounts the main checkout, and services:down refuses with exit 1. `docker compose exec php ...` therefore runs the main checkout's code, not a worktree's, so container-bound work, such as the Mutation suite, runs from the main checkout.
- `composer dev:prepare` readies the workbench's dev database `cms`, which every checkout shares, for `vendor/bin/testbench cms:doctor` (in the php container, `docker compose exec php`, it needs no flag, because the drop-in `docker/php/conf.d/cms.ini` sets `allow_url_fopen = Off`; on a host with `allow_url_fopen = On`, run `php -d allow_url_fopen=0 vendor/bin/testbench cms:doctor`): after `composer services:up`, run it from the main checkout, never from a worktree. It runs the migrations as the owner role (`migrate --database=pgsql_owner`, the connection in `cbox-cms.database.owner_connection`), then `cms:partitions:maintain` for the partition runway, then `cms:build`. Each step is idempotent; it stops at a failing step and exits with its code.
- `composer check` runs the local profile of GUARDRAILS 10, gates 1 to 6, and marks each gate and step pass, fail or not run. It exits 1 when a gate fails. Run it before handing work over, with the services up; with Postgres or Valkey down, gate 5 fails. `composer check -- --report=<file> --brief` writes a JSON report and keeps failed output out of the console.
- `composer check:selftest` plants one known violation per gate in a temporary git worktree of HEAD and fails unless each gate catches its violation with a path inside the worktree. Run it after changing a gate, the tool configuration or the check itself, and commit first. The worktree's suites run in its own test database, which the selftest drops before it removes the worktree.
- `composer test-db:prune` drops the Postgres test databases of checkouts removed by hand, such as a worktree removed with `git worktree remove`: those whose testkit comment names this host and a checkout that is gone or no longer derives the name, with `DROP DATABASE ... WITH (FORCE)`. It keeps the configured database, this checkout's, other hosts' and those without a valid comment. `composer test-db:prune -- --dry-run` prints the same verdicts and drops nothing; without the `--`, Composer drops the option and the prune is real.
- Every changed, removed or new check and test is recorded with its reason in `CHECKS-LOG.md` at the repo root (GUARDRAILS 7.3, version 1.9), in an entry under the heading of its block (`## M0`, `## M1`, ...) that starts with the task (`M1-T3:`) and says GUARDRAILS 7.3. "Til review af Sylvester" in `PROGRESS.md` holds only open decisions for Sylvester; notes without a decision go under "Info" there.

The merge queue of `.claude/workflows/cms-milestone.js` writes each task's entries in a commit `<block>-<task>: progress` and runs it before it moves main; a task reports its changed checks in `changedChecks` and never commits without a change. `composer progress:test` runs the tests that read `PROGRESS.md`, `CHECKS-LOG.md` and this checkout's review commits, which all live in `tests/Feature/Tooling/Progress` (a test there keeps them there), on the working tree and HEAD. `composer check` runs before the progress commit exists, so every agent of the workflow that commits entries, the merge queue, the regression fix and the exit phase, runs `composer progress:test` on that commit, and the merge queue moves main only after it passed.

## Hvor ting bor

The namespace layout for the layers of GUARDRAILS 2.5. The Arch suite (`vendor/bin/pest --testsuite=Arch`, files in `tests/Arch`) enforces it over `packages/*/src` and `workbench/app`. The Arch suite checks the "May not use" column and the only-use rules for Domain, Actions and Infrastructure; the `mixed` and `array` column is enforced by the testkit's PHPStan rules in `packages/testkit/src/Phpstan`. This section is the same in `CLAUDE.md` and `AGENTS.md`; a test keeps them equal.

Code sits in a module below the package, and the layer is a namespace segment below the module: `Cbox\Cms\Core\Entries\Domain\Commands\ReleaseVariant`, `Cbox\Cms\Core\ReceiptStore\Adapter\PostgresReceiptStore`. A namespace is in a layer when one of its segments is the layer name, either as the last segment or with more segments below it. When several segments match, the innermost one decides: `Cbox\Cms\Http\Boundary\RequestParser` is Boundary. `Domain` does not match `DomainEvents`.

| Segment | What lives there | May use | May not use |
|---|---|---|---|
| `Domain` | value objects, enums, invariants, domain interfaces | the domain and the contracts | everything else, including `Illuminate\Http`, facades and Eloquent |
| `Domain\Commands`, `Domain\Queries`, `Domain\Dto`, `Domain\Receipts` | command and query DTOs, other DTOs, receipts and results | as Domain | as Domain; only `final readonly` classes, no enums or interfaces |
| `Actions` | write actions, query actions and planners | the domain, the contracts, other classes in Actions | the framework, the DB facade, connections; only `final readonly` classes |
| `Boundary` | HTTP parsers, config readers, JSON decoders, queue payloads | the domain, the contracts, the framework, `mixed` and `array` | actions, surfaces |
| `Adapter` | implementations of contracts that need the framework or Postgres: the receipt and idempotency stores and their row mappers, Eloquent casts, Inertia props | the domain, the contracts, the framework, `mixed` and `array` | actions, surfaces |
| `Infrastructure` | Eloquent models, migration support, the partition manager | the domain, the contracts, `Illuminate\Database`, Boundary (the row mappers and error readers for what Postgres returns), casts in Adapter | `Illuminate\Http`, facades, actions, surfaces, `mixed` |
| `Jobs` | queue jobs; a surface | actions, DTOs, Boundary | Infrastructure, Adapter, Eloquent, the DB facade, connections |
| `Http` | the http package, `Cbox\Cms\Http`; a surface | actions, DTOs, Boundary | Infrastructure, Adapter, Eloquent |
| `Cli` | the cli package, `Cbox\Cms\Cli`; a surface. Artisan commands live in `Cli\Console`, never in a `Commands` namespace | actions, DTOs, Boundary | Infrastructure, Adapter, Eloquent |

More rules:

- The contracts package, `Cbox\Cms\Contracts`, is part of the domain and has no layer segments. The attributes `#[Stable]`, `#[Experimental]`, `#[Internal]`, `#[Command]` and `#[Hook]`, and the enum `Phase`, live in `Cbox\Cms\Contracts\Attributes`. `#[Action]` and the enum `Surface` come back in M1 with the WriteAction and QueryAction shapes and the actions registry (`PROGRESS.md`, Fjernet fra M0).
- `Commands`, `Queries`, `Dto` and `Receipts` namespaces sit only below `Domain` or in the contracts package.
- Every class, interface, trait and enum in `packages/*/src` carries exactly one of `#[Stable]`, `#[Experimental]` and `#[Internal]`. Service providers are `#[Internal]`.
- Outbound HTTP (Guzzle, the Http facade, HTTP clients, `curl_*`, sockets, `file_get_contents`) is allowed only in the gateway namespace `Cbox\Cms\Core\Egress`, which goes through the SSRF guard. That includes everything PHP's URL wrappers let fetch a URL or that runs a program: `fopen`, `file`, `readfile`, `copy`, `get_headers`, the `*_file` functions, `SplFileObject`, `SplFileInfo::openFile()`, `DOMDocument`, `XMLReader`, `pfsockopen`, `stream_context_create`, `socket_*`, `ftp_*`, `proc_open`, `exec` and the other program functions, backticks, Symfony Process and Illuminate Process. Writing, moving, removing or listing through ftp:// counts too (`file_put_contents`, `rename`, `unlink`, `mkdir`, `rmdir`, `opendir`, `scandir`, `dir`, `DirectoryIterator`, `FilesystemIterator`, `RecursiveDirectoryIterator`), as do `touch`, `chmod`, `chown` and `chgrp`, which a registered wrapper serves, and `bzopen`, as do the filesystems that pass a URL on (`Illuminate\Filesystem`, the `File` facade, Symfony's Filesystem), XML that fetches entities or documents (`simplexml_load_string`, `XSLTProcessor`, `SoapServer`) and mail (`mail`, `mb_send_mail`, `error_log`). So do the framework's and the packages' own HTTP senders, which `allow_url_fopen` does not stop, with their contracts, because a type-hinted contract gets a client without naming it: storage disks (the `Storage` facade, `Illuminate\Contracts\Filesystem`, `League\Flysystem`, `Aws`), mail (the `Mail` facade, `Illuminate\Mail`, `Illuminate\Contracts\Mail`, `Symfony\Component\Mailer`), notifications (the `Notification` facade, `Illuminate\Notifications`, `Illuminate\Contracts\Notifications`), the image manager (the `Image` facade, `Illuminate\Image`), `Symfony\Contracts\HttpClient` and HTTPlug (`Http\Client`, `Http\Discovery`), and the container ids that resolve them, `Egress::SERVICE_IDS`: 'files', 'filesystem', 'filesystem.disk', 'filesystem.cloud', 'mailer', 'mail.manager', 'image' and 'http'. A quoted string that spells one of these names counts as well, so a string callable such as `array_map('file_get_contents', ...)`, `[$info, 'openFile']`, `app('GuzzleHttp\Client')` or `app('filesystem')` is reported; an array key or offset is not, and `Egress::ALLOWED_WORDS` lists the strings that are only words, such as 'file' in a report. The lists and the allowed local uses, each with its reason, are in `tests/Support/Arch/Egress.php`; the Arch suite reads exact names from the tokens (`ReferenceScan`) and fails an allowance no code uses. Read and write local files through code that refuses a path naming a stream wrapper before it touches it, with `Cbox\Cms\Contracts\Storage\LocalPath::namesStreamWrapper()` (`#[Internal]`), as the generators' `Schema\Boundary\LocalFile` and the writers `FileRegistryCache`, `FilesystemGeneratedOutput` and `FilesystemSchemaFiles` do. The stat functions (`is_file`, `file_exists` and the like) are not on the lists. The runtime contract also turns `allow_url_fopen` off (`php.allow_url_fopen` in `cms:doctor`).
- The kernel knows no content types (GUARDRAILS 2.4). `tests/Arch/ContentTypesTest.php` reads every blueprint below `workbench/schema` with symfony/yaml and takes the type handles, the field handles (groups included) and the select values. Each starts with `fixture_` (`ContentTypeScan::PREFIX`; the test fails on one that does not), so no handle is an ordinary word such as `title`, and the test fails on each match in the text of the files below `packages/{contracts,core,testkit,generators,http,cli}/src`, comments included, reported as `file:line: text`: a handle matches anywhere in a line, in any case, with each underscore written as `_`, `-`, several of them or nothing, so `fixture_article` also matches `FixtureArticle`, `$fixtureArticle` and `fixture-article-id`. The scanner is `tests/Support/Arch/ContentTypeScan.php`, covered by `tests/Feature/Tooling/ContentTypeScanTest.php`, and the selftest plants `'fixture_article'` in `Selftest\Domain\ContentType`. Test data in the core packages uses neutral words, such as `{"value":"A"}` for a content hash.
- `mixed`, untyped arrays and array shapes are allowed only in Boundary and Adapter. The PHPStan rules report them in parameters, returns, properties, class constants (the var tag, or else the native type, so a `const array` needs a typed var tag), template bounds and class PHPDoc tags as `cboxCms.mixed`, `cboxCms.untypedArray` and `cboxCms.arrayShape`. A typed array is `list<T>` or `array<K, V>` where neither K nor V is `mixed`; `Foo[]` and `array<Foo>` have no key type and count as untyped. Structured data is a DTO. Closures are checked on their native types only.
- Test code, meaning a namespace with a `Tests` segment or the global namespace of Pest files, is exempt from that rule. Code in `packages/*/src` and `workbench/app` therefore always declares a namespace without a `Tests` segment; the Arch suite checks it.
- `@phpstan-ignore` in any form is allowed only in Boundary and Adapter. The PHPStan rule `cboxCms.phpstanIgnore` reads the tokens of every analysed file, tests included, and a token scan in the Arch suite checks `packages/*/src` and `workbench/app`. The testkit's own PHPStan rules report errors that no ignore comment and no `ignoreErrors` entry can hide. The one exception is `cboxCms.internalUse` in an addon: a comment that names it, `@phpstan-ignore cboxCms.internalUse (reason)`, hides one use on its line for each naming; `@phpstan-ignore-line`, `@phpstan-ignore-next-line`, a comment for other identifiers and an `ignoreErrors` entry never do. `docs/addons/static-analysis.md` documents it for addon authors.
- `#[Internal]` sits on a class, a method or a class constant. Code outside the `Cbox\Cms` namespace, the global namespace included, may not use it (GUARDRAILS 2.3). The testkit's PHPStan extensions report every use, in code and in PHPDoc, as `cboxCms.internalUse`: PHPStan's restricted usage rules find the uses, `InternalUseIgnoreErrorExtension` takes each out of the file's ignorable errors and emits it as collected data, and `InternalUseRule` reports it after the analysis, non-ignorable unless a comment on its line names the identifier. `InternalUseCollector` reads those lines from the `linesToIgnore` attribute PHPStan's parser sets, so a waiver sits on the line PHPStan applies the comment to. A Pest file in this repo that uses internals therefore declares a namespace below `Cbox\Cms`, such as `Cbox\Cms\Tests\Feature` or `Cbox\Cms\Core\Tests`.
- Actions and Jobs never manage transactions (GUARDRAILS 4.1, PRD 4.2): no `transaction`, `beginTransaction`, `commit`, `rollBack`, `savepoint` or `createSavepoint` on a connection, the database manager, PDO or the DB facade, and no string containing `SAVEPOINT`. The PHPStan rules report them as `cboxCms.transaction` and `cboxCms.savepoint`; test code is exempt.
- Ids are value objects (PRD 5.3). Outside Boundary and Adapter, a public method parameter named `$id` or ending in `Id`, and the return of a public method named `id()` or ending in `Id`, may not be a string, nullable or not. The PHPStan rule reports `cboxCms.stringId`; test code is exempt, and so is a signature the framework requires: a method that implements or overrides a method of a PHP, `Illuminate`, `Symfony` or `Psr` interface or parent class whose declaration, PHPDoc included, has a string in that place (a constructor only when that declaration is abstract). The method's name never exempts it, so a job's `uniqueId(): string` is reported, because `ShouldBeUnique` declares no method. A value object takes its string as `$value`, and a Boundary parses the string into it.
- Contracts live in `Cbox\Cms\Contracts` (GUARDRAILS 2.3). `CoreServiceProvider` binds each one as a singleton to the class in `cbox-cms.contracts` (defaults in `packages/core/config/cbox-cms.php`); an application overrides one entry at a time. The configuration is `config/cbox-cms.php`, every key sits under `cbox-cms.*` (`cbox-cms.contracts`, `cbox-cms.database`, `cbox-cms.doctor`, `cbox-cms.generators`), and the commands keep their `cms:*` names (GUARDRAILS 2.3). Every contract has a fake in the testkit and a shared suite there, a trait such as `Cbox\Cms\Testkit\Clock\ClockContract`. A package runs it in `tests/Contract` with one PHPUnit class per implementation.
- Code asks the `Clock` contract for the time instead of reading the system clock; only a clock implementation, a class that implements `Clock`, reads it. The testkit's PHPStan rule `SystemClockRule` reports every other read as `cboxCms.systemClock`, non-ignorable and in every layer; test code is exempt, meaning a namespace with a `Tests` segment or a file in the global namespace below a `tests` directory (`LayerScope::isTestFile()`), so migrations, config files and route files are checked. A read is `time()`, `microtime()`, `uniqid()`, `now()`, `date()` without a timestamp, `strtotime()` without a base, `new DateTimeImmutable()` or `date_create()` without a date or with a constant relative one such as `'now'` or `'+1 day'`, `createFromFormat()` with a constant format that leaves a field to the clock, Carbon's `now()`, `parse()` and comparisons with now, or `$_SERVER['REQUEST_TIME']` (the full list is `ClockReads`). `hrtime(true)` measures durations and deadlines of real waits and is allowed. `now()` is UTC with microseconds and is not monotonic. Tests use the testkit's `FakeClock` (`set`, `advance`, `freeze`). The core's `SystemClock` and the testkit's `FakeClock` also implement PSR-20's `Psr\Clock\ClockInterface` (`psr/clock`, required by core and testkit), so a library that asks for a PSR-20 clock gets the same clock; the `Clock` contract does not extend it, because the contracts package depends only on PHP.
- Code asks the `IdGenerator` contract for a new id instead of making a UUID itself; only a class that implements `IdGenerator` makes one. The testkit's PHPStan rule `UuidCreationRule` reports every other one as `cboxCms.uuid`, non-ignorable; test code is exempt, read as for `cboxCms.systemClock`. It covers `Str::uuid()`, `uuid7()`, `orderedUuid()` and `ulid()`, the Eloquent traits `HasUuids`, `HasVersion4Uuids` and `HasUlids`, the random and time-based factories of ramsey/uuid and symfony/uid, and `uuid_create()` (the full list is `UuidCreations`). `next()` returns a `Cbox\Cms\Contracts\Ids\Uuid7`, and a typed id such as `ChangesetId` wraps it. The first 48 bits are the Clock's unix milliseconds; ids from one instance are strictly increasing, also when the clock repeats a millisecond or steps back. `Uuid7::lowestAt()` and `highestAt()` give the bounds of a millisecond for partition ranges. A bad string throws `InvalidUuid7`. Tests use the testkit's seeded `FakeIdGenerator`.
- The `ReceiptStore` contract (`Cbox\Cms\Contracts\ReceiptStore`) has `store(StoredReceipt)`, `find(ChangesetId): ?StoredReceipt` and `markProjection(ChangesetId, ProjectionStatus): bool`; the status names the projection. A `StoredReceipt` holds only facts about a committed changeset: the `ChangesetId`, the `RetentionClass` and the projection statuses. It has no outcome and no wait level, because the kernel stores it in the command transaction (PRD 6.2 phase 7), before any wait level past commit is reached; the kernel builds each call's `Receipt`, a replay's too (PRD 6.1), from it, the wait level the call asks for and whether that level was reached. `store()` and `markProjection()` run on the caller's connection and never begin, end or savepoint a transaction. `store()` runs only inside the caller's open transaction and throws `TransactionRequired` (in `Contracts\Consistency`, a `LogicException`) and stores nothing without one, so a store holds no lock or other state past its transaction, which a pooler in transaction mode (PRD 5.10) could leave behind on a server connection; `markProjection()` runs inside the caller's transaction when one is open and otherwise commits on its own. A second receipt for a changeset throws `DuplicateReceipt` (in `Contracts\Consistency`). A changeset time that no partition covers throws `Contracts\Storage\PartitionMissing` (`CODE` `partition_missing`) and stores nothing; the caller rolls back, because Postgres has failed the transaction. `markProjection()` is idempotent, an acknowledgement is final, and it returns false and changes nothing when no live receipt lists the projection. Expiry is logical: `find()` returns null once the Clock is later than `RetentionClass::expiresAt()`, the changeset id's time plus 7 days for Standard; Evidence has none. A `store()` of a changeset that another open transaction stored waits for that transaction and then throws `DuplicateReceipt` or stores; the duplicate comes from `store()`, never from commit. A store on a database may need the caller's transaction at READ COMMITTED, so that it sees a receipt committed while it waited, and throws `Contracts\Consistency\UnsupportedIsolation` at another level. The testkit's `FakeReceiptStore` is the store and the harness; used directly it has no transaction, so its `store()` throws `TransactionRequired`, and `session()` gives connections with `begin`, `commit` and `rollBack`, and `whenWaiting()` schedules what happens while a store waits (a store with nothing scheduled throws a LogicException). The shared suite `ReceiptStoreContract` takes a `ReceiptStoreHarness` that hands out `ReceiptStoreSession`s and whose `uncover($from, $to)` takes a range of partition keys out of the partitions: on the fakes exactly that range, on Postgres the test helper `PartitionGaps` drops every managed partition that overlaps it. After a PartitionMissing inside a transaction, a fake session refuses every call and `commit()` with a LogicException until `rollBack()`. Testkit code for the store lives in the module `ReceiptStore`, not `Receipts`, because of the category rule.
- The `IdempotencyStore` contract (`Cbox\Cms\Contracts\IdempotencyStore`) has `claim(IdempotencyScope, IdempotencyKey, ContentHash, WaitBudget): ClaimResult` and `complete(ClaimToken, ChangesetId)`, and no `release()`. Both run only inside the caller's open command transaction and throw `InvalidClaim` without one. `claim()` takes a claim on (scope, key) that lasts until that transaction ends, waiting at most the `WaitBudget` (0 to 5000 ms, real time, not the Clock; a store ends the wait sooner when the database's time limit on the transaction would end it first) while another transaction holds it, and then looks up the completed record. The result is one of four final readonly classes in `Contracts\Idempotency`: `Fresh` (a `ClaimToken`), `Replay` (the stored `ChangesetId`; the caller resolves the receipt through the `ReceiptStore`), `Conflict` (`Conflict::CODE` is `idempotency_conflict`) or `InFlight` (the budget ran out; holds nothing). Every result but `InFlight` holds the claim. `complete()` writes the record in the same transaction, so a rollback, or a commit without `complete()`, leaves the key fresh. A record expires with the Standard receipt of its changeset, `RetentionClass::Standard->expiresAt()`. The testkit's `FakeIdempotencyStore` is the harness; its `session()` is the fake store, and `whenWaiting()` schedules what happens while a contested claim waits. `complete()` throws `PartitionMissing` and records nothing when no partition covers the record's date, the later of the Clock's time and the changeset's time; the caller rolls back, which leaves the key fresh. The shared suite `IdempotencyStoreContract` takes an `IdempotencyStoreHarness` of `IdempotencyStoreSession`s, with the same `uncover()` as the receipt store's harness. Both session interfaces extend `Cbox\Cms\Testkit\Sessions\TransactionalSession`, so one session for a real database can serve both stores.
- The receipt and idempotency types live in the contracts package, because the store contracts take them and the contracts package depends only on PHP: `Receipt` (the result of one call), `StoredReceipt` and `ProjectionStatus` in `Cbox\Cms\Contracts\Receipts` (final readonly DTOs), the enums `Outcome`, `WaitLevel`, `RetentionClass` and `ProjectionState` with `ProjectionName` and `InvalidReceipt` in `Cbox\Cms\Contracts\Consistency`, `ChangesetId`, `PrincipalId` and `CommandName` in `Cbox\Cms\Contracts\Ids`, and `IdempotencyKey`, `IdempotencyScope`, `ContentHash` and `PrincipalKind` in `Cbox\Cms\Contracts\Idempotency`. A committed outcome requires a `ChangesetId`; the others forbid one. An `IdempotencyScope` is a `PrincipalKind`, a `PrincipalId` (the actor's or source's id, 1 to 255 visible ASCII characters, compared exactly; `InvalidPrincipalId` otherwise) and a `CommandName` (the name from `#[Command]` without the version, in the form of `Command::NAME_PATTERN`; `InvalidCommandName` otherwise), and takes no string. No code serialises a receipt to JSON; the JSON form comes with the codecs M1 generates (GUARDRAILS 2.2). A `Receipts` segment anywhere in a namespace makes it the Receipts category, so a core module for the stores cannot be called `Receipts`.
- Range partitions are kept by the partition manager in `Cbox\Cms\Core\Partitions` (PRD 4, 4.2). A partitioned table is listed in `cbox-cms.database.partitions.tables` with its key (`uuid7`: bounds are `Uuid7::lowestAt()` of the span's first millisecond and of the next span's; or `timestamp`), its interval (`day` or `month`, spans start at midnight UTC) and `retention_days` (null keeps all). Partitions are named `<table>_p<YYYYMMDD>` or `<table>_p<YYYYMM>`, and only those names are managed. There is no DEFAULT partition, so a write outside the partitions fails; an adapter that writes to a partitioned table catches the `QueryException` and throws `MissingPartitionMapper::map()`, which turns SQLSTATE 23514 "no partition of relation" into `Cbox\Cms\Contracts\Storage\PartitionMissing` (`CODE` `partition_missing`). `cms:partitions:maintain` (scheduled hourly by `CoreServiceProvider` in a process where the owner connection is configured, `CoreServiceProvider::ownerConnectionConfigured()`) runs the action `MaintainPartitions` at the Clock's time: it creates partitions from now to `runway_days` ahead (default 14) and removes partitions past retention with `DETACH PARTITION CONCURRENTLY` and `DROP TABLE`, never `DELETE`. Because autovacuum never analyzes a partitioned table (PRD 4.2), a maintain run then runs `ANALYZE` on the root of each partition tree whose partitions it changed (`pg_partition_root()`, so `receipts` for `receipts_standard` and `receipts_evidence`), once per root, as step `DdlStep::Analyze` under the same lock timeout and retry, and names the roots in `PartitionReport::$analyzed` (the command prints `analyzed <root>`); `ANALYZE ONLY` is Postgres 18 and not used, and `--from` and `--to` analyze nothing. A new partition gets its parent's row security flags and its parent's grants (`TablePrivileges::copy()`), so the owner's default privileges never reach a partition. A table with a managed name that is not a partition (detached by hand, or by a run whose Clock was ahead) and not past retention is attached again when a run needs its span (`PartitionChangeKind::Reattached`, step `DdlStep::Attach`, with the parent's row security and grants), and one left pending detach is finalized first; when Postgres refuses the attach (other columns or constraints, rows outside the span) the create phase of that table stops there with `UnmanageableTable::detachedPartition()` naming the table. It runs only on `cbox-cms.database.owner_connection` and throws `OwnerConnectionRequired` on the app connection. Every step runs with `lock_timeout` 2 s and a bounded retry with backoff, and gives up with `LockTimeout`. A run creates the partitions of every table before it retires any, and a step that gives up on one table's lock ends that phase for that table only: the `LockTimeout` goes in `PartitionReport::$gaveUp` as a `Domain\Dto\GaveUpStep` (its step, table, partition, attempts, message and the message of its cause, no exception) and the run goes on with the other tables; only a busy maintenance lock is thrown. An `UnmanageableTable` (`CODE` `partition_table_unmanageable`) also stops its table only: a table that is missing, not partitioned by range or has a DEFAULT partition gets no phase and no runway, a refused attach ends that table's create phase, and any other step on a partition that Postgres refuses for another reason than a lock wait (a DROP that a view on the partition blocks, a CREATE of a managed name that a view or a partition of another parent holds) ends that phase of that table as `UnmanageableTable::stepRefused()`; it goes in `PartitionReport::$failed` as a `Domain\Dto\FailedTable` (table, partition, message and the message of its cause) and the run goes on, so a table listed before its migration has run never stops the runway of the others. Only `UnmanageableTable::inTransaction()` is thrown. The command prints the report, then each step that gave up and each table that failed, and exits 78 when a table failed, else 75 when anything gave up. The doctor's `partitions.runway` fails with `doctor_partition_table_unmanageable` for such a table and still gives the runway of the others. `--from` and `--to` only create the partitions of a range. A run's report gives each table's runway from the Clock's time, with or without `--from` and `--to`: the end of the unbroken run of attached partitions from the partition that holds now, so a gap ends it. `Partitions\Domain\PartitionRunway::end()` computes it for the report and for the doctor's `partitions.runway`. Tests that write to a partitioned table first call the testkit's `app(PartitionFixtures::class)->cover($from, $to)` or `coverClock($clock, $interval)` for the dates they write at.
- The receipt store on Postgres is `Cbox\Cms\Core\ReceiptStore\Adapter\PostgresReceiptStore`, bound to `ReceiptStore` in `cbox-cms.contracts`. It runs on the default connection (or a named one), through the query builder except for that insert, and never begins a transaction. Every read, the lock included, uses the write PDO (`useWritePdo()`), so outside a transaction a lagging read host never hides a stored receipt from `find()` or `markProjection()`. Its tables come from the core migration `packages/core/database/migrations/*_create_receipts_tables.php`: `receipts` (one row per changeset, with no outcome or wait level) and `receipt_projections` (one row per changeset and projection), both LIST-partitioned on `retention_class` and then RANGE-partitioned on `changeset_id`, managed as `receipts_standard` and `receipt_projections_standard` (per day, `retention_days` 7) and `receipts_evidence` and `receipt_projections_evidence` (per month, never dropped). The primary keys are `(changeset_id, retention_class)` and `(changeset_id, retention_class, projection)`; there is no foreign key between them. `find()` and `markProjection()` filter on the Clock's live window (`PostgresReceiptStore::lowestLiveStandard()`), `markProjection()` updates only a pending row, and `store()` reports a duplicate without aborting the caller's transaction. The database holds the app role to that: it may update only `state` and `acknowledged_at` of `receipt_projections` (column grants from `TablePrivileges::limitColumns()`, on every partition), so an update of any other column fails with SQLSTATE 42501, and the trigger `receipt_projections_acknowledged` refuses every update of an acknowledged projection row with SQLSTATE 23000, for every role, which `markProjection()` never fires. The primary key cannot hold one receipt per changeset across the retention classes, so `store()` first takes the transaction-scoped advisory lock `ReceiptLock::of($changesetId)` (`pg_advisory_xact_lock`, the first 64 bits of a versioned SHA-256 of the changeset id), then looks for a receipt of either class, then inserts the receipt row with `ON CONFLICT DO NOTHING` and its projection rows in one statement (`PostgresReceiptStore::INSERT_RECEIPT`, a data-modifying CTE per table), so they are stored or fail together. Without an open transaction (`transactionLevel()` below 1) `store()` throws `TransactionRequired` before its first statement, so it never takes a session-level lock; a concurrent store of the same changeset waits for the first transaction and, under READ COMMITTED, gets `DuplicateReceipt`. `store()` needs READ COMMITTED, because its lookup must see a receipt committed while it waited: the lock statement `PostgresReceiptStore::LOCK_CHANGESET` also reads `transaction_isolation` and takes the lock only at that level, and at REPEATABLE READ or SERIALIZABLE `store()` throws `Cbox\Cms\Contracts\Consistency\UnsupportedIsolation` and holds no lock. The Postgres contract test is `packages/core/tests/Postgres/PostgresReceiptStoreContractTest.php`; it and the adapter tests cover the dates they write at with `PartitionFixtures`.
- The idempotency store on Postgres is `Cbox\Cms\Core\IdempotencyStore\Adapter\PostgresIdempotencyStore`, bound to `IdempotencyStore` in `cbox-cms.contracts`. It runs on the default connection (or a named one), inside the caller's transaction, and never begins one. Its table comes from the core migration `packages/core/database/migrations/*_create_idempotency_keys_table.php`: `idempotency_keys`, RANGE-partitioned per day on `created_at` and managed with `retention_days` 7, with an index on `lock_key`, no primary or unique key, and SELECT and INSERT for the app role. Postgres cannot keep a key unique across daily partitions, so a claim is a transaction-scoped advisory lock on `ClaimLock::of($scope, $key)`, the first 64 bits of a versioned SHA-256 of the scope and key: `pg_try_advisory_xact_lock` polled with a growing sleep (2 ms up to 50 ms) until it is granted or the `WaitBudget` has passed, never a blocking lock or `lock_timeout`, which would abort the caller's transaction. The wait also ends `PostgresIdempotencyStore::TRANSACTION_MARGIN_MILLISECONDS` (250) before the transaction's `transaction_timeout`, read in the first try from `pg_settings`, `transaction_timestamp()` and `clock_timestamp()`, because that timeout counts from the start of the transaction and terminates the session; the effective budget is the lower of the two, and 0 (off) leaves the budget alone. The lookup is a separate statement after the lock, so under READ COMMITTED it sees a commit made while the claim waited; a claim at another isolation level throws `InvalidClaim::isolationLevel()` and takes no lock. The lookup matches the full scope and key, so a lock key collision only makes two keys wait for each other. A Fresh claim is noted in the transaction-local setting `cbox_cms.idempotency_claims`, which `complete()` checks and Postgres resets when the transaction ends. `created_at` is the Clock's time, or the changeset's time when that is later, and `expires_at` is `RetentionClass::Standard->expiresAt()`; the CHECK `idempotency_keys_window` keeps `expires_at` within 168 hours of `created_at`, so every live record has `created_at` at or after `PostgresIdempotencyStore::lowestLiveCreatedAt()`, 7 days before the Clock's time, and the lookup prunes the older partitions. The lookup has no upper bound on `created_at`: a changeset's time, and so a record's `created_at`, can be on a later day than the claimer's Clock (a clock that stepped back, another node's clock ahead), so it reads every partition from then onward, the runway included. The Postgres contract test is `packages/core/tests/Postgres/PostgresIdempotencyStoreContractTest.php`.
- The registry (PRD 13.2) is compiled by `cms:build` (the cli's `Console\BuildCommand`, which calls the action `Cbox\Cms\Core\Registry\Actions\BuildRegistry`) to `bootstrap/cache/cms/`: `commands.php` and `hooks.php`, one per case of `Registry\Domain\RegistryName`. The cache owns that directory: after writing the files, `FileRegistryCache` removes every other file there, but not its lock file `.lock`, subdirectories or the temporary file of a registry, so a registry an earlier version wrote cannot linger. Each file returns `['build' => '<sha256>', 'entries' => [...], 'format' => 3, 'registry' => '<name>']`, sorted and without timestamps or paths, so two builds of the same code give the same bytes; `build` is the sha256 of the entries of both registries, so the files of one build carry the same one and `RegistryCacheCodec::decode()` refuses files of different builds and entries that do not match their build. A write puts every file in a temporary file first and then renames them into place one after the other, so a reader can meet the files of two builds; `FileRegistryCache::read()` then tells OPcache to forget them and loads them again, up to `FileRegistryCache::READ_ATTEMPTS` (10) times 5 ms apart, and so gives the whole old or the whole new registry. Files that stay mixed, as a build that stopped between two renames leaves them, are `MalformedRegistryCache` until cms:build runs again. Writes run one at a time, so two builds that both finish never interleave their renames: a write holds an exclusive `flock()` on `FileRegistryCache::LOCK_FILE` (`.lock` in the directory, never removed) from before its first rename until it has removed the other files, waits for it at most `FileRegistryCache::LOCK_WAIT_MILLISECONDS` (30 s) of real time, and otherwise writes nothing and throws `RegistryCacheUnwritable`; reads take no lock. `packages/core/tests/Registry/FileRegistryCacheInterleavingTest.php` puts a build's renames between a read's files through the stream wrapper `Fakes\InterleavedFiles`. A package's service provider implements `Cbox\Cms\Contracts\Build\DeclaresScanRoots` and returns `ScanRoot`s, each a Composer package name and an absolute directory (`__DIR__`); core, http, cli and generators declare their `src`, and deferred providers are asked too. The scanner, `Registry\Infrastructure\AttributeScanner`, reads the classes each `.php` file declares from its tokens, loads them through the autoloader and reads `#[Command]` and `#[Hook]` with reflection; reflection is allowed at build time only (GUARDRAILS 2.2). Commands are sorted by name and version, and hooks by command, phase in pipeline order, priority with the lowest first, package and class. A `#[Command]` class must be `final readonly` (GUARDRAILS 2.1), or the build fails with `registry_not_final_readonly`; `#[Hook]` is checked only through its attribute (a `#[Command]` class, a budget of 1 to 20 ms), because the hook interfaces of GUARDRAILS 2.4 come with the pipeline in M1. A build with problems writes nothing and lists every problem with a code from `BuildErrorCode`, such as `registry_duplicate_command` and `registry_unknown_hook_command`; the command then exits 65, and 73 when a cache file cannot be written or removed. At run time the container's `CompiledRegistry` singleton is read through `RegistryCache` and the Boundary `RegistryCacheCodec` into typed entries in `Registry\Domain\Dto`; a missing file throws `RegistryCacheMissing` and a damaged one `MalformedRegistryCache`. A command's name, `CommandEntry::$name` and `HookEntry::$command`, is the id `Cbox\Cms\Contracts\Ids\CommandName` (GUARDRAILS 2.2), never a string: the scanner takes it from `Command::name()`, the codec parses it and reports a bad one at `entries[<n>].name` or `entries[<n>].command`, and the compiler compares names by value. A registry is a case of `RegistryName` only when it has an entry type and a source; the action (GUARDRAILS 2.1), subscriber (PRD 7.6), schema contribution (PRD 13.3) and slot (PRD 13.4) registries come with the blocks named in `PROGRESS.md`. The doctor's `registry.cache` check dates the cache by the oldest of the files of `RegistryName`. Composer's `post-autoload-dump` runs `testbench cms:build`, and the cache is not committed. The registry's test fixtures live in `packages/core/tests/Registry/Fixtures`, one directory per scan root.
