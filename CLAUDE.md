# laravel-cms

Monorepo for Cbox CMS: the kernel, packages, sidecars and JS packages. Nothing is pushed anywhere; there is no remote yet.

## Sources of truth

These live in the planning repo and are read-only unless a rule below says otherwise:

## Hard rules

- Never `git push`, never add a remote, never publish packages. Commit locally only.
- Never change the cboxdk ecosystem repos (laravel-id, laravel-telemetry and the others); use them as released. Lifting them is a separate track (GUARDRAILS 1.7). If a package lacks something, record it in `PROGRESS.md`.
- One commit per task, message `<block>-<task>: <what>`, for example `M1-T3: command envelope and idempotency store`.
- Follow GUARDRAILS 7.3: never weaken a check that verifies your own change (analysis config, test filters, snapshots, architecture tests, CI). If you believe a check is wrong, leave it, and add the case under "Til review af Sylvester" in `PROGRESS.md`.
- A bug fix has a regression test that fails before the fix.
- Everything committed is production-ready (GUARDRAILS 11). No placeholders: no temporary or provisional formats, no hard-coded or "not implemented" bodies, no TODO/FIXME/XXX, no skipped tests, no gates reported as not run because work is missing. If something cannot be finished in its block, do not build it; record it in `PROGRESS.md`. Fakes for contracts are not placeholders.
- The kernel knows no content types (GUARDRAILS 2.4). Every type, field, block type and capability is defined in schema files (Data Studio, a template or starter, a module or addon's own types, or `workbench/` fixtures). The kernel packages (contracts, core, testkit, generators, http, cli) never name a type, field or route and never assumes one such as `page` or `article` exists; everything works for any type from its schema.
- PHP 8.5, Laravel 13 only, PHPStan level 10 without baseline, Pest 5, Rector, Pint, React 19 with strict TypeScript.
- Run `composer check` before saying a task is done. It is the local profile of GUARDRAILS 10: gates 1 to 6 in order (Pint and Prettier, Rector, PHPStan, tsc and ESLint, the Pest suites, `check:generated`), every gate also after a failure, each marked pass, fail or not run, and it exits 1 when a gate fails. Start the services first with `composer services:up`, which also converges an existing Postgres volume with the init script; with Postgres or Valkey down, gate 5 fails, it is never skipped. Gates 7 to 11 show as not in the local profile. `composer check -- --report=<file>` also writes a JSON report, `--brief` leaves the output of failed steps out of the console. Report the gates you ran and any that did not run.
- CI is `bin/ci`, the single entry script: `.github/workflows/ci.yml` runs it on every pull request, and `docker compose -f compose.ci.yaml run --rm ci` runs it locally in a container on a clean git archive of HEAD (commit first; `docker compose -f compose.ci.yaml down` stops its services). It installs the locked dependencies and runs `composer check -- --pr`: the same scripts as `composer check`, plus the `Mutation` suite and mutation on changed files in gate 5, gate 8 (the Browser suite) and gate 9 (`composer audit --locked --abandoned=report` and `npm audit`), with gates 7, 10 and 11 reported as not run. Mutation on changed files needs `CMS_CI_BASE_REF`, the base of the change: `ci.yml` sets it to the pull request's base commit (the commit before the push for a push to main) and checks out with `fetch-depth: 0`; for the containerized run, set it on the host, as in `CMS_CI_BASE_REF=HEAD~3 docker compose -f compose.ci.yaml run --rm ci`, and `docker/ci-entry.sh` builds the archive as two commits, the merge base's tree and HEAD's, with `CMS_CI_BASE_REF=HEAD~1` inside. Unset, empty or unknown, the mutation step fails with the reason. Before `bin/ci`, `docker/ci-setup.sh` runs from the checkout in both places; it fails when PCOV is not loaded, and gives the image Chromium for the Playwright that `package-lock.json` pins, and fails when it cannot. Every action in `ci.yml` is pinned to a commit SHA with its tag as a comment. It never runs the gates as root, because the tests of file permissions skip as root. Run the containerized run after changing `bin/ci`, the CI files or the environment the gates need, and record its wall time in `PROGRESS.md` against the 15-minute budget of GUARDRAILS 10.
- Run `composer check:selftest` after changing a gate, the tool configuration or the check itself. It makes a git worktree of HEAD in the system temp directory, runs `composer install` and `npm ci` there, plants one known violation per gate and passes only when each gate fails with a path inside the worktree; then it removes the worktree. It checks HEAD, so commit first. It takes about four minutes. The worktree's suites run in the worktree's own test database, and the selftest drops it as the owner role before it removes the worktree, also after a failure, so it can run next to the suites of another checkout.
- The JS gates run from the root after `npm ci`: `npm run typecheck`, `npm run lint` and `npm run format:check`. The shared tsconfig, ESLint and Prettier configuration lives in the `js/tooling` workspace; the root files only point at it.
- The Pest suites are gate 5 of GUARDRAILS 10: `Unit`, `Codecs`, `Contract`, `Postgres`, `Arch` and `Actions` in `phpunit.xml`. A package puts tests for a suite in `packages/<package>/tests/<Suite>`; its other tests are `Unit`. The `Postgres` suite needs `composer services:up` and runs through the testkit's `RealPostgres` harness: this checkout's own test database, `cms_test_<hash of the checkout's path>`, created by the owner role when it is missing (see "Hvor ting bor"), the app role on the default connection, migrations by the owner role, no wrapping transaction, the owner truncates after each test, and a nested transaction fails the test. Helpers: `app(IndependentConnections::class)` and `app(ChildProcesses::class)`. The testkit's `RealValkey` harness runs there too: every Redis connection uses database index 15 and a key prefix per PHP process, `cms_test_<run id>_`, and the keys under it are removed with SCAN and UNLINK after each test and when the process ends. The run is `app(ValkeyRun::class)`.
- The `Browser` suite is gate 8 of GUARDRAILS 10: Pest 5 browser tests in `tests/Browser`, run with `vendor/bin/pest --testsuite=Browser`. It needs Playwright from `npm ci` and Chromium from `npx playwright install chromium`, run once per machine and again after Playwright's pin in `package.json` changes. The browser plugin serves the Testbench workbench application in-process on a free port, so a test calls `visit('/')` with a path; routes live in `workbench/routes/web.php` with the web middleware group, and a test may add its own with `Route::get()`. Each page test asserts its visible text, `assertNoConsoleLogs()` and `assertNoJavaScriptErrors()`. Screenshots of failures land in `tests/Browser/Screenshots`, which git ignores.
- The `Mutation` suite holds the tests that need a coverage driver, in `tests/Mutation`: mutation on changed files for real, on a scratch repository. PCOV is in the php container and the CI image, not on the host, so the local profile leaves the suite out (`LocalProfile::OTHER_SUITES`) and the PR profile runs it in gate 5. Run it with `docker compose exec php vendor/bin/pest --testsuite=Mutation`. Mutation on changed files itself runs the same way: `docker compose exec -e CMS_CI_BASE_REF=<base> php composer check -- --pr`. Both run in the main checkout's code, because the php container mounts the main checkout; run them from the main checkout, never from a linked worktree.
- Services for tests run in Docker on cboxdk images: `ghcr.io/cboxdk/postgres:18` and `ghcr.io/cboxdk/valkey:8`; PHP on `ghcr.io/cboxdk/php-baseimages/php-cli:8.5-bookworm-dev-v1`. Do not use Herd's Postgres for tests. Postgres 17 stays the minimum, so never use features that arrived in 18 (GUARDRAILS 1.2).
- `composer services:up` and `composer services:down` run `tools/bin/services.php` (module `Cbox\Cms\Tooling\Services`). It finds the main checkout from `git rev-parse --path-format=absolute --git-common-dir` and always runs docker compose with the main checkout's `compose.yaml` and `--project-directory`, so no container ever mounts a worktree. From the main checkout, services:up runs `up -d --wait` and then the idempotent `10-cms.sh`, and services:down stops the services and keeps the volumes. The services are shared by the main checkout and every linked worktree: from a worktree, services:up runs `up -d --wait --no-recreate postgres valkey`, so it never recreates a running container and never starts php, then runs `10-cms.sh`, and says that the php container mounts the main checkout; services:down refuses with exit 1. `docker compose exec php ...` therefore always runs the main checkout's code, not a worktree's: container-bound work, such as the Mutation suite with `docker compose exec php`, runs from the main checkout. `tests/Feature/Tooling/Ci/ServicesScriptTest.php` covers it with a fake docker.

## Hvor ting bor

The namespace layout for the layers of GUARDRAILS 2.5. The Arch suite (`vendor/bin/pest --testsuite=Arch`, files in `tests/Arch`) enforces it over `packages/*/src` and `workbench/app`. The Arch suite checks the "May not use" column and the only-use rules for Domain and Actions; the `mixed` and `array` column is enforced by the testkit's PHPStan rules in `packages/testkit/src/Phpstan`. This section is the same in `CLAUDE.md` and `AGENTS.md`; a test keeps them equal.

Code sits in a module below the package, and the layer is a namespace segment below the module: `Cbox\Cms\Core\Entries\Domain\Commands\ReleaseVariant`, `Cbox\Cms\Core\ReceiptStore\Adapter\PostgresReceiptStore`. A namespace is in a layer when one of its segments is the layer name, either as the last segment or with more segments below it. When several segments match, the innermost one decides: `Cbox\Cms\Http\Boundary\RequestParser` is Boundary. `Domain` does not match `DomainEvents`.

| Segment | What lives there | May use | May not use |
|---|---|---|---|
| `Domain` | value objects, enums, invariants, domain interfaces | the domain and the contracts | everything else, including `Illuminate\Http`, facades and Eloquent |
| `Domain\Commands`, `Domain\Queries`, `Domain\Dto`, `Domain\Receipts` | command and query DTOs, other DTOs, receipts and results | as Domain | as Domain; only `final readonly` classes, no enums or interfaces |
| `Actions` | write actions, query actions and planners | the domain, the contracts, other classes in Actions | the framework, the DB facade, connections; only `final readonly` classes |
| `Boundary` | HTTP parsers, config readers, JSON decoders, queue payloads | the domain, the contracts, the framework, `mixed` and `array` | actions, surfaces |
| `Adapter` | implementations of contracts that need the framework or Postgres: the receipt and idempotency stores and their row mappers, Eloquent casts, Inertia props | the domain, the contracts, the framework, `mixed` and `array` | actions, surfaces |
| `Infrastructure` | Eloquent models, migration support, the partition manager | the domain, the contracts, `Illuminate\Database`, casts in Adapter | `Illuminate\Http`, facades, actions, surfaces, `mixed` |
| `Jobs` | queue jobs; a surface | actions, DTOs, Boundary | Infrastructure, Adapter, Eloquent, the DB facade, connections |
| `Http` | the http package, `Cbox\Cms\Http`; a surface | actions, DTOs, Boundary | Infrastructure, Adapter, Eloquent |
| `Cli` | the cli package, `Cbox\Cms\Cli`; a surface. Artisan commands live in `Cli\Console`, never in a `Commands` namespace | actions, DTOs, Boundary | Infrastructure, Adapter, Eloquent |

More rules:

- The contracts package, `Cbox\Cms\Contracts`, is part of the domain and has no layer segments. The attributes `#[Stable]`, `#[Experimental]`, `#[Internal]`, `#[Command]`, `#[Action]` and `#[Hook]`, and the enums `Surface` and `Phase`, live in `Cbox\Cms\Contracts\Attributes`.
- `Commands`, `Queries`, `Dto` and `Receipts` namespaces sit only below `Domain` or in the contracts package.
- Every class, interface, trait and enum in `packages/*/src` carries exactly one of `#[Stable]`, `#[Experimental]` and `#[Internal]`. Service providers are `#[Internal]`.
- Outbound HTTP (Guzzle, the Http facade, HTTP clients, `curl_*`, sockets, `file_get_contents`) is allowed only in the gateway namespace `Cbox\Cms\Core\Egress`, which goes through the SSRF guard.
- `mixed`, untyped arrays and array shapes are allowed only in Boundary and Adapter. The PHPStan rules report them in parameters, returns, properties, template bounds and class PHPDoc tags as `cboxCms.mixed`, `cboxCms.untypedArray` and `cboxCms.arrayShape`. A typed array is `list<T>` or `array<K, V>` where neither K nor V is `mixed`; `Foo[]` and `array<Foo>` have no key type and count as untyped. Structured data is a DTO. Closures are checked on their native types only.
- Test code, meaning a namespace with a `Tests` segment or the global namespace of Pest files, is exempt from that rule. Code in `packages/*/src` and `workbench/app` therefore always declares a namespace without a `Tests` segment; the Arch suite checks it.
- `@phpstan-ignore` in any form is allowed only in Boundary and Adapter. The PHPStan rule `cboxCms.phpstanIgnore` reads the tokens of every analysed file, tests included, and a token scan in the Arch suite checks `packages/*/src` and `workbench/app`. The testkit's own PHPStan rules report errors that no ignore comment and no `ignoreErrors` entry can hide. `cboxCms.internalUse` comes from PHPStan's restricted usage rules and is an ordinary error.
- `#[Internal]` sits on a class, a method or a class constant. Code outside the `Cbox\Cms` namespace, the global namespace included, may not use it (GUARDRAILS 2.3). The testkit's PHPStan extensions report every use, in code and in PHPDoc, as `cboxCms.internalUse`. A Pest file in this repo that uses internals therefore declares a namespace below `Cbox\Cms`, such as `Cbox\Cms\Tests\Feature` or `Cbox\Cms\Core\Tests`.
- Actions and Jobs never manage transactions (GUARDRAILS 4.1, PRD 4.2): no `transaction`, `beginTransaction`, `commit`, `rollBack`, `savepoint` or `createSavepoint` on a connection, the database manager, PDO or the DB facade, and no string containing `SAVEPOINT`. The PHPStan rules report them as `cboxCms.transaction` and `cboxCms.savepoint`; test code is exempt.
- Ids are value objects (PRD 5.3). Outside Boundary and Adapter, a public method parameter named `$id` or ending in `Id`, and the return of a public method named `id()` or ending in `Id`, may not be a string, nullable or not. The PHPStan rule reports `cboxCms.stringId`; test code is exempt. A value object takes its string as `$value`, and a Boundary parses the string into it.
- Contracts live in `Cbox\Cms\Contracts` (GUARDRAILS 2.3). `CoreServiceProvider` binds each one as a singleton to the class in `cms.contracts` (defaults in `packages/core/config/cms.php`); an application overrides one entry at a time. Every contract has a fake in the testkit and a shared suite there, a trait such as `Cbox\Cms\Testkit\Clock\ClockContract`. A package runs it in `tests/Contract` with one PHPUnit class per implementation.
- Code asks the `Clock` contract for the time instead of reading the system clock; only a clock implementation reads it. `now()` is UTC with microseconds and is not monotonic. Tests use the testkit's `FakeClock` (`set`, `advance`, `freeze`).
- Code asks the `IdGenerator` contract for a new id instead of making a UUID itself. `next()` returns a `Cbox\Cms\Contracts\Ids\Uuid7`, and a typed id such as `ChangesetId` wraps it. The first 48 bits are the Clock's unix milliseconds; ids from one instance are strictly increasing, also when the clock repeats a millisecond or steps back. `Uuid7::lowestAt()` and `highestAt()` give the bounds of a millisecond for partition ranges. A bad string throws `InvalidUuid7`. Tests use the testkit's seeded `FakeIdGenerator`.
- The `ReceiptStore` contract (`Cbox\Cms\Contracts\ReceiptStore`) has `store(Receipt)`, `find(ChangesetId): ?Receipt` and `markProjection(ChangesetId, ProjectionStatus): bool`; the status names the projection. `store()` and `markProjection()` run on the caller's connection, inside the caller's transaction when one is open, and never begin, end or savepoint one. Only committed receipts are stored: a Rejected or DryRun receipt throws `UnstorableReceipt`, a second receipt for a changeset throws `DuplicateReceipt` (both in `Contracts\Consistency`). `markProjection()` is idempotent, an acknowledgement is final, and it returns false and changes nothing when no live receipt lists the projection. Expiry is logical: `find()` returns null once the Clock is later than `RetentionClass::expiresAt()`, the changeset id's time plus 7 days for Standard; Evidence has none. The testkit's `FakeReceiptStore` is the store and the harness; `session()` gives connections with `begin`, `commit` and `rollBack`. The shared suite `ReceiptStoreContract` takes a `ReceiptStoreHarness` that hands out `ReceiptStoreSession`s. Testkit code for the store lives in the module `ReceiptStore`, not `Receipts`, because of the category rule.
- The `IdempotencyStore` contract (`Cbox\Cms\Contracts\IdempotencyStore`) has `claim(IdempotencyScope, IdempotencyKey, ContentHash, WaitBudget): ClaimResult` and `complete(ClaimToken, ChangesetId)`, and no `release()`. Both run only inside the caller's open command transaction and throw `InvalidClaim` without one. `claim()` takes a claim on (scope, key) that lasts until that transaction ends, waiting at most the `WaitBudget` (0 to 5000 ms, real time, not the Clock) while another transaction holds it, and then looks up the completed record. The result is one of four final readonly classes in `Contracts\Idempotency`: `Fresh` (a `ClaimToken`), `Replay` (the stored `ChangesetId`; the caller resolves the receipt through the `ReceiptStore`), `Conflict` (`Conflict::CODE` is `idempotency_conflict`) or `InFlight` (the budget ran out; holds nothing). Every result but `InFlight` holds the claim. `complete()` writes the record in the same transaction, so a rollback, or a commit without `complete()`, leaves the key fresh. A record expires with the Standard receipt of its changeset, `RetentionClass::Standard->expiresAt()`. The testkit's `FakeIdempotencyStore` is the harness; its `session()` is the fake store, and `whenWaiting()` schedules what happens while a contested claim waits. The shared suite `IdempotencyStoreContract` takes an `IdempotencyStoreHarness` of `IdempotencyStoreSession`s. Both session interfaces extend `Cbox\Cms\Testkit\Sessions\TransactionalSession`, so one session for a real database can serve both stores.
- The receipt and idempotency types live in the contracts package, because the store contracts take them and the contracts package depends only on PHP: `Receipt` and `ProjectionStatus` in `Cbox\Cms\Contracts\Receipts` (final readonly DTOs), the enums `Outcome`, `WaitLevel`, `RetentionClass` and `ProjectionState` with `ProjectionName` and `InvalidReceipt` in `Cbox\Cms\Contracts\Consistency`, `ChangesetId`, `PrincipalId` and `CommandName` in `Cbox\Cms\Contracts\Ids`, and `IdempotencyKey`, `IdempotencyScope`, `ContentHash` and `PrincipalKind` in `Cbox\Cms\Contracts\Idempotency`. A committed outcome requires a `ChangesetId`; the others forbid one. An `IdempotencyScope` is a `PrincipalKind`, a `PrincipalId` (the actor's or source's id, 1 to 255 visible ASCII characters, compared exactly; `InvalidPrincipalId` otherwise) and a `CommandName` (the name from `#[Command]` without the version, in the form of `Command::NAME_PATTERN`; `InvalidCommandName` otherwise), and takes no string. No code serialises a receipt to JSON; the JSON form comes with the codecs M1 generates (GUARDRAILS 2.2). A `Receipts` segment anywhere in a namespace makes it the Receipts category, so a core module for the stores cannot be called `Receipts`.
- Range partitions are kept by the partition manager in `Cbox\Cms\Core\Partitions` (PRD 4, 4.2). A partitioned table is listed in `cms.database.partitions.tables` with its key (`uuid7`: bounds are `Uuid7::lowestAt()` of the span's first millisecond and of the next span's; or `timestamp`), its interval (`day` or `month`, spans start at midnight UTC) and `retention_days` (null keeps all). Partitions are named `<table>_p<YYYYMMDD>` or `<table>_p<YYYYMM>`, and only those names are managed. There is no DEFAULT partition, so a write outside the partitions fails; an adapter that writes to a partitioned table catches the `QueryException` and throws `MissingPartitionMapper::map()`, which turns SQLSTATE 23514 "no partition of relation" into `Cbox\Cms\Contracts\Storage\PartitionMissing` (`CODE` `partition_missing`). `cms:partitions:maintain` (scheduled hourly by `CoreServiceProvider`) runs the action `MaintainPartitions` at the Clock's time: it creates partitions from now to `runway_days` ahead (default 14) and removes partitions past retention with `DETACH PARTITION CONCURRENTLY` and `DROP TABLE`, never `DELETE`. A new partition gets its parent's row security flags and its parent's grants (`TablePrivileges::copy()`), so the owner's default privileges never reach a partition. It runs only on `cms.database.owner_connection` and throws `OwnerConnectionRequired` on the app connection. Every step runs with `lock_timeout` 2 s and a bounded retry with backoff, and gives up with `LockTimeout`. `--from` and `--to` only create the partitions of a range. A run's report gives each table's runway from the Clock's time, with or without `--from` and `--to`: the end of the unbroken run of attached partitions from the partition that holds now, so a gap ends it. `Partitions\Domain\PartitionRunway::end()` computes it for the report and for the doctor's `partitions.runway`. Tests that write to a partitioned table first call the testkit's `app(PartitionFixtures::class)->cover($from, $to)` or `coverClock($clock, $interval)` for the dates they write at.
- The receipt store on Postgres is `Cbox\Cms\Core\ReceiptStore\Adapter\PostgresReceiptStore`, bound to `ReceiptStore` in `cms.contracts`. It runs on the default connection (or a named one), through the query builder, and never begins a transaction. Its tables come from the core migration `packages/core/database/migrations/*_create_receipts_tables.php`: `receipts` (one row per changeset) and `receipt_projections` (one row per changeset and projection), both LIST-partitioned on `retention_class` and then RANGE-partitioned on `changeset_id`, managed as `receipts_standard` and `receipt_projections_standard` (per day, `retention_days` 7) and `receipts_evidence` and `receipt_projections_evidence` (per month, never dropped). The primary keys are `(changeset_id, retention_class)` and `(changeset_id, retention_class, projection)`; there is no foreign key between them. `find()` and `markProjection()` filter on the Clock's live window (`PostgresReceiptStore::lowestLiveStandard()`), `markProjection()` updates only a pending row, and `store()` reports a duplicate with `ON CONFLICT DO NOTHING` without aborting the caller's transaction. The Postgres contract test is `packages/core/tests/Postgres/PostgresReceiptStoreContractTest.php`; it and the adapter tests cover the dates they write at with `PartitionFixtures`.
- The idempotency store on Postgres is `Cbox\Cms\Core\IdempotencyStore\Adapter\PostgresIdempotencyStore`, bound to `IdempotencyStore` in `cms.contracts`. It runs on the default connection (or a named one), inside the caller's transaction, and never begins one. Its table comes from the core migration `packages/core/database/migrations/*_create_idempotency_keys_table.php`: `idempotency_keys`, RANGE-partitioned per day on `created_at` and managed with `retention_days` 7, with an index on `lock_key`, no primary or unique key, and SELECT and INSERT for the app role. Postgres cannot keep a key unique across daily partitions, so a claim is a transaction-scoped advisory lock on `ClaimLock::of($scope, $key)`, the first 64 bits of a versioned SHA-256 of the scope and key: `pg_try_advisory_xact_lock` polled with a growing sleep (2 ms up to 50 ms) until it is granted or the `WaitBudget` has passed, never a blocking lock or `lock_timeout`, which would abort the caller's transaction. The lookup is a separate statement after the lock, so under READ COMMITTED it sees a commit made while the claim waited; a claim at another isolation level throws `InvalidClaim::isolationLevel()` and takes no lock. The lookup matches the full scope and key, so a lock key collision only makes two keys wait for each other. A Fresh claim is noted in the transaction-local setting `cbox_cms.idempotency_claims`, which `complete()` checks and Postgres resets when the transaction ends. `created_at` is the Clock's time, or the changeset's time when that is later, and `expires_at` is `RetentionClass::Standard->expiresAt()`; the CHECK `idempotency_keys_window` keeps `expires_at` within 168 hours of `created_at`, so the lookup window, `PostgresIdempotencyStore::window()`, from 7 days before the Clock's time to the end of its UTC day, holds every live record and scans 8 partitions. The Postgres contract test is `packages/core/tests/Postgres/PostgresIdempotencyStoreContractTest.php`.
- The registry (PRD 13.2) is compiled by `cms:build` (the cli's `Console\BuildCommand`, which calls the action `Cbox\Cms\Core\Registry\Actions\BuildRegistry`) to `bootstrap/cache/cms/`: `actions.php`, `commands.php` and `hooks.php`, one per case of `Registry\Domain\RegistryName`. The cache owns that directory: after writing the files, `FileRegistryCache` removes every other file there, but not subdirectories or the temporary file of a concurrent build, so a registry an earlier version wrote cannot linger. Each file returns `['entries' => [...], 'format' => 1, 'registry' => '<name>']`, sorted and without timestamps or paths, so two builds of the same code give the same bytes. A package's service provider implements `Cbox\Cms\Contracts\Build\DeclaresScanRoots` and returns `ScanRoot`s, each a Composer package name and an absolute directory (`__DIR__`); core, http, cli and generators declare their `src`, and deferred providers are asked too. The scanner, `Registry\Infrastructure\AttributeScanner`, reads the classes each `.php` file declares from its tokens, loads them through the autoloader and reads `#[Action]`, `#[Command]` and `#[Hook]` with reflection; reflection is allowed at build time only (GUARDRAILS 2.2). Commands are sorted by name and version, actions by class, and hooks by command, phase in pipeline order, priority with the lowest first, package and class. A build with problems writes nothing and lists every problem with a code from `BuildErrorCode`, such as `registry_duplicate_command` and `registry_unknown_hook_command`; the command then exits 65, and 73 when a cache file cannot be written or removed. At run time the container's `CompiledRegistry` singleton is read through `RegistryCache` and the Boundary `RegistryCacheCodec` into typed entries in `Registry\Domain\Dto`; a missing file throws `RegistryCacheMissing` and a damaged one `MalformedRegistryCache`. A registry is a case of `RegistryName` only when it has an entry type and a source; the subscriber (PRD 7.6), schema contribution (PRD 13.3) and slot (PRD 13.4) registries come with the blocks named in `PROGRESS.md`. The doctor's `registry.cache` check dates the cache by the oldest of the files of `RegistryName`. Composer's `post-autoload-dump` runs `testbench cms:build`, and the cache is not committed. The registry's test fixtures live in `packages/core/tests/Registry/Fixtures`, one directory per scan root.
- The type chain (PRD 11.12) is generated by `cms:generate`, the generators package's `Cli\Console\GenerateCommand`, which calls the action `Cbox\Cms\Generators\Generation\Actions\GenerateCode`. In milestone 0 it reads one schema file in the provisional format `format: m0-provisional` (types with `handle`, `label` and at least one field, fields with `handle` and `type`, every handle lowercase snake_case of at most 63 characters); the format does not pre-empt M1's blueprint schema v1. The workbench's schema is `workbench/schema/fixture.yaml`, and `WorkbenchServiceProvider` points `cms.generators` at it. The M0 generators write a PHP enum `TypeHandle` with `fields()` to `workbench/app/Cms/Generated` and the TypeScript union `TypeHandle` with the interface `TypeFields` to `workbench/resources/js/cms/generated/index.ts`; both are committed and never edited by hand. A generator implements `Cbox\Cms\Generators\Generation\Domain\Generator` (`#[Internal]`, not a contract, so no fake), is a pure function of the schema and the target, and owns a directory named `Generated` or `generated`: the `GeneratorRunner` sorts the output, and cms:generate writes only files whose bytes differ and removes the other files in the owned directories. Output is sorted and has no timestamps or absolute paths. Errors carry a code from `GenerateErrorCode`, such as `generate_schema_invalid`, and the command exits 65 for an invalid schema, 66 for a missing one, 69 without symfony/yaml, 70 for invalid generator output, 73 when a file cannot be written and 78 for invalid configuration. Gate 6 is `composer check:generated`: it fails on unstaged changes or untracked files under the generated paths, runs cms:generate, and checks again. symfony/yaml is a root `require-dev` and only a `suggest` of `cboxdk/cms-generators` until that is decided; `packages/generators/tests/DependenciesTest.php` fails when the generators' src uses a package that is neither required nor suggested.
- `cms:doctor` (the cli's `Console\DoctorCommand`, which calls the action `Cbox\Cms\Core\Doctor\Actions\RunDoctor`) checks the installation and the runtime contract (PRD 3.3, 4.2, 13.2). A check implements the contract `Cbox\Cms\Contracts\Doctor\DoctorCheck`: `id()` (a `CheckId` such as `postgres.reachable`), `blocking()` (whether the kernel may not start while it fails; not blocking means readiness only), `requires()` (checks listed earlier that must pass, or the doctor skips it) and `run()`, which only looks, never throws and returns a `CheckResult`: Pass, or Fail with a `FailureKind` (`Violation` or `Unavailable`), an error code, the cause and the fix. Skip comes only from the doctor, and a check that throws becomes the failure `doctor_check_crashed`. The exit codes are defined once, in `Contracts\Doctor\DoctorExitCode`: `Ok`, `Unavailable` (EX_TEMPFAIL) and `Violation` (EX_CONFIG); a violation wins, and every failure counts, blocking or not. M1 folds them into the error catalog. `--json` prints the document described by `packages/contracts/resources/schemas/doctor.v1.json`, encoded by the Boundary `DoctorReportJson` with every key present and keys sorted; the Codecs suite validates it with opis/json-schema. The core's checks live in `Core\Doctor\Domain\Checks` and ask `#[Internal]` probe interfaces in `Doctor\Domain\Probes`, implemented in `Doctor\Adapter`; a test swaps a probe by binding its interface, with the fakes in `packages/core/tests/Doctor/Fakes`. The runtime checks are `php.version`, `laravel.version`, `postgres.reachable`, `postgres.version`, `postgres.app_role`, `postgres.transaction_timeout` (above zero and from the role, read from `pg_settings.source`), `postgres.prepared_transactions`, `postgres.lc_messages` (lc_messages of the app role and of the owner role, and LC_MESSAGES of the PHP process, which libpq follows, must be `C`, `POSIX`, `C.<charset>` or `en_*`, because `MissingPartitionMapper` and `PostgresErrors` match English text; `docker/postgres/conf.d/cms.conf` sets `lc_messages = 'C'` as the server default and `roles.sql` on both roles), `postgres.ddl_privileges`, `valkey.reachable`, `partitions.runway` (not blocking; the unbroken run of partitions from now must reach `partition_runway_days` ahead) and `registry.cache` (not older than `vendor/composer/installed.json`); `--dev` adds `dev.node`, `dev.playwright` and `dev.chromium`, which do not block. The Postgres probes share the scoped connection `cms_doctor`, a copy of the app role's connection with `PDO::ATTR_TIMEOUT`, because pdo_pgsql ignores `connect_timeout` in the DSN; `postgres.lc_messages` also reads the owner role on `cms_doctor_owner`, a copy of `cms.doctor.owner_connection` (null means `cms.database.owner_connection`). The settings are `cms.doctor`; an invalid one gives the single failing check `doctor.config`. The testkit has `FakeDoctorCheck` and the shared suite `DoctorCheckContract`, which every core check runs in `packages/core/tests/Contract` with fake probes.
- The actions' ports that are not contracts (`PartitionMaintenance`, `DeclarationScanner`, `RegistryCache`, `DoctorChecks`, `SchemaSource`, `GeneratedOutput`) have hand-written fakes in `packages/<package>/tests/<Module>/Fakes`, as the doctor's probes do, and no fakes in the testkit. Each fake is held to the real implementation by a behaviour trait `<Port>Behaviour` in `packages/<package>/tests/<Module>`, which a test class per implementation uses, named `<Implementation><Port>BehaviourTest` or `Fake<Port>BehaviourTest`: each in the suite its implementation needs: `PostgresPartitionMaintenanceBehaviourTest` in `Postgres`, the rest next to the trait in `Unit`, because the ports are not contracts and `Contract` holds the contracts' shared suites. `vendor/bin/pest --filter=<Port>Behaviour` runs both. The action tests are the `Actions` suite, in `packages/<package>/tests/Actions` (`BuildRegistryTest`, `MaintainPartitionsTest`, `RunDoctorTest`, `GenerateCodeTest`): each calls its action directly with its DTOs and these fakes (GUARDRAILS 9) and covers success, rejection and, where the action has one, the conflict. An action takes DTOs from its module's `Domain\Dto`, never primitives: `MaintainPartitions::cover(PartitionRange)`, `RunDoctor::run(DoctorRunOptions)` and `BuildRegistry::build(ScanRoots)`; a cli command builds them in a Boundary (`Cli\Boundary\PartitionRangeOptions`, `Cli\Boundary\DoctorOptions`, the core's `Registry\Boundary\ProviderScanRoots`). `DoctorChecks` is the port, and `OrderedDoctorChecks` the list `CoreServiceProvider` builds.
- The gate runner behind `composer check` and `composer check:selftest` is monorepo tooling in `tools/` (`Cbox\Cms\Tooling`, autoload-dev, entry scripts in `tools/bin`), not a package. PHPStan, Rector and Pint cover it; the Arch suite does not, as for `tests/Support`. `Check\Domain\LocalProfile` defines the gates: each gate runs the Composer or npm script a developer runs by hand (`lint:check`, `format:check`, `rector:check`, `analyse`, `typecheck`, `lint`, `check:generated`), and gate 5 runs `vendor/bin/pest --testsuite=<suite> --fail-on-skipped --fail-on-incomplete` for each suite. A new suite in `phpunit.xml` must be added there; a test fails until it is. `Check\Domain\PrProfile` is the PR profile as CI runs it (`composer check -- --pr`, from `bin/ci`): the same steps for gates 1 to 6, with gate 5 adding the `Mutation` suite and mutation on changed files, gate 8 and gate 9, and each gate CI does not run yet as not run with its reason. Mutation on changed files is the module `Cbox\Cms\Tooling\Mutation`: `Boundary\GitMutationScope` finds the PHP files below `packages/*/src` added or changed between the merge base of `CMS_CI_BASE_REF` and HEAD and the class, enum, interface or trait each declares; `Domain\MutationSteps` makes the steps: `vendor/bin/pest --mutate --everything --path=<files> --min=80 --ignore-min-score-on-zero-mutations` with PCOV from `tools/mutation/pcov.ini` (through `PHP_INI_SCAN_DIR`, because the image loads PCOV but leaves it off), for classes in Adapter and Infrastructure serially against the fast suites and `Postgres`, for the others with `--parallel` against `Unit`, `Codecs`, `Contract`, `Actions` and `Arch`. In pest-plugin-mutate 5, `--everything` ignores `--class`, so the files are named with `--path`. No changed file passes the step with "0 changed classes"; a missing base fails it. The Pest plugin `Mutation\Adapter\PestMutationReport`, in `composer.json`'s `extra.pest.plugins`, prints each file's mutations and caught mutations on one line when `CMS_MUTATION_REPORT=1`, and `Domain\MutationReportReader` lists each class with its score and fails the step below 80 over all its mutations, naming the classes below 80. A step can carry variables of its own (`Step::run(..., environment: [...])`) and can be decided without a command (`Step::passed()`, `Step::failed()`). A test that starts a Pest run of its own clears the parallel worker's variables (`tests/Support/Tooling/ParallelWorker`), because the fast suites run in parallel workers there. Gate 8's step runs Pest in a process group of its own (`Step::run(..., ownProcessGroup: true)`, started through `tools/bin/process-group.php`), and the runner kills what is left of the group when the step ends, so a `playwright run-server` left by a dead Pest cannot hold the output open. Gate 9's composer audit step has an `OutputReader`, `ComposerAuditReader`: any advisory fails it, and abandoned packages pass and are listed as notes below the step in the summary and the report. `.github/workflows/ci.yml` has only setup steps besides `bin/ci`, uses the PHP image and the Postgres and Valkey images of `compose.yaml`, and gives `bin/ci` the same environment as the ci service of `compose.ci.yaml`; `tests/Feature/Tooling/Ci` holds them to each other. The environment never has `POSTGRES_*` variables, because Testbench copies them into the pgsql connection; the superuser is `CMS_CI_POSTGRES_SUPERUSER`. The selftest's violations are `Selftest\Domain\Plants`, at least one per gate, planted in the module `packages/core/src/Selftest`, which must never exist in the repository.
- Each checkout, a git worktree included, runs its tests in a Postgres test database of its own, so parallel worktrees never share rows. The name is `TestDatabaseName::for($base, $root)` in the testkit's module `Cbox\Cms\Testkit\Postgres`: the configured database (`DB_DATABASE`, `cms_test`), `_`, and the first 12 hex digits of the SHA-256 of the real path of the checkout root, the directory of the Composer root package of the autoloader that loads the testkit (`Boundary\CheckoutRoot`); at most 63 bytes. `tests/TestCase.php` points every pgsql connection that names the configured database at it before the first connection opens (`Boundary\CheckoutConnections::point()`), so the owner connection, `IndependentConnections`, `ChildProcesses` and the doctor's `cms_doctor` and `cms_doctor_owner` follow; the `RealPostgres` harness does it too and then calls `TestDatabase::ensure()`, which runs `TestDatabase::provision()` once per process and keeps a failure, before `migrate:fresh`. `provision()` is the one entry point, also for a child process with another root (`TestDatabase::command()`, `packages/testkit/bin/test-database.php`, payload `Boundary\TestDatabasePayload` on stdin): it connects as the owner role to the configured database, fails fast when the server does not answer or the owner role lacks CREATEDB (the message names the role, CREATEDB, the database and `composer services:up`), and under a transaction-scoped advisory lock on the configured database (`Infrastructure\PostgresTestDatabases::lockKey()`) runs `Infrastructure\TestDatabaseSetup`, a copy of `docker/postgres/sql/database.sql` with the role names and the schema read from the connections, where SQLSTATE 42P04 on CREATE DATABASE counts as done; then it records `{"checkout": <real path>, "host": <gethostname()>}` with COMMENT ON DATABASE (`Boundary\TestDatabaseComment`). `tests/Feature/Tooling/TestDatabaseSetupTest.php` holds the copy equal to the file, statement for statement. `TestDatabase::drop()` drops a checkout's database; `composer check:selftest` drops its worktree's through `tools/bin/drop-test-database.php`, which reads the owner connection from `phpunit.xml` and the environment (`Cbox\Cms\Tooling\TestDatabase\Boundary\PhpunitDatabase`). The owner role has CREATEDB in `docker/postgres/sql/roles.sql`, which is for development, tests and CI only, and `composer services:up` runs the idempotent init script again after `up --wait`, so an existing volume gets it. A test that starts `vendor/bin/testbench` against the database passes `DB_DATABASE` of the checkout's database. Two processes of one checkout share its database.
- Gate tools keep their caches in the checkout, in the git-ignored `.cache/` with a directory per tool, never in the shared system temp directory, so parallel worktrees and the selftest's worktree never share them: PHPStan's `tmpDir` is `.cache/phpstan` (`phpstan.neon`; result cache, container cache and Larastan's migration cache), Rector's file cache is `.cache/rector/files` and the container cache of its PHPStan `.cache/rector/container` (`rector.php` creates that one, because Rector requires it to exist), and Pint's cache file is `.cache/pint/pint.cache` (`pint.json`, relative to the root, where the Composer scripts run it). PHPUnit's cache stays in `.phpunit.cache`, and the mutation plugin's in `vendor/pestphp/pest-plugin-mutate/.temp`, both in the checkout already. tsc, ESLint and Prettier run without a cache; a cache for one of them gets a directory in `.cache/` first. The only file a gate leaves in the system temp directory is the PHPStan boot lock, named by a hash of the checkout's path, and paratest's worker files, named per run and removed at its end. `tests/Feature/Tooling/ToolCachesTest.php` holds the configuration to this and runs each tool with `TMPDIR` pointed at an empty directory.
- Migrations live in `packages/<package>/database/migrations`, run as the owner role and may use raw SQL. A migration whose table needs less than the owner's default privileges (SELECT, INSERT, UPDATE and DELETE for the app role) narrows them with `Cbox\Cms\Core\Database\Infrastructure\TablePrivileges::limitTo()`, which applies to every partition below the table and names no role. The receipt tables give the app role SELECT and INSERT on `receipts` and SELECT, INSERT and UPDATE on `receipt_projections`, and `idempotency_keys` gives it SELECT and INSERT. Every foreign key has a non-partial index that leads with its columns (PRD 4.1); `tests/Postgres/ForeignKeyIndexTest.php` checks the whole schema.
- Raw SQL (GUARDRAILS 6) is allowed only in migrations and in the Infrastructure and Adapter layers; everything else uses the query builder. The testkit's PHPStan rule reports `cboxCms.rawSql`, non-ignorable, for the SQL-taking methods of a connection, the database manager and the DB facade (`select`, `statement`, `raw` and the like), the `*Raw` methods of the query and Eloquent builders, relations and models, `query`, `exec` and `prepare` on PDO, and `new Expression`. Test code and the global namespace, where migrations live, are not checked. The testkit's own raw SQL lives in `Cbox\Cms\Testkit\Postgres\Infrastructure`.
- Facades are imported by their full class name. Global aliases such as `\DB` and real-time facades are not allowed.
- A service provider at the package root has no layer. It wires contracts to adapters. A namespace without a layer segment has only the global rules; put code in a layer.
- `declare(strict_types=1)` in every PHP file, and no `dd`, `dump`, `ddd`, `ray` or `var_dump`.

## When the PRD is unclear

- If the PRD is ambiguous but one reading is clearly consistent with the rest of the PRD and GUARDRAILS, pick it, implement it, and record the interpretation under "Tolkninger" in `PROGRESS.md`.
- If the PRD needs a small correction to be buildable, edit `PRD.md` in the planning repo, add a version entry at the top of its section 0, and commit it there with message `PRD v2.x: ...`.
- If it is a decision reserved for Sylvester (the open questions in PRD section 26, product scope, naming, licensing, anything outward-facing), do not decide. Add it under "Blokeret" in `PROGRESS.md` with what it blocks, and continue with work that does not depend on it.

## Autopilot

`.harness/autopilot.on` switches on the stop guard in `.harness/stop-hook.sh`. While it is on, a session may not stop until `PROGRESS.md` says `STATUS: complete` or `STATUS: blocked`. `.harness/waiting` marks that a background workflow is running and lets the session idle until it reports back. The workflow for one block is `.claude/workflows/cms-milestone.js`.

Delete `.harness/autopilot.on` to stop autopilot.
