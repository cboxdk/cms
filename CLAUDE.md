# laravel-cms

The repository of the one Composer package `cboxdk/cms` (GUARDRAILS 2.6, PRD 2.32), with the kernel's modules in `packages/<module>` (see "Modules" under "Hvor ting bor"), the JS workspaces in `js/` and, as they come, the sidecars. The remote is `origin`, github.com/cboxdk/cms.

## Sources of truth

These live in the planning repo and are read-only unless a rule below says otherwise:

- `/Users/sylvester/Projects/Cbox/cms-planning/PRD.md`: what is built (Danish).
- `/Users/sylvester/Projects/Cbox/cms-planning/GUARDRAILS.md`: how code is written. Every rule applies here.

## Hard rules

- Push to `origin` (github.com/cboxdk/cms) is allowed; never force-push, never rewrite pushed history, never publish packages or tag releases without Sylvester.
- Never change the cboxdk ecosystem repos (laravel-id, laravel-telemetry and the others); use them as released. Lifting them is a separate track (GUARDRAILS 1.7). If a package lacks something, record it in `PROGRESS.md`.
- One commit per task, message `<block>-<task>: <what>`, for example `M1-T3: command envelope and idempotency store`.
- Follow GUARDRAILS 7.3: never weaken a check that verifies your own change (analysis config, test filters, snapshots, architecture tests, CI). If you believe a check is wrong, leave it, and add the case under "Til review af Sylvester" in `PROGRESS.md`.
- A bug fix has a regression test that fails before the fix.
- Everything committed is production-ready (GUARDRAILS 11). No placeholders: no temporary or provisional formats, no hard-coded or "not implemented" bodies, no TODO/FIXME/XXX, no skipped tests, no gates reported as not run because work is missing. If something cannot be finished in its block, do not build it; record it in `PROGRESS.md`. Fakes for contracts are not placeholders.
- The kernel knows no content types (GUARDRAILS 2.4). Every type, field, block type and capability is defined in schema files (Data Studio, a template or starter, a module or addon's own types, or `workbench/` fixtures). The kernel's modules (contracts, core, testkit, generators, http, cli, mcp) never name a type, field or route and never assumes one such as `page` or `article` exists; everything works for any type from its schema.
- PHP 8.5, Laravel 13 only, PHPStan level 10 without baseline, Pest 5, Rector, Pint, React 19 with strict TypeScript.
- Run `composer check` before saying a task is done. It is the local profile of GUARDRAILS 10: gates 1 to 6 in order (Pint and Prettier, Rector, PHPStan, tsc and ESLint, the Pest suites, `check:generated`), every gate also after a failure, each marked pass, fail or not run, and it exits 1 when a gate fails. Start the services first with `composer services:up`, which also converges an existing Postgres volume with the init script; with Postgres or Valkey down, gate 5 fails, it is never skipped. Gates 7 to 11 show as not in the local profile. `composer check -- --report=<file>` also writes a JSON report, `--brief` leaves the output of failed steps out of the console. Report the gates you ran and any that did not run.
- The gates run in the php-baseimages dev image `ghcr.io/cboxdk/php-baseimages/php-cli:8.5-bookworm-dev-v1` (PHP 8.5, PCOV, Xdebug, Node 22, Playwright's Chromium in `/ms-playwright`), locally as in CI (Sylvester, 30 September). `composer check` started on the host checks its options and runs itself again in a container of the image (module `Cbox\Cms\Tooling\DevImage`, `DevImageRun`), for the current checkout, a linked worktree included: the checkout is mounted at its own absolute path and is the working directory, so the testkit derives the checkout's own test database and the reports name host paths; a linked worktree also gets the main checkout's `.git` at its path; `node_modules` is a Docker volume of the checkout's own, `laravel-cms-node-modules-<12 hex digits of the SHA-256 of the checkout's path>`, which `tools/bin/dev-image-entry.php` fills with `npm ci` in the image whenever `package-lock.json` changed (the host's `node_modules` holds macOS binaries); the host's `~/.pest` is `/tmp/.pest` with `HOME=/tmp`; it runs as the host user's uid and gid with the host's name, never as root; `.cache` and the Testbench application's bootstrap cache are Docker volumes of the checkout's own too (`VolumeKind`), because on Docker Desktop's bind mount a file another process replaces with a rename is missing for a moment to a reader in the container, and parallel workers then failed to open PHPStan's container or `bootstrap/cache/services.php`; the entry mirrors the host's bootstrap cache, mounted read-only, into its volume at the start of each run; and it joins the network of the main checkout's `compose.yaml` and reaches the services as `postgres` and `valkey`. It never starts or recreates them: when Postgres or Valkey is not running and healthy, it fails with exit 1 and says to run `composer services:up` in the main checkout. A report file outside the checkout has its directory mounted too. A process already in the image, where the image's `CBOX_IMAGE_TIER` is `dev` (CI, the php service, the container itself), runs the gates in place. `composer image:run -- <command>` runs any command the same way, such as `composer image:run -- vendor/bin/pest --testsuite=Browser` or `--testsuite=Mutation`, and `composer image:prune [-- --dry-run]` removes the volumes (`laravel-cms-<node-modules|cache|bootstrap-cache>-<hash>`, labelled with the checkout's path) of checkouts that are gone (`composer check:selftest` removes its own). `tests/Feature/Tooling/DevImage` covers the docker command with a fake docker.
- `composer test:affected [-- <pest arguments>]` is fast feedback while working, not a gate: in the dev image, `vendor/bin/pest --parallel --tia` with Pest 5's test impact analysis, which records per test the files and tables it touches through PCOV (`tools/tia/pcov.ini`) in the graph below `~/.pest/tia`, and then reruns only the tests that depend on what changed and replays the rest. The analysis takes Pest files only and stops at a PHPUnit test class, so `tools/bin/test-affected.php` runs the Pest files with `--tia` from `.cache/test-affected/pest.xml` and then every PHPUnit test class, such as the contract suites' classes, from `.cache/test-affected/classes.xml`, both derived from `phpunit.xml` (`Affected\Boundary\PhpunitConfiguration`). An argument that selects tests, such as `--filter` or `--testsuite`, makes Pest run the selection without the analysis.
- CI is `bin/ci`, the single entry script: `.github/workflows/ci.yml` runs it on every pull request, and `docker compose -f compose.ci.yaml run --rm ci` runs it locally in a container on a clean git archive of HEAD (commit first; `docker compose -f compose.ci.yaml down` stops its services). It installs the locked dependencies and runs `composer check -- --pr`: the same scripts as `composer check`, plus the `Mutation` suite and mutation on changed files in gate 5, gate 8 (the Browser suite), gate 9 (`composer audit --locked --abandoned=report` and `npm audit`) and gate 10 (`composer docs:check`), with gates 7 and 11 reported as not run with their reasons: 7 because there is no panel UI or Storybook before the panel skeleton (B1), 11 because review by someone other than the author needs branch protection on main that requires it, a repository setting on github.com/cboxdk/cms that Sylvester makes. Mutation on changed files needs `CMS_CI_BASE_REF`, the base of the change: `ci.yml` sets it to the pull request's base commit (the commit before the push for a push to main) and checks out with `fetch-depth: 0`; for the containerized run, it may be set on the host, as in `CMS_CI_BASE_REF=HEAD~3 docker compose -f compose.ci.yaml run --rm ci`, and `docker/ci-entry.sh` builds the archive as two commits, the merge base's tree and HEAD's, with `CMS_CI_BASE_REF=HEAD~1` inside. Unset, empty or 40 zeros (the commit before a push that creates a branch), the base is derived from the checkout, by `GitMutationScope` in `bin/ci` and by `docker/ci-entry.sh` in the mounted repository: HEAD~1 when HEAD is the branch `main`, the merge base with `origin/main` (`main` when there is no `origin/main`) on another branch or a detached HEAD, and the empty tree when HEAD is the only commit or the first commit of `main`, so every file counts as changed. An unknown ref, or a base that cannot be derived, fails the mutation step with the reason. Before `bin/ci`, `docker/ci-setup.sh` runs from the checkout in both places; it fails when PCOV is not loaded, and gives the image Chromium for the Playwright that `package-lock.json` pins, and fails when it cannot. Every action in `ci.yml` is pinned to a commit SHA with its tag as a comment. It never runs the gates as root, because the tests of file permissions skip as root. Run the containerized run after changing `bin/ci`, the CI files or the environment the gates need, and record its wall time in `PROGRESS.md` against the 15-minute budget of GUARDRAILS 10.
- Run `composer check:selftest` after changing a gate, the tool configuration or the check itself. It makes a git worktree of HEAD in the system temp directory, runs `composer install` and `npm ci` there, plants one known violation per gate and passes only when each gate fails with a path inside the worktree; then it removes the worktree. It checks HEAD, so commit first. It takes about four minutes. The worktree's suites run in the worktree's own test database, and the selftest drops it as the owner role before it removes the worktree, also after a failure, so it can run next to the suites of another checkout.
- Run `composer test-db:prune` after removing a checkout or a worktree by hand (`git worktree remove`), from any checkout that remains. It drops the Postgres test databases whose checkout on this host is gone, also while a session is still connected, and keeps everything else; `composer test-db:prune -- --dry-run` prints the same verdicts and drops nothing. Composer passes options to it only after `--`: `composer test-db:prune --dry-run` runs a real prune.
- Every changed, removed or new check and test is recorded with its reason in `CHECKS-LOG.md` at the repo root (GUARDRAILS 7.3, version 1.9), in an entry under the heading of its block (`## M0`, `## M1`, ...) that starts with the task (`M1-T3:`) and says GUARDRAILS 7.3. "Til review af Sylvester" in `PROGRESS.md` holds only open decisions for Sylvester; notes without a decision go under "Info" there.
- `composer progress:check -- <block>-<task> [--changed-checks] [--range=main..HEAD]` fails unless the task is recorded: an entry naming it under "Kontroller kørt" in `PROGRESS.md` with the gates it ran, with `--changed-checks` also its entry in `CHECKS-LOG.md` under its block that says GUARDRAILS 7.3 (an entry under "Til review af Sylvester" does not count), and with `--range` no commit of the range that changes no file (feature `Cbox\Cms\Tooling\Progress`, `tools/bin/progress-check.php`). The merge queue of `.claude/workflows/cms-milestone.js` writes each task's entries in a commit `<block>-<task>: progress` and runs it before it moves main; a task reports its changed checks in `changedChecks` and never commits without a change. `composer progress:test` runs the tests that read `PROGRESS.md`, `CHECKS-LOG.md` and this checkout's review commits, which all live in `tests/Feature/Tooling/Progress` (a test there keeps them there), on the working tree and HEAD. `composer check` runs before the progress commit exists, so every agent of the workflow that commits entries, the merge queue, the regression fix and the exit phase, runs `composer progress:test` on that commit, and the merge queue moves main only after it passed.

- The Pest suites are gate 5 of GUARDRAILS 10: `Unit`, `Codecs`, `Contract`, `Postgres`, `Arch` and `Actions` in `phpunit.xml`. A module puts tests for a suite in `packages/<module>/tests/<Suite>`; its other tests are `Unit`. The `Postgres` suite needs `composer services:up` and runs through the testkit's `RealPostgres` harness: this checkout's own test database, `cms_test_<hash of the checkout's path>`, created by the owner role when it is missing (see "Hvor ting bor"), the app role on the default connection, migrations by the owner role (`migrate:fresh` once per process, after `Infrastructure\PartitionSweep` has dropped the leaf partitions an earlier run left, one statement each, so no statement runs out of the server's shared lock table), no wrapping transaction, after each test the owner drops every leaf partition (`PartitionSweep`, so a test covers the dates it writes at itself) and truncates, and a nested transaction fails the test. Helpers: `app(IndependentConnections::class)` and `app(ChildProcesses::class)`. A test that needs cluster-wide roles, such as `packages/core/tests/Postgres/DoctorRoleMembershipTest.php`, connects as the superuser of compose.yaml from `DB_SUPERUSER_USERNAME` and `DB_SUPERUSER_PASSWORD` in `phpunit.xml`, makes scratch roles under random names and drops them after the test; the application never connects as it. The testkit's `RealValkey` harness runs there too: every Redis connection uses database index 15 and a key prefix per PHP process, `cms_test_<run id>_`, and the keys under it are removed with SCAN and UNLINK after each test and when the process ends. The run is `app(ValkeyRun::class)`.
- The `Browser` suite is gate 8 of GUARDRAILS 10: Pest 5 browser tests in `tests/Browser`, run with `composer image:run -- vendor/bin/pest --testsuite=Browser`, in the dev image with the image's Chromium for the Playwright that `package.json` pins. The browser plugin serves the Testbench workbench application in-process on a free port, so a test calls `visit('/')` with a path; routes live in `workbench/routes/web.php` with the web middleware group, and a test may add its own with `Route::get()`. Each page test asserts its visible text, `assertNoConsoleLogs()` and `assertNoJavaScriptErrors()`. Screenshots of failures land in `tests/Browser/Screenshots`, which git ignores.
- The `Mutation` suite holds the tests that need a coverage driver, in `tests/Mutation`: mutation on changed files for real, on a scratch repository. The local profile leaves the suite out (`LocalProfile::OTHER_SUITES`) and the PR profile runs it in gate 5. Run it with `composer image:run -- vendor/bin/pest --testsuite=Mutation`, which has PCOV in the dev image, from any checkout. Mutation on changed files itself runs with `CMS_CI_BASE_REF=<base> composer check -- --pr`, which passes `CMS_CI_BASE_REF` into the image.
- `cms:doctor` checks the workbench's dev database `cms`, which every checkout shares. In the php container, `docker compose exec php vendor/bin/testbench cms:doctor` needs no flag: compose.yaml mounts the drop-in `docker/php/conf.d/cms.ini` read-only as `/usr/local/etc/php/conf.d/zz-cms.ini`, after the image's `99-cbox.ini`, and it sets `allow_url_fopen = Off`; Composer there downloads through the curl extension. On a host whose php.ini has `allow_url_fopen = On`, such as Herd's, run `php -d allow_url_fopen=0 vendor/bin/testbench cms:doctor`; without the flag `php.allow_url_fopen` fails and the doctor exits 78. The CI files keep the image's default. Prepare the database from the main checkout, never from a worktree: `composer services:up`, then `composer dev:prepare`, which runs the migrations as the owner role (`migrate --database=pgsql_owner`, the connection in `cbox-cms.database.owner_connection`), then `cms:partitions:maintain` for the partition runway, then `cms:build`. Each step is idempotent, so run it again after pulling a new migration; it stops at a failing step and exits with its code. Without it, `partitions.runway` fails with `doctor_partition_table_unmanageable` and the doctor exits 78.
- Services for tests run in Docker on cboxdk images: `ghcr.io/cboxdk/postgres:18` and `ghcr.io/cboxdk/valkey:8`; PHP on `ghcr.io/cboxdk/php-baseimages/php-cli:8.5-bookworm-dev-v1`. Do not use Herd's Postgres for tests. Postgres 17 stays the minimum, so never use features that arrived in 18 (GUARDRAILS 1.2).
- `composer services:up` and `composer services:down` run `tools/bin/services.php` (feature `Cbox\Cms\Tooling\Services`). It finds the main checkout from `git rev-parse --path-format=absolute --git-common-dir` and always runs docker compose with the main checkout's `compose.yaml` and `--project-directory`, so no container of compose.yaml ever mounts a worktree. From the main checkout, services:up runs `up -d --wait` and then the idempotent `10-cms.sh`, and services:down stops the services and keeps the volumes. The services are shared by the main checkout and every linked worktree: from a worktree, services:up runs `up -d --wait --no-recreate postgres valkey`, so it never recreates a running container and never starts php, then runs `10-cms.sh`, and says that the php container mounts the main checkout; services:down refuses with exit 1. `docker compose exec php ...` therefore always runs the main checkout's code, not a worktree's; `composer check`, `composer test:affected` and `composer image:run` run the current checkout's code in a container of their own. `tests/Feature/Tooling/Ci/ServicesScriptTest.php` covers it with a fake docker.

## Hvor ting bor

The namespace layout for the layers of GUARDRAILS 2.5. The Arch suite (`vendor/bin/pest --testsuite=Arch`, files in `tests/Arch`) enforces it over `packages/*/src` and `workbench/app`. The Arch suite checks the "May not use" column and the only-use rules for Domain, Actions and Infrastructure; the `mixed` and `array` column is enforced by the testkit's PHPStan rules in `packages/testkit/src/Phpstan`. This section is the same in `CLAUDE.md` and `AGENTS.md`; a test keeps them equal.

### Modules

Cbox CMS is one Composer package, `cboxdk/cms`, a library like `statamic/cms` (GUARDRAILS 2.6, PRD 2.32), with one `composer.json` at the repository root. There is no `composer.json` per module and no path repository for a module; the one path repository brings the workbench's fixture addon (below). The kernel is seven modules, each a namespace of the package:

| Module | Namespace | Directory | What it holds |
|---|---|---|---|
| contracts | `Cbox\Cms\Contracts` | `packages/contracts` | contracts, attributes, ids, the types the contracts take, and the JSON Schemas in `resources/schemas`; depends only on PHP |
| core | `Cbox\Cms\Core` | `packages/core` | the default implementations, the partition manager, the registry, the doctor, `config/cbox-cms.php` and the migrations |
| http | `Cbox\Cms\Http` | `packages/http` | the HTTP surface |
| cli | `Cbox\Cms\Cli` | `packages/cli` | the Artisan surface: `cms:build`, `cms:doctor`, `cms:partitions:maintain` |
| mcp | `Cbox\Cms\Mcp` | `packages/mcp` | the MCP surface: a tool per action exposed on MCP, for agents, on `laravel/mcp` behind its adapter |
| generators | `Cbox\Cms\Generators` | `packages/generators` | the blueprint reader, the generators, `cms:generate` and `cms:schema:editor`; development only |
| testkit | `Cbox\Cms\Testkit` | `packages/testkit` | fakes, shared contract suites, the Postgres and Valkey harnesses, the PHPStan rules and the shared tool configuration in `config/`; development only |

- Layout. A module's code is `packages/<module>/src`, the PSR-4 root of its namespace in `autoload`; its tests are `packages/<module>/tests`, the PSR-4 root of `Cbox\Cms\<Module>\Tests` in `autoload-dev`; its other files sit beside them (`config/`, `database/migrations/`, `resources/schemas/`, `bin/`). Its service provider sits at the root of its namespace and is listed in `extra.laravel.providers`, and `testbench.yaml` registers the same providers before `WorkbenchServiceProvider`.
- Why the layout stays `packages/<module>/src` after the merge into one package: the directory names the module, and the checks and the published paths read it. The Arch suite scopes by `packages/*/src`, `phpstan.neon` lists each module's directories and `rector.php` globs `packages/*/{bin,config,database,src,tests}`, the content type scan reads `packages/{contracts,core,testkit,generators,http,cli,mcp}/src`, gate 10's inventory by `packages/*/src` and `packages/*/resources/schemas`, mutation on changed files by `packages/*/src`, `Progress\Domain\CheckPaths` by the `tests` directories, and the selftest plants in `packages/core/src/Selftest`. Addons include `vendor/cboxdk/cms/packages/testkit/config/phpstan.neon` (and `pint.json` and `rector.php`), and applications' blueprint files point at `vendor/cboxdk/cms/packages/contracts/resources/schemas/blueprint.v1.json`. Moving the code to `src/<Module>` would change all of these and every file's history for no change in behaviour.
- The boundaries. No package boundary keeps the modules apart, so `tests/Arch/ModulesTest.php` does, with the rules in `Cbox\Cms\Tests\Support\Arch\ModuleDependencies`: the repository is the one library `cboxdk/cms` with no manifest per module; every directory below `packages/` is a module in `ModuleDependencies::MODULES`, autoloaded from its `src` and its tests from its `tests`; the modules' providers are in `extra.laravel.providers`; contracts uses no other module and no package; core, http, cli and mcp never use the testkit or the generators, the generators never use the testkit, and the testkit uses no module but contracts (`FORBIDDEN_MODULES`); no module uses the tests, the tooling, the workbench or the examples (`DEVELOPMENT_CODE`); every package a module uses is in `require` or `suggest`, and the production modules (`PRODUCTION`: contracts, core, http, cli, mcp) use none that is only suggested. A class counts as used when src names it in code, and a class outside the package is mapped to the installed package that holds its file. The last tests plant each kind of violation in a scratch directory and check that it is reported. The layers of the table below and the content type rule hold in every module.
- Dependencies. `require` holds only what the production modules use: PHP, `composer-runtime-api`, `illuminate/console`, `illuminate/contracts`, `illuminate/database`, `illuminate/redis`, `illuminate/support`, `psr/clock`, `psr/log`, `symfony/console` and `symfony/process`. The testkit's and the generators' heavy dependencies, `phpstan/phpstan`, `larastan/larastan`, `rector/rector`, `driftingly/rector-laravel`, `laravel/pint`, `orchestra/testbench`, `phpunit/phpunit`, `symfony/yaml` and `opis/json-schema`, are in `suggest`, each with the reason, and in this repository's `require-dev`; an application or addon puts the ones it uses in its own `require-dev`, so they never reach production. The generators check theirs before they read a blueprint (`Schema\Boundary\SuggestedPackages`, `generate_invalid_config` with the `composer require --dev` command). `docs/requirements.md` restates both lists, and a test holds it to `composer.json`.
- New modules. A first-party module is a new namespace in the same package, never a package of its own: MCP as `Cbox\Cms\Mcp` in `packages/mcp`, the panel's PHP side as `Cbox\Cms\Panel` in `packages/panel` (its React code is `js/panel`, published to npm), and a module that owns content types, such as end-user accounts with the member profile (PRD 15.1), as `Cbox\Cms\Members` in `packages/members`, with its types in its own schema files. Adding one means its PSR-4 roots in `autoload` and `autoload-dev`, its provider in `extra.laravel.providers` and `testbench.yaml`, its entry in `ModuleDependencies::MODULES`, `FORBIDDEN_MODULES` and, when it runs in production, `PRODUCTION`, its directories in `phpstan.neon`'s `paths`, and its directory in `ContentTypeScan` when it is kernel code. E-commerce is an addon with a package of its own that requires `cboxdk/cms` and uses only `#[Stable]` and `#[Experimental]` API (GUARDRAILS 2.3).

### Layers

Code sits in a feature namespace below its module, and the layer is a namespace segment below the feature: in `Cbox\Cms\Core\ReceiptStore\Adapter\PostgresReceiptStore` the module is core, the feature `ReceiptStore` and the layer `Adapter`, and `Cbox\Cms\Core\Entries\Domain\Commands\ReleaseVariant` has the same shape. "Module" in this file always means one of the modules above; the namespace below it is a feature. A namespace is in a layer when one of its segments is the layer name, either as the last segment or with more segments below it. When several segments match, the innermost one decides: `Cbox\Cms\Http\Boundary\RequestParser` is Boundary. `Domain` does not match `DomainEvents`.

| Segment | What lives there | May use | May not use |
|---|---|---|---|
| `Domain` | value objects, enums, invariants, domain interfaces | the domain and the contracts | everything else, including `Illuminate\Http`, facades and Eloquent |
| `Domain\Commands`, `Domain\Queries`, `Domain\Dto`, `Domain\Receipts` | command and query DTOs, other DTOs, receipts and results | as Domain | as Domain; only `final readonly` classes, no enums or interfaces |
| `Actions` | write actions, query actions and planners | the domain, the contracts, other classes in Actions | the framework, the DB facade, connections; only `final readonly` classes |
| `Boundary` | HTTP parsers, config readers, JSON decoders, queue payloads | the domain, the contracts, the framework, `mixed` and `array` | actions, surfaces |
| `Adapter` | implementations of contracts that need the framework or Postgres: the receipt and idempotency stores and their row mappers, Eloquent casts, Inertia props | the domain, the contracts, the framework, `mixed` and `array` | actions, surfaces |
| `Infrastructure` | Eloquent models, migration support, the partition manager | the domain, the contracts, `Illuminate\Database`, Boundary (the row mappers and error readers for what Postgres returns), casts in Adapter | `Illuminate\Http`, facades, actions, surfaces, `mixed` |
| `Jobs` | queue jobs; a surface | actions, DTOs, Boundary | Infrastructure, Adapter, Eloquent, the DB facade, connections |
| `Http` | the http module, `Cbox\Cms\Http`; a surface | actions, DTOs, Boundary | Infrastructure, Adapter, Eloquent |
| `Cli` | the cli module, `Cbox\Cms\Cli`; a surface. Artisan commands live in `Cli\Console`, never in a `Commands` namespace | actions, DTOs, Boundary | Infrastructure, Adapter, Eloquent |
| `Mcp` | the mcp module, `Cbox\Cms\Mcp`; a surface. `laravel/mcp` is used only in `Mcp\Adapter`, whose server reaches the surface through the port `Mcp\Domain\McpEndpoint` | actions, DTOs, Boundary | Infrastructure, Adapter, Eloquent |

More rules:

- The contracts module, `Cbox\Cms\Contracts`, is part of the domain and has no layer segments. The attributes `#[Stable]`, `#[Experimental]`, `#[Internal]`, `#[Command]`, `#[Query]` and `#[Hook]`, and the enum `Phase`, live in `Cbox\Cms\Contracts\Attributes`. `#[Action(handles: ..., surfaces: [...])]`, the enum `Surface` (`Rest`, `Inertia`, `Mcp`, `Cli`) and `UnknownSurface`, which `#[Action]` throws for anything in `surfaces` that is not a case, live there too; `cms:build` registers the actions in `actions.php`. `#[Subscription(name, events: [...], lane: ..., projection: ...)]`, with `UnknownLane` and `UnknownEvent`, lives there too, and the subscriber contract `Subscriber` (`handle(StoredEvent)`), the enum `Lane` (`Critical`, `Standard`, `External`, `Revalidate`, `Background`, PRD 7.6) and `SubscriptionName` live in `Cbox\Cms\Contracts\Subscribers`; `cms:build` registers the subscribers in `subscribers.php` (`docs/addons/subscribers.md`). Every type in `Cbox\Cms\Contracts` is a final readonly class, an interface, an enum or a final exception (`tests/Arch/ContractsShapesTest.php`).
- `Commands`, `Queries`, `Dto` and `Receipts` namespaces sit only below `Domain` or in the contracts module.
- The pipeline's shapes live in the contracts module (GUARDRAILS 2.1, PRD 5.5, 6.1, 6.2; `docs/addons/commands.md`, `plans.md` and `queries.md`). `Pipeline\Command` and `Pipeline\Query` are marker interfaces for the command and query DTOs, which declare their name and version with `#[Command]` and `#[Query]` (one namespace of `CommandName`s for both), and `Pipeline\Result` for a read's result. `Pipeline\WriteAction<TCommand, TAggregates>` has the two pure steps `resolve(Command): Aggregates` and `plan(Command, Aggregates): Plan`; `Pipeline\Aggregates::versions()` gives the `ReadVersions` the kernel checks at commit, each an `AggregateRef` (the typed ids and `Content\VariantRef`, keyed `<kind>:<id>` by `aggregateKey()`) with its `AggregateVersion`, or null when it was absent. `Pipeline\QueryAction<TQuery, TResult>` has `handle(Query): Result`. `Plans\Plan` is an ordered list of `Plans\Mutation`s and sub-plans, applied depth first (`mutations()`); the mutations are in `Plans\Mutations`: `EntryCreated`, `RevisionCreated`, `HeadMoved`, `VariantReleased`, `VariantUnreleased`, `PlacementCreated`, `PlacementWindowSet` and `ActorDeactivated` (`RevisionCreated` names the entry's `TypeId`, so the kernel validates its fields), over the ids `EntryId`, `NodeId`, `PlacementId`, `SiteId`, `ActorId` and `TypeId` in `Ids` and `Locale`, `VariantKey`, `RevisionNumber` and `TimeWindow` in `Content`. A revision's fields are `Fields\FieldValues`: the owner's `FieldMap` by `FieldHandle` and each extender's under its `FieldNamespace`, with the values in `Fields` (`NullValue`, `TextValue`, `IntegerValue`, `DecimalValue`, `BooleanValue`, `DateValue`, `DateTimeValue`, `ListValue`, `GroupValue`, `MapValue`). `Envelope\Envelope` is built by a surface, never an action: `Envelope::external()` requires the caller's `IdempotencyKey` and takes only an exposed `IssuingSurface`, and `Envelope::internal()` takes only an internal issuer (`Job`, `Scheduler`, `Subscriber`, `Sidecar`, `Seed`) and derives the key from its `UnitOfWork` as `<issuer>:<sha256 of the unit>` (`Envelope::deriveKey()`). The wait level defaults to `Commit`; the actor never appears in its `OnBehalfOf` chain; the reason's `ReasonText` has no public property and is read only with `classifiedContent()`, and `auditReason()` gives the audit chain and events the `ReasonCode` alone. A write ends in `Results\WriteResult`: the `Receipt`, at least one `CatalogError` (an `ErrorCode`, an optional `FieldPath` and the cause) when rejected, and for a dry run a `Results\DryRunReport`: the `Plan`, its `BlastRadius` (the mutations and the aggregates changed, by kind) and its diff, an `AggregateChange` per aggregate with the version read and the version the commit would give it. A command that carries the versions its caller saw implements `Pipeline\ExpectsVersions` (`expectedVersions(): ReadVersions`). The receipt, a rejection's problem details and the envelope fields a caller sends have generated JSON forms (see the kernel's JSON contracts below); no code serialises them by hand.
- The command pipeline (GUARDRAILS 2.1, 4.1, PRD 6.1, 6.2) is the action `Cbox\Cms\Core\Pipeline\Actions\CommandPipeline` (`#[Internal]`): `run(CommandCall): WriteResult`, where the `Domain\Dto\CommandCall` holds the command, the envelope and the `AccessContext`, whose principal must be the envelope's actor with its chain in order (`InvalidCommandCall` otherwise). The whole call runs in the port `Domain\CommandTransaction` (`run(AccessContext, Closure(): WriteResult)`), bound to `Adapter\ConnectionCommandTransaction` on the default connection: it begins the transaction, sets READ COMMITTED as its first statement, then `transaction_timeout` to `CommandTransaction::TIMEOUT_MILLISECONDS` (5000, PRD 7.4) by turning it off and on in one statement (`ConnectionCommandTransaction::TIMEOUT`), because Postgres restarts the timer only when the setting goes from off to on, then the call's access context through `ActorContext`; while the work runs, the process's `Adapter\SavepointRefusal` (a singleton, callbacks registered once per connection object) refuses a nested `beginTransaction()` and a `SAVEPOINT`, `RELEASE` or `ROLLBACK TO` statement on the connection with `Domain\SavepointRefused` before it reaches Postgres. It commits only a result that committed a changeset, rolls back every other result and work that throws (then throws the same exception), rolls back a commit that fails, and refuses to run inside an open transaction with `Domain\CommandTransactionOpen`; the pipeline itself never begins or ends one. It owns every phase: idempotency first (PRD 6.1; not for a dry run, which claims nothing): the `IdempotencyStore` claims the envelope's key (an internal issuer's is the key `Envelope::internal()` derived from its unit of work) in `Envelope::idempotencyScope()` with the command's content hash from the port `Domain\CommandContentHasher` (name, version and input) and the wait budget of `IdempotencySettings` (`cbox-cms.idempotency.wait_budget_ms`); `Fresh` runs the phases below and a commit completes the key with the changeset in the same transaction, `Replay` returns the first call's receipt from the `ReceiptStore` built by `Domain\ReplayReceipt` for this call's wait level (Commit is reached; a level past commit only when every listed projection has acknowledged, else `committed_wait_timeout`; the stored commit position and no consistency token) and runs nothing, a missing receipt throws `Domain\MissingReplayReceipt`, `Conflict` is `idempotency_conflict` and `InFlight` is `idempotency_in_flight`; then resolve (the actor and each actor of its on-behalf-of chain read through the `ActorDirectory` as aggregates at their version, `actor_not_active` when one is missing or not active, invariant 37; then the action's `resolve()`; `version_conflict` when a command that `ExpectsVersions` saw another version, or when the action read an actor at another version than the kernel), authorize (the port `Domain\CommandAuthorizer` with the access context, the command's name, the command and the aggregates; a `Dto\Authorization` refusal is `unauthorized` with its reason), plan (the action's `plan()`, then its shape: every aggregate a mutation changes was read, or `InvalidCommandCall`, a bug of the action, and every `RevisionCreated`'s type is in the `TypeCatalog`, or `validation_failed`), the hooks' phases, and validate (on the plan as the transform hooks left it, invariant 12: the fields of every revision pass the port `Domain\FieldValidation` at the Write stage, with paths below `fields`, then the validate hooks add theirs; errors reject with `validation_failed` followed by each error), the dry-run exit (`WriteResult::dryRun()` with `DryRunReport::of($plan, $reads)`) and commit (the port `Domain\ChangesetCommitter`, given a `Dto\PendingChangeset` with the command's name, version and input, the envelope, the access context, the plan and every read, actors included; it writes in the command transaction and answers `Dto\Committed` with the receipt and its changeset id or `Dto\VersionConflict` of `StaleRead`s, mapped to `version_conflict`; a `PartitionMissing` from the commit or from the completion of the key is `partition_missing`, and the transaction rolls back everything). Rejected and dry-run receipts use the envelope's wait level and `RetentionClass::Standard`. The action of a command comes from the port `Domain\WriteActions`, bound to `Adapter\RegistryWriteActions` (the compiled registry's `actionFor()` and the container; `UnknownCommand` for a class no write action handles), and `FieldValidation` is bound to `Boundary\TypeRulesFieldValidation`, which finds the type's validator through `TypeValidators`, puts the `FieldValues` in the input form with `Boundary\FieldValuesInput` (objects for groups and maps, lists for lists, a UTC date-time with microseconds) and runs the `InputValidator`. `CommandAuthorizer` is bound to `Access\Adapter\PostgresCommandAuthorizer`: a command is allowed only through a role of the actor whose permissions (`role_permissions`) name it and that reaches every `AuthorizationTarget` (a `NodeId` and a `Locale`, or null for every locale) of the action's `Aggregates::authorizationScope()`, as `Access\Domain\PermissionRule` decides with the AccessCompiler's nearest-grant rule per role and locale; a target in every locale must be reached in each, `AuthorizationScope::anywhere()` (no node, or the aggregate read as absent) needs the permission on some node, and the anonymous principal is refused. It reads the grants and the targets' paths through `Access\Adapter\PostgresGrants` under the command transaction's actor context. `FakeCommandAuthorizer::granting()` decides the same from `Tests\Access\Fakes\FakePermissions`, held to it by `CommandAuthorizerBehaviour`. The content hasher is `CodecCommandContentHasher` (over the command's canonical form from its generated codec). `resolve()` and `plan()` get the command and the aggregates and nothing else, and `tests/Arch/ActionsTest.php` (`Cbox\Cms\Tests\Support\Arch\ActionPlacement`, covered by `tests/Feature/Tooling/ActionPlacementTest.php`) holds every `WriteAction` and `QueryAction` of `packages/*/src` and `workbench/app` to an `Actions` namespace, where the layer's rules forbid connections and transactions. The pipeline's tests are `packages/core/tests/Actions/CommandPipelineTest.php` and `CommandPipelineIdempotencyTest.php` (with the testkit's fake idempotency and receipt stores) with the test-only command `probe.rename` (`packages/core/tests/Pipeline/Probe`) and the fakes in `packages/core/tests/Pipeline/Fakes`; `WriteActionsBehaviour`, `FieldValidationBehaviour` and `CommandTransactionBehaviour` hold the fakes of the three bound ports to their implementations. `docs/addons/commands.md` describes the phases.
- The commit (PRD 6.2 phase 7, 7.3, 8.4, GUARDRAILS 4.1) is `Cbox\Cms\Core\Pipeline\Adapter\PostgresChangesetCommitter`, bound to `ChangesetCommitter`, on the command transaction's connection and under its actor context; it never begins, ends or savepoints a transaction and throws `TransactionRequired::forChangeset()` outside one. It locks every read aggregate, actors included, one at a time in aggregate key order through the `Domain\VersionLock` of its kind (the part of the key before the first colon), with `Domain\LockStrength::Update` for an aggregate the plan changes and `Share` for one it only read; an aggregate read as absent first takes the transaction-scoped advisory lock `Adapter\AggregateLock::of($aggregate)` (first 64 bits of a versioned SHA-256 of the key), so two creates of one aggregate end in `version_conflict`, not a unique violation. Any stale read answers `VersionConflict` and writes nothing. Then it writes the changeset through `Changesets\Infrastructure\ChangesetWriter` (`changeset_register` with retention class Standard, `changesets` with `format_version` 1 and the commit position as the `xid` default, `changeset_principals` from position 1, the reason's text in `changeset_reason_texts` classified `personal`, and one `audit` row with the changed aggregates' keys and no legal basis, from a `Changesets\Domain\Dto\ChangesetRecord`), each mutation in plan order through the `Domain\MutationWriter` of its class with a `Dto\MutationContext` (changeset id, the Clock's time, the actor, and the aggregate's new version: one above the version read, 1 for an absent one, the same for every mutation of one aggregate), the returned events through the `EventWriter` (bulk stream for the issuers `migration` and `seed`, interactive otherwise), and the `StoredReceipt` with `TransactionPosition::current()` and the projections of `AffectedProjections`. An empty plan, a mutation without a writer, a kind without a lock, two writers or locks for one class or kind, or an event about another version than the context's throws `Domain\UncommittableChangeset`. The registries are `Domain\MutationWriters` and `Domain\VersionLocks`, built from the container tags `MutationWriters::TAG` and `VersionLocks::TAG`: a command task tags its writers and locks; the core tags `Identity\Adapter\PostgresActorVersionLock`, which locks through the SECURITY DEFINER lookup `cms_identity_lock_actor(uuid, boolean)` (FOR SHARE, or FOR NO KEY UPDATE for a change) because the app role reads no identity row. The migration `*_add_commit_locks_and_audit_variants.php` adds that function and lets `audit.aggregates` hold a variant's key `variant:<uuid>:<variant>`. The tests run the real pipeline with the test-only command `tally.add` and its writer, lock and scratch table `tally_counters` (`packages/core/tests/Pipeline/Tally`, `TallyWorld`): `packages/core/tests/Postgres/PostgresChangesetCommitterTest.php` (all or nothing across changeset, audit, events, idempotency record and receipt, `partition_missing`, `version_conflict`) and `tests/Postgres/WalkingSkeleton/IdempotentRepeatsTest.php`. The reads are locked in runs of one kind and strength, which the key order groups because a key starts with its kind: the advisory locks of a run's absent aggregates in one statement (`PostgresChangesetCommitter::LOCK_ABSENT_ALL`), and its rows in one when the kind's lock is a `Domain\BatchVersionLock` (`lockAll()`; the entry, variant and node locks are). A run of mutations of one class that follow each other in the plan goes to a `Domain\BatchMutationWriter` at once (`writeAll()` of `Dto\PendingMutation`s; the four entry writers are one, their `write()` is `writeAll()` of one mutation, and `TypeRows` has `writeAll()` and `releaseAll()`), each event still held to its mutation's version; `packages/core/tests/Postgres/BatchCommitTest.php` covers the runs. `ChangesetCommitterBehaviour` (`packages/core/tests/Pipeline`) holds the action tests' `FakeChangesetCommitter` to it, with the tally: an empty plan and a plan that changes an unread aggregate are refused, a stale read (an absent aggregate created twice included) is `VersionConflict` with every stale read and commits nothing, the receipt lists the projections of the events, and an uncovered time throws `PartitionMissing`; the fake compares each read with the versions a test states with `at()` and the versions its own commits left.
- The entry commands (PRD 4.1, 5.4, 6.4, 11.6) live in the core module `Cbox\Cms\Core\Entries`: the commands `Domain\Commands\CreateEntry` (`entry.create` version 1: the caller's `EntryId`, the `TypeId`, the home `NodeId` and the `FieldValues` of the shared variant; it expects the entry absent) and `Domain\Commands\ReviseEntry` (`entry.revise` version 1: the entry, the `AggregateVersion` of its shared variant the caller read, and every field), both `ExpectsVersions`, and their actions `Actions\CreateEntryAction` and `Actions\ReviseEntryAction`, `#[Action]` on the surfaces rest, inertia, mcp and cli. resolve() reads through the port `Domain\EntryReader` (bound to `Adapter\PostgresEntryReader`, one lookup by key under the actor context, with a fake and `EntryReaderBehaviour` in `packages/core/tests/Entries`); a create reads the entry and its variant as absent and the home node at its version, a revise the entry and the variant. A create plans `EntryCreated`, `RevisionCreated` 1 and `HeadMoved` null to 1; a revise `RevisionCreated` and `HeadMoved` from the head's revision to the next, for the entry's own type. The core tags the version locks `Entries\Adapter\PostgresEntryVersionLock` (`entry`), `PostgresVariantVersionLock` (`variant`, the row of `variant_heads`) and `Structure\Adapter\PostgresNodeVersionLock` (`node`), FOR SHARE or FOR NO KEY UPDATE, and the writers `EntryCreatedWriter` (the `entries` row; `entry.created`), `RevisionCreatedWriter` (the `variant_heads` row with the first revision; for `history: full` the `revisions` row, a draft, and its `revision_payloads` row; for audit-only or none the `head_snapshots` row with its `rev_no`, the column the migration `*_add_revision_number_to_head_snapshots.php` adds; then the type table's row through `Adapter\TypeRows`: the draft row for `stages: draft-release`, removed again when it equals the released row, and the released row for `stages: none`) and `HeadMovedWriter` (the head's draft revision, schema version and version in one statement; `variant.revised`). - The publish commands (PRD 5.6, 5.10, 6.2, 6.4, invariants 7, 14 and 18) live in the core module `Cbox\Cms\Core\Publishing`: `Domain\Commands\PublishEntry` (`entry.publish` version 1: the entry, the shared variant's `AggregateVersion`, a `?RevisionNumber` to release, null for and only for a type with `stages: none`, the home `PlacementId` with its `AggregateVersion`, the `Locale` and a `?TimeWindow`, null for live from now) and `Domain\Commands\UnpublishEntry` (`entry.unpublish` version 1: the entry and the shared variant's version), with `Actions\PublishEntryAction` and `Actions\UnpublishEntryAction`, `#[Action]` on rest, inertia, mcp and cli. - `actor.deactivate` (PRD 5.16, 6.4, invariant 37) is the command `Cbox\Cms\Core\Identity\Domain\Commands\DeactivateActor` (the actor and a `Contracts\Identity\DeactivationSource`, `local` by default or `inactivity`) with the write action `Identity\Actions\DeactivateActorAction`, exposed on no surface in M1. It reads the actor through the `ActorDirectory` and plans one `ActorDeactivated(actor, source)` for an active or pending actor, and nothing for one that is missing, deactivated or deprovisioned; the `CommandPipeline` rejects a plan without mutations with `validation_failed`, so a second deactivation changes nothing. The writer `Identity\Adapter\ActorDeactivatedWriter`, tagged under `MutationWriters::TAG`, calls the owner-role function `cms_identity_deactivate_actor(actor, version, source, changeset)` (migration `*_add_actor_deactivation.php`): one statement that sets the state `deactivated`, the context's version, the credential generation one higher and `actors.deactivation_source`, and ends every grant of the actor that has not ended by setting `grants.ended_changeset_id`, whatever the number of grants; it raises 42501 outside the transaction of an actor.deactivate changeset by the context's actor. - Range partitions are kept by the partition manager in `Cbox\Cms\Core\Partitions` (PRD 4, 4.2). A partitioned table is listed in `cbox-cms.database.partitions.tables` with its key (`uuid7`: bounds are `Uuid7::lowestAt()` of the span's first millisecond and of the next span's; or `timestamp`), its interval (`day` or `month`, spans start at midnight UTC) and `retention_days` (null keeps all). Partitions are named `<table>_p<YYYYMMDD>` or `<table>_p<YYYYMM>`, and only those names are managed. There is no DEFAULT partition, so a write outside the partitions fails; an adapter that writes to a partitioned table catches the `QueryException` and throws `MissingPartitionMapper::map()`, which turns SQLSTATE 23514 "no partition of relation" into `Cbox\Cms\Contracts\Storage\PartitionMissing` (`CODE` `partition_missing`). `cms:partitions:maintain` (scheduled hourly by `CoreServiceProvider` in a process where the owner connection is configured, `CoreServiceProvider::ownerConnectionConfigured()`) runs the action `MaintainPartitions` at the Clock's time: it creates partitions from now to `runway_days` ahead (default 14) and removes partitions past retention with `DETACH PARTITION CONCURRENTLY` and `DROP TABLE`, never `DELETE`. Because autovacuum never analyzes a partitioned table (PRD 4.2), a maintain run then runs `ANALYZE` on the root of each partition tree whose partitions it changed (`pg_partition_root()`, so `receipts` for `receipts_standard` and `receipts_evidence`), once per root, as step `DdlStep::Analyze` under the same lock timeout and retry, and names the roots in `PartitionReport::$analyzed` (the command prints `analyzed <root>`); `ANALYZE ONLY` is Postgres 18 and not used, and `--from` and `--to` analyze nothing. A new partition gets its parent's row security flags and its parent's grants (`TablePrivileges::copy()`), so the owner's default privileges never reach a partition. A table with a managed name that is not a partition (detached by hand, or by a run whose Clock was ahead) and not past retention is attached again when a run needs its span (`PartitionChangeKind::Reattached`, step `DdlStep::Attach`, with the parent's row security and grants), and one left pending detach is finalized first; when Postgres refuses the attach (other columns or constraints, rows outside the span) the create phase of that table stops there with `UnmanageableTable::detachedPartition()` naming the table. It runs only on `cbox-cms.database.owner_connection` and throws `OwnerConnectionRequired` on the app connection. Every step runs with `lock_timeout` 2 s and a bounded retry with backoff, and gives up with `LockTimeout`. A run creates the partitions of every table before it retires any, and a step that gives up on one table's lock ends that phase for that table only: the `LockTimeout` goes in `PartitionReport::$gaveUp` as a `Domain\Dto\GaveUpStep` (its step, table, partition, attempts, message and the message of its cause, no exception) and the run goes on with the other tables; only a busy maintenance lock is thrown. An `UnmanageableTable` (`CODE` `partition_table_unmanageable`) also stops its table only: a table that is missing, not partitioned by range or has a DEFAULT partition gets no phase and no runway, a refused attach ends that table's create phase, and any other step on a partition that Postgres refuses for another reason than a lock wait (a DROP that a view on the partition blocks, a CREATE of a managed name that a view or a partition of another parent holds) ends that phase of that table as `UnmanageableTable::stepRefused()`; it goes in `PartitionReport::$failed` as a `Domain\Dto\FailedTable` (table, partition, message and the message of its cause) and the run goes on, so a table listed before its migration has run never stops the runway of the others. Only `UnmanageableTable::inTransaction()` is thrown. The command answers through the cli's `Boundary\PartitionReportOutput` (a `CliAnswer`, exit codes from the error catalog): it prints the report, then each step that gave up and each table that failed on standard error, and exits with the exit code of `partition_table_unmanageable` (78) when a table failed, else of `partition_lock_timeout` (75) when anything gave up, and 64 for invalid --from and --to. The doctor's `partitions.runway` fails with `doctor_partition_table_unmanageable` for such a table and still gives the runway of the others. `--from` and `--to` only create the partitions of a range. A run's report gives each table's runway from the Clock's time, with or without `--from` and `--to`: the end of the unbroken run of attached partitions from the partition that holds now, so a gap ends it. `Partitions\Domain\PartitionRunway::end()` computes it for the report and for the doctor's `partitions.runway`. Tests that write to a partitioned table first call the testkit's `app(PartitionFixtures::class)->cover($from, $to)` or `coverClock($clock, $interval)` for the dates they write at.
- Tables partitioned on a `bigint` that a sequence feeds (PRD 4.1, 7.2: `revision_payloads` on `revision_id`, `events` on `event_id`) are listed in `cbox-cms.database.partitions.tables` with the key `bigint`, no interval, `width` (ids per partition), `sequence` (unqualified, in the search path) and optionally `retention_days` with `retention_column`, a timestamptz column (both or neither). `Boundary\PartitionConfig` puts them in `PartitionPolicy::$sequenceTables` as `Domain\SequencePartitionedTable`s (retention a `Domain\SequenceRetention`), apart from the tables on time in `$tables`; a name is unique across both, and the manager, its report and the doctor take the tables on time first. A partition holds `width` ids from a multiple of `width` and is named `<table>_p<lower bound zero-padded to 19 digits>` (`SequencePartitionedTable::BOUND_DIGITS`), and only those names are managed; the last one ends at `PHP_INT_MAX`, and an id below 0 has none. The runway is counted in empty partitions ahead of the sequence's current value, `last_value` less 1 when `is_called` is false (`PartitionCatalog::sequenceValue()`): a run creates the partition that holds the current value and `partitions.runway_partitions` (default 2, 1 to 100) partitions whose lower bound is above it (`SequencePartitionedTable::runway()`), and a cover run (`--from`, `--to`) creates that runway too. `PartitionCatalog::table()` also checks the sequence (it exists, increment at least 1 and minimum at least 0, the role may SELECT it) and the retention column (a timestamptz column of the table), and throws `UnmanageableTable::sequenceMissing()`, `sequenceNotAscending()`, `sequenceUnreadable()` or `retentionColumn()`, so the table gets no phase. Retirement walks the managed partitions in id order and stops at the first it keeps: a partition is retired when the sequence has passed it (upper bound at most the current value, `SequencePartition::isPassed()`) and its newest `retention_column` value, read under step `DdlStep::Detach` with `row_security` off (`PartitionCatalog::newestRow()`), is at least `retention_days` old or the partition is empty (`SequencePartition::isExpiredAt()`), then DETACH CONCURRENTLY and DROP; a read that row security would filter is refused by Postgres and recorded as `UnmanageableTable::stepRefused()`, never taken as empty. A table with a LIST level above the range is listed once per leaf parent with the shared sequence, and its root is analyzed once. `PartitionRunway::ahead()` gives a `Domain\Dto\SequenceRunway` (current value, `coveredUntil` id or null, `partitionsAhead`) for `TableRunway::$sequence` and the doctor's `PartitionCoverage::$sequence`; the command prints `runway <table> until id <end> (<n> partitions ahead of id <current>)`, and `partitions.runway` fails when a table has fewer than `cbox-cms.doctor.partition_runway_partitions` (default 1) empty partitions ahead. The Postgres tests use the scratch tables `partition_scratch_seq` and `partition_scratch_kind` (LIST) of `PartitionScratch`, and `FakePartitionMaintenance` has `advanceSequence()` and `insertRow()`.
- The receipt store on Postgres is `Cbox\Cms\Core\ReceiptStore\Adapter\PostgresReceiptStore`, bound to `ReceiptStore` in `cbox-cms.contracts`. It runs on the default connection (or a named one), through the query builder except for that insert, and never begins a transaction. Every read, the lock included, uses the write PDO (`useWritePdo()`), so outside a transaction a lagging read host never hides a stored receipt from `find()` or `markProjection()`. Its tables come from the core migrations `packages/core/database/migrations/*_create_receipts_tables.php` and `*_add_position_to_receipts.php`: `receipts` (one row per changeset with its commit position `position`, an xid8 without a default, and no outcome or wait level) and `receipt_projections` (one row per changeset and projection), both LIST-partitioned on `retention_class` and then RANGE-partitioned on `changeset_id`, managed as `receipts_standard` and `receipt_projections_standard` (per day, `retention_days` 7) and `receipts_evidence` and `receipt_projections_evidence` (per month, never dropped). The primary keys are `(changeset_id, retention_class)` and `(changeset_id, retention_class, projection)`; there is no foreign key between them. `find()` and `markProjection()` filter on the Clock's live window (`PostgresReceiptStore::lowestLiveStandard()`), `markProjection()` updates only a pending row, and `store()` reports a duplicate without aborting the caller's transaction. The database holds the app role to that: it may update only `state` and `acknowledged_at` of `receipt_projections` (column grants from `TablePrivileges::limitColumns()`, on every partition), so an update of any other column fails with SQLSTATE 42501, and the trigger `receipt_projections_acknowledged` refuses every update of an acknowledged projection row with SQLSTATE 23000, for every role, which `markProjection()` never fires. The primary key cannot hold one receipt per changeset across the retention classes, so `store()` first takes the transaction-scoped advisory lock `ReceiptLock::of($changesetId)` (`pg_advisory_xact_lock`, the first 64 bits of a versioned SHA-256 of the changeset id), then looks for a receipt of either class, then inserts the receipt row with `ON CONFLICT DO NOTHING` and its projection rows in one statement (`PostgresReceiptStore::INSERT_RECEIPT`, a data-modifying CTE per table), so they are stored or fail together. Without an open transaction (`transactionLevel()` below 1) `store()` throws `TransactionRequired` before its first statement, so it never takes a session-level lock; a concurrent store of the same changeset waits for the first transaction and, under READ COMMITTED, gets `DuplicateReceipt`. `store()` needs READ COMMITTED, because its lookup must see a receipt committed while it waited: the lock statement `PostgresReceiptStore::LOCK_CHANGESET` also reads `transaction_isolation` and `pg_current_xact_id()`, takes the lock only at that level, and a receipt at another position throws `ForeignPosition` before the lookup, and at REPEATABLE READ or SERIALIZABLE `store()` throws `Cbox\Cms\Contracts\Consistency\UnsupportedIsolation` and holds no lock. The Postgres contract test is `packages/core/tests/Postgres/PostgresReceiptStoreContractTest.php`; it and the adapter tests cover the dates they write at with `PartitionFixtures`.
- The commit position (PRD 7.4, 8.4, 8.12) is `Cbox\Cms\Contracts\Consistency\CommitPosition`: a Postgres xid8 kept as a decimal string without leading zeros (up to `CommitPosition::MAX`, 2^64 - 1), compared by numeric value with `isBelow()`. A changeset's position is the xid8 of its command transaction, `pg_current_xact_id()`: the changeset row's `xid`, each event's `xid` and the receipt's `position` carry the same value. A read's position is the xmin of its snapshot, `pg_snapshot_xmin(pg_current_snapshot())`, and a read at position R saw every changeset whose position is below R (`$changeset->seenBy($read)`), the event horizon of PRD 7.4. `Cbox\Cms\Core\Consistency\Infrastructure\TransactionPosition::current()` (`#[Experimental]`) reads the position of the caller's open transaction on the default or a named connection and throws `TransactionRequired::forPosition()` without one, before any statement. Its fake is `packages/core/tests/Pipeline/Fakes/FakeAffectedProjections.php`, held to the registry by `AffectedProjectionsBehaviour`. `packages/core/tests/Postgres/CommitPositionTest.php` shows the rule on Postgres. - The idempotency store on Postgres is `Cbox\Cms\Core\IdempotencyStore\Adapter\PostgresIdempotencyStore`, bound to `IdempotencyStore` in `cbox-cms.contracts`. It runs on the default connection (or a named one), inside the caller's transaction, and never begins one. Its table comes from the core migration `packages/core/database/migrations/*_create_idempotency_keys_table.php`: `idempotency_keys`, RANGE-partitioned per day on `created_at` and managed with `retention_days` 7, with an index on `lock_key`, no primary or unique key, and SELECT and INSERT for the app role. Postgres cannot keep a key unique across daily partitions, so a claim is a transaction-scoped advisory lock on `ClaimLock::of($scope, $key)`, the first 64 bits of a versioned SHA-256 of the scope and key: `pg_try_advisory_xact_lock` polled with a growing sleep (2 ms up to 50 ms) until it is granted or the `WaitBudget` has passed, never a blocking lock or `lock_timeout`, which would abort the caller's transaction. The wait also ends `PostgresIdempotencyStore::TRANSACTION_MARGIN_MILLISECONDS` (250) before the transaction's `transaction_timeout`, read in the first try from `pg_settings`, `transaction_timestamp()` and `clock_timestamp()`, because that timeout counts from the start of the transaction and terminates the session; the effective budget is the lower of the two, and 0 (off) leaves the budget alone. The lookup is a separate statement after the lock, so under READ COMMITTED it sees a commit made while the claim waited; a claim at another isolation level throws `InvalidClaim::isolationLevel()` and takes no lock. The lookup matches the full scope and key, so a lock key collision only makes two keys wait for each other. A Fresh claim is noted in the transaction-local setting `cbox_cms.idempotency_claims`, which `complete()` checks and Postgres resets when the transaction ends. `created_at` is the Clock's time, or the changeset's time when that is later, and `expires_at` is `RetentionClass::Standard->expiresAt()`; the CHECK `idempotency_keys_window` keeps `expires_at` within 168 hours of `created_at`, so every live record has `created_at` at or after `PostgresIdempotencyStore::lowestLiveCreatedAt()`, 7 days before the Clock's time, and the lookup prunes the older partitions. The lookup has no upper bound on `created_at`: a changeset's time, and so a record's `created_at`, can be on a later day than the claimer's Clock (a clock that stepped back, another node's clock ahead), so it reads every partition from then onward, the runway included. The Postgres contract test is `packages/core/tests/Postgres/PostgresIdempotencyStoreContractTest.php`.
- The event log (PRD 7.2 to 7.5, 7.10, GUARDRAILS 2.4) has its contract in `Cbox\Cms\Contracts\Events`. - The event runner (PRD 7.4 to 7.8, `docs/addons/subscribers.md`) is `cms:events:run [--lane=critical] [--until-idle]`, the cli's `Console\RunEventsCommand`, which calls the action `Cbox\Cms\Core\Subscriptions\Actions\RunLane::run(LaneRun, RunnerStop)`; one process per lane, and only the critical lane is built (`Cli\Boundary\SubscriptionArguments::lane()` refuses the others with exit 64). - The wait after commit (PRD 8.4, MILESTONES M1 point 5) is phase 8 of `CommandPipeline`: once the command transaction has committed, a committed call waits for its envelope's wait level through the action `Cbox\Cms\Core\Pipeline\Actions\AwaitWaitLevel` (`#[Internal]`), which reads the receipt from the `ReceiptStore` with a growing pause (2 ms up to 50 ms) on real time, the event runner's `Subscriptions\Domain\Pacing`, never the Clock, at most `cbox-cms.receipts.wait_budget_ms` (default 5000, 0 to 30000; `Pipeline\Domain\Dto\WaitSettings`, read by `Pipeline\Boundary\WaitConfig`). - The registry (PRD 13.2) is compiled by `cms:build` (the cli's `Console\BuildCommand`, which calls the action `Cbox\Cms\Core\Registry\Actions\BuildRegistry`) to `bootstrap/cache/cms/`: `actions.php`, `commands.php`, `hooks.php`, `rest.php`, `schema.php` and `subscribers.php`, one per case of `Registry\Domain\RegistryName`, and the REST surface's `openapi.json`. The cache owns that directory: after writing the files, `FileRegistryCache` removes every other file there, but not its lock file `.lock`, subdirectories, the temporary file of a registry, or `openapi.json` and its temporary file, so a registry an earlier version wrote cannot linger. Each file returns `['build' => '<sha256>', 'entries' => [...], 'format' => 8, 'registry' => '<name>']`, sorted and without timestamps or paths, so two builds of the same code give the same bytes; `build` is the sha256 of the entries of every registry, so the files of one build carry the same one and `RegistryCacheCodec::decode()` refuses files of different builds and entries that do not match their build. A write puts every file in a temporary file first and then renames them into place one after the other, so a reader can meet the files of two builds; `FileRegistryCache::read()` then tells OPcache to forget them and loads them again, up to `FileRegistryCache::READ_ATTEMPTS` (10) times 5 ms apart, and so gives the whole old or the whole new registry. Files that stay mixed, as a build that stopped between two renames leaves them, are `MalformedRegistryCache` until cms:build runs again. Writes run one at a time, so two builds that both finish never interleave their renames: a write holds an exclusive `flock()` on `FileRegistryCache::LOCK_FILE` (`.lock` in the directory, never removed) from before its first rename until it has removed the other files, waits for it at most `FileRegistryCache::LOCK_WAIT_MILLISECONDS` (30 s) of real time, and otherwise writes nothing and throws `RegistryCacheUnwritable`; reads take no lock. `packages/core/tests/Registry/FileRegistryCacheInterleavingTest.php` puts a build's renames between a read's files through the stream wrapper `Fakes\InterleavedFiles`. A module's or an addon's service provider implements `Cbox\Cms\Contracts\Build\DeclaresScanRoots` and returns `ScanRoot`s, each a Composer package name and an absolute directory (`__DIR__`); core, http, cli, mcp and generators declare their `src` under the package name `cboxdk/cms`, and deferred providers are asked too. The scanner, `Registry\Infrastructure\AttributeScanner`, reads the classes each `.php` file declares from its tokens, loads them through the autoloader and reads `#[Action]`, `#[Command]`, `#[Query]`, `#[Hook]` and `#[Subscription]` with reflection; reflection is allowed at build time only (GUARDRAILS 2.2). Actions are sorted by the name and version of the command or query they handle, commands by name and version, hooks by command, phase in pipeline order, priority with the lowest first, package and class, and subscribers by subscription name. An `ActionEntry` holds the action class and its package, its `ActionKind` (`write` for a class that implements `WriteAction`, `query` for one that implements `QueryAction`), the command or query it handles by `CommandName`, version and class, and its surfaces in the order of `Surface`; `#[Action(handles: ...)]` names the handled class, which must be a registered `#[Command]` class for a write action and a registered `#[Query]` class for a query action. A command and a query never share a name and version (`registry_duplicate_command`). The build fails with `registry_not_an_action` for an `#[Action]` class that implements neither or both interfaces, `registry_unknown_action_command` for an action whose handled class is not a registered one of its kind, `registry_duplicate_action` for two actions of one command or query, and `registry_unknown_surface` for a surface that is not a case of `Surface` (`UnknownSurface`, or an undefined case such as `Surface::Graphql`). `CompiledRegistry::action($name, $version)` and `actionFor($class)` give the kernel the action of a command or query. A `#[Command]`, `#[Query]`, `#[Action]` or `#[Subscription]` class must be `final readonly` (GUARDRAILS 2.1), or the build fails with `registry_not_final_readonly`; a `#[Hook]` needs a `#[Command]` class and a budget of 1 to 20 ms, and its class must implement the interface of its phase, or the build fails with `registry_not_a_hook`. A build with problems writes nothing and lists every problem with a code from `BuildErrorCode`, such as `registry_duplicate_command` and `registry_unknown_hook_command`; the command then exits 65, and 73 when a cache file cannot be written or removed. At run time the container's `CompiledRegistry` singleton is read through `RegistryCache` and the Boundary `RegistryCacheCodec` into typed entries in `Registry\Domain\Dto`; a missing file throws `RegistryCacheMissing` and a damaged one `MalformedRegistryCache`. A command's name, `CommandEntry::$name` and `HookEntry::$command`, is the id `Cbox\Cms\Contracts\Ids\CommandName` (GUARDRAILS 2.2), never a string: the scanner takes it from `Command::name()`, the codec parses it and reports a bad one at `entries[<n>].name` or `entries[<n>].command`, and the compiler compares names by value. A registry is a case of `RegistryName` only when it has an entry type and a source; the slot registry (PRD 13.4) comes with the block named in `PROGRESS.md`. A `SubscriberEntry` (PRD 7.6) holds the subscriber class and its package, its `SubscriptionName`, its `Lane`, the `ProjectionName` it acknowledges on the receipt or null, and its events, each a `SubscribedEvent` of the event class and the `EventType` its `type()` gives, sorted by class; the build fails with `registry_not_a_subscriber` for a `#[Subscription]` class that does not implement `Subscriber`, `registry_unknown_event` for an event class that does not exist, does not implement `Event` or whose `type()` fails, `registry_unknown_lane` for a lane that is not a case of `Lane` (`UnknownLane`, or an undefined case such as `Lane::Urgent`), and `registry_duplicate_subscription` for two subscribers with one name. `CompiledRegistry::subscribersOf($eventClass)` and `projectionsFor($eventClass)` give the kernel the subscribers of an event class and the projections it affects, which a receipt lists (PRD 8.4). The doctor's `registry.cache` check dates the cache by the oldest of the files of `RegistryName`. Composer's `post-autoload-dump` runs `testbench cms:build`, and the cache is not committed. ## When the PRD is unclear

- If the PRD is ambiguous but one reading is clearly consistent with the rest of the PRD and GUARDRAILS, pick it, implement it, and record the interpretation under "Tolkninger" in `PROGRESS.md`.
- If the PRD needs a small correction to be buildable, edit `PRD.md` in the planning repo, add a version entry at the top of its section 0, and commit it there with message `PRD v2.x: ...`.
- If it is a decision reserved for Sylvester (the open questions in PRD section 26, product scope, naming, licensing, anything outward-facing), do not decide. Add it under "Blokeret" in `PROGRESS.md` with what it blocks, and continue with work that does not depend on it.

## Autopilot

`.harness/autopilot.on` switches on the stop guard in `.harness/stop-hook.sh`. While it is on, a session may not stop until `PROGRESS.md` says `STATUS: complete` or `STATUS: blocked`. `.harness/waiting` marks that a background workflow is running and lets the session idle until it reports back. The workflow for one block is `.claude/workflows/cms-milestone.js`.

Delete `.harness/autopilot.on` to stop autopilot.
